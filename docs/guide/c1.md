## What the controller does

The controller takes the measured state (q, q̇) and returns the generalized acceleration q̈* = A(q)⁻¹(μ − Ȧq̇), which makes the outputs ȳ obey ȳ̈ = μ; it never sees M, C or G. The caller turns q̈* into an input with eq:fb, u = M q̈* + C q̇ + G. For the rigid body that line is `src/rigid_body_example.cpp:103`; for the Panda at the joint-acceleration level the simulator integrates q̈* directly (`src/panda_example.cpp:196-198`).

The whole design follows from one identity. Differentiate ȳ̇ = A(q) q̇ once more and choose q̈ so that the result is μ:

```latex
\dot{\bar y} = A(q)\,\dot q, \qquad
\ddot{\bar y} = A(q)\,\ddot q + \dot A\,\dot q, \qquad
\ddot q^{*} = A(q)^{-1}\bigl(\mu - \dot A\,\dot q\bigr) \;\Longrightarrow\; \ddot{\bar y} = \mu .
```

Every piece of the right-hand side is computed from geometry alone: A from the tube and the kinematics, Ȧq̇ by a finite difference of A, μ from the gains and the reference. That is why one class, `Controller<System>` in `include/se3pf/controller.hpp`, serves the rigid-body simulation, the Panda simulation, the MuJoCo runs and (later) the robot.

### The System concept

A "concept" here is a list of requirements that a template argument must meet. C++17 has no language feature to state such a list (C++20 adds `concept`), so it lives in the comment above the class, and the compiler checks it only when you write `Controller<RigidBody>` or `Controller<PandaArm>`:

```cpp
// include/se3pf/controller.hpp:121-137
    // The path following controller of Section V for a fully actuated system with pose output (Algorithm 1).
    //
    // System provides (see RigidBody and PandaArm, and the design doc, The system interface):
    //     static constexpr int kDof;                                       n = 6 (rigid body) or 7 (Panda)
    //     using Config;                                                    q: a Pose, or a Vec7 of joint angles
    //     static Pose output(const Config& q, Mat<6, kDof>* Jb);           Pi(q) and the body Jacobian J_b(q)
    //     static Config retract(const Config& q, const Vec<kDof>& dq, double h);  a curve through q with velocity dq
    //
    // The outputs are ybar = (eta, xi) for n = 6 and ybar = (eta, xi, beta) for n = 7, with ybar_dot = A(q) qdot
    // (eq:A). step returns the generalized acceleration qdd* = A^-1 (mu - Adot qdot) that makes ybar_dd = mu. The
    // caller turns it into the input of eq:fb, u = M qdd* + C qdot + G, so the controller needs no dynamics.
    //
    // The controller keeps a reference to the tube, so the tube (and its path) must outlive it, and a pointer to the
    // redundancy output, which must outlive it too. Construction is offline and may throw; outputs and step are
    // online: fixed-size types only, no allocation, no exceptions (failure is a return value of false).
    template <class System>
    class Controller {
```

| Member | Meaning | `RigidBody` | `PandaArm` |
| --- | --- | --- | --- |
| `static constexpr int kDof` | n, the number of generalized velocities | 6 | 7 |
| `using Config` | the type of q | `Pose` (a 4 × 4 `Eigen::Matrix4d`) | `Vec7` (joint angles) |
| `static Pose output(const Config&, Mat<6, kDof>*)` | Π(q) and, if the pointer is not null, J_b(q) | Π = id, J_b = I (`src/rigid_body.cpp:44`) | flange forward kinematics and body Jacobian (`include/se3pf/panda.hpp:24`) |
| `static Config retract(const Config&, const Vec<kDof>&, double h)` | a curve c(h) with c(0) = q, c′(0) = q̇ | g Exp_I(hζ) (`src/rigid_body.cpp:54`) | q + h q̇ (`include/se3pf/panda.hpp:27`) |

Two consequences matter. First, n and `Config` are known at compile time, so every matrix in the controller has a fixed size (6 × 6 or 7 × 7) and lives on the stack. Second, `output` and `retract` are `static`: the controller never holds a `System` object, it only uses the type. A `RigidBody` object (with its J and m) exists only in the simulator, which needs the dynamics.

### RedundancyOutput

`RedundancyOutput` is the one place where the controller itself makes a virtual call: it is how the seventh output β enters A. It is an abstract base class, that is, a class with pure virtual functions (`= 0`) that you cannot instantiate, only derive from:

```cpp
// include/se3pf/redundancy.hpp:9-20
    class RedundancyOutput {
        public:
            virtual ~RedundancyOutput() = default;

            // beta(q) and its differential dbeta (a row, stored as a column), given eta(q) and d eta(q), the first
            // row of J_Psi^-1 J_b, which the controller has already computed.
            virtual void evaluate(const Vec7& q, double eta, const Vec7& deta, double& beta, Vec7& dbeta) const = 0;

            // Among configurations with eta(Pi(q)) = eta, the level set {beta = value} is the hyperplane p^T q = b.
            // Used to find start configurations.
            virtual void levelSet(double eta, double value, Vec7& p, double& b) const = 0;
    };
```

- `virtual ~RedundancyOutput() = default;` gives the base a virtual destructor. Without it, deleting a derived object through a `RedundancyOutput*` would be undefined behaviour (in practice only the base destructor runs). `= default` means "the compiler-written body".
- `evaluate` receives η and dη instead of computing them. η(q) and dη(q) come from the projection and from row 0 of J_Ψ⁻¹J_b, which `Controller::outputs` has already paid for, so β of Lemma 3 (eq:beta-flat) and its differential eq:dbeta cost only two spline lookups (`lift_.eval` and `kernel_.eval`, `src/lift.cpp:276-277`).
- dβ is a row (a covector) in the paper, stored as a `Vec7` column; the controller transposes it into row 6 of A (`include/se3pf/controller.hpp:236`).
- Results come back through reference parameters (`double& beta, Vec7& dbeta`). Returning a small struct would work as well and would not allocate either; out-parameters are the convention of this code base, as in `Tube::outputs`.
- The trailing `const` on both functions promises that evaluating β does not change the object, so a `const RedundancyOutput*` can call them.
- `levelSet` is not used by the controller at all. It describes {β = value} as a hyperplane pᵀq = b at fixed η, which `startConfiguration` (`src/lift.cpp:306`) needs to build start configurations with a given β.

Three classes implement it:

| Implementation | β | dβ | Where |
| --- | --- | --- | --- |
| `LiftRedundancy` | X(η)ᵀ(q − q*(η)), eq:beta-flat | Xᵀ + (X′ᵀ(q − q*) − Xᵀq*′) dη, eq:dbeta | `src/lift.cpp:273-281` |
| `CouplingRedundancy` | q₃ − q₁ (`q[2] - q[0]`) | e₃ − e₁, independent of q and η | `src/lift.cpp:291-295` |
| `WavyCouplingOutput` (test only) | q₃ − q₁ + 0.2 sin(8η) | e₃ − e₁ + 1.6 cos(8η) dη | `tests/test_controller.cpp:256-276` |

The comment at `include/se3pf/redundancy.hpp:8` sets the rule for implementations: they must not allocate or throw, because `evaluate` runs inside every 1 kHz step, up to three times (once per projection: three when moving, one at rest).

### The rigid body as the first System

The free rigid body is the simplest possible `System`: its configuration is the pose itself, so Π = id and J_b = I, and A reduces to J_Ψ⁻¹. With n = 6 there is no redundancy and no β, so `Controller<RigidBody>` exercises everything in the controller except the n = 7 branches. That is why it was built first (milestone M6 in `TICKETS.md:121`) and why most generic controller tests use it.

### One step at a glance

`Controller::step` (`include/se3pf/controller.hpp:246-328`) is Algorithm 1. Its parts, each explained line by line in the section on `Controller<System>`:

1. `outputs(q, etaHat_, out)`: g = Π(q), J_b, (η, ξ) by Newton's method from the prediction η̂, J_Ψ, β and A.
1. `yDot = out.A * dq`: η̇, ξ̇ and β̇ in one product.
1. Ȧq̇ by a central difference of A along `System::retract(q, dq, ±1e-5)`, skipped at rest.
1. μ∥ from eq:tan-vel or eq:tan-pos, μ⋔ from eq:transverse, μ_β from eq:beta-law.
1. Optionally μ ← r(t/T) μ (the hardware ramp).
1. σ_min(A) by SVD; refuse below 1e-9.
1. q̈* = A⁻¹(μ − Ȧq̇) by one LU solve; refuse a non-finite result.
1. η̂ ← (η + η̇Δt) mod L for the next cycle; fill `Status`.

What the controller deliberately does not do: dynamics (the caller adds M, C, G), integration (the simulator or the robot moves the plant), logging (the `Status` struct carries what a logger needs), and safety margins (`HardwareBounds` in `include/se3pf/panda.hpp:53-63` and the MuJoCo checks). Its only own guard is the numerical one: refuse when A is singular to working precision.
