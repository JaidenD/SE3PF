## What sits on top of the library

Four things sit on top of the `se3pf` library: two plain simulation apps, a separate MuJoCo layer, Python scripts that read the apps' CSV logs, and the build and CI scripts that tie everything together. None of them changes the controller. They connect the library to a plant, run it, compare its numbers with the expected ones, and fail loudly if something is off.

### The map

| Piece | Files | Links against | Built or run | Produces |
| --- | --- | --- | --- | --- |
| Plain apps | `apps/rigid_body_sim.cpp`, `apps/panda_sim.cpp`, `apps/panda_limits.hpp` | `se3pf` | always built | `out/rigid_body_pose.csv`, `out/rigid_body_velocity.csv`, `out/panda_paper.csv`, `out/panda_self_motion.csv`, `out/panda_limits.csv` |
| MuJoCo library | `sim/mujoco_panda.hpp`, `sim/mujoco_panda.cpp`, built as `se3pf_mujoco` | `se3pf`, `mujoco::mujoco` | only with `-DSE3PF_WITH_MUJOCO=ON` | nothing by itself |
| MuJoCo apps | `apps/panda_mujoco.cpp`; `apps/mujoco_smoke.cpp` | `se3pf_mujoco`; the smoke test links `mujoco::mujoco` only | same option | `out/mujoco_{A,A2,B,C,C0,D,DG}.csv`, `out/mujoco_path.csv`, `out/panda_limits.csv`; the smoke test prints only |
| MuJoCo tests | `tests/mujoco/test_mujoco_panda.cpp`, built as `tests_mujoco` | `se3pf_mujoco`, Catch2 | same option | a temporary XML file, deleted again |
| Python tools | `tools/plot_rigid_body.py`, `tools/plot_panda.py`, `tools/plot_mujoco.py`, `tools/render_mujoco.py`, `tools/view_mujoco.py`, `tools/mujoco_model_check.py` | numpy, matplotlib; the `mujoco` Python package for the last three (the video also imageio, imageio-ffmpeg and Pillow) | by hand, from `.venv` | PNG and PDF figures, an MP4 video, a live viewer |
| Build and CI | `CMakeLists.txt`, `cmake/mujoco.cmake`, `tools/ci.sh`, `tools/fetch_mujoco.sh`, `.gitignore`, `tools/requirements-mujoco.txt` | | by hand | `build*/`, `build-ci-*.log`, `third_party/` (and, by hand, `.venv/`) |

One more program lives in `tools/`: `tools/oracle/panda_oracle.cpp`. It is not part of the CMake build. It recomputes the expected Panda numbers with the earlier reference library `pf`, which is why those numbers can be trusted as an independent target.

### Which way the dependencies point

The dependency arrows only point down, toward the library. Read them as "needs":

1. `se3pf` (`include/se3pf/`, `src/`) needs Eigen and nothing else. A search for "mujoco" in `include/` and `src/` finds three comment lines (`include/se3pf/panda.hpp:51-52`, `include/se3pf/controller.hpp:109`) and no include.
2. `se3pf_mujoco` needs `se3pf` and MuJoCo. Both are linked `PUBLIC` (`CMakeLists.txt:85`), so anything that links `se3pf_mujoco` gets both include paths and both libraries.
3. `panda_mujoco` and `tests_mujoco` need `se3pf_mujoco`.
4. `mujoco_smoke` needs MuJoCo alone, on purpose. If the smoke test passes and `tests_mujoco` fails, the fault is in our wrapper, not in the MuJoCo install.

The separation has three reasons:

- The library is what the future robot driver links. Its 1 kHz step must stay allocation-free and must not pull a physics engine into the real-time process.
- The default build and its 132 test cases need nothing downloaded except Catch2. Someone who only works on the math never needs MuJoCo.
- MuJoCo is a binary release of about 90 MB plus a 43 MB model checkout (`third_party/README.md`). It is fetched only by `tools/fetch_mujoco.sh` and never committed.

### What an app does

Every app follows the same five steps, so once you know one you know all of them:

1. Read an output directory from `argv[1]` (default `out/`), and for `panda_mujoco` a model directory from `argv[2]`.
2. Build the example object offline: the path, the tube and, for the Panda, the lift, kernel frame and start configurations (`RigidBodyExample` or `PandaExample`).
3. Call a simulate function: `simulate` (`src/rigid_body_example.cpp`, `src/panda_example.cpp`) or `simulateMujoco` (`sim/mujoco_panda.cpp`).
4. Print each summary number with its expected value in square brackets, taken from `docs/DESIGN.md` (Testing, Closed loops) or, in `panda_mujoco`, the bound the app checks.
5. Write one CSV file per logged run and return an exit code.

| App | Exit 0 | Exit 1 | Exit 2 |
| --- | --- | --- | --- |
| `rigid_body_sim` | both runs completed | an exception, or a log that cannot be written | a run failed (`ok == false`) |
| `panda_sim` | both runs completed inside the joint range | the same | a run failed or left the joint range |
| `panda_mujoco` | every summary check passed | an exception (bad option, model not loadable), or a log that cannot be written | a summary check failed |
| `mujoco_smoke` | the torque checks passed, or were skipped because the model is not a 7-dof Panda with torque-capable actuators | the model does not load, or a torque check failed | wrong number of arguments |

`tools/ci.sh` only looks at the exit code, so the exit code is the contract. The bracketed values are for your eyes. The tolerance checks of the same numbers live in the Catch2 tests, except in `panda_mujoco`, whose summary is itself a list of pass or fail checks.

### The CSV contract between C++ and Python

Every log has one header line and one row per control instant t_k = k Δt, taken before the plant moves on. The plot scripts read the logs' columns by their header names, never by position; only `render_mujoco.py` reads the path samples of `mujoco_path.csv` by position. In `plot_rigid_body.py` and `plot_panda.py` a missing column stops the script with a message such as "missing columns [...]; rerun panda_sim"; `plot_mujoco.py` would stop with a Python `KeyError`.

The joint limits travel the same way. `panda_sim` and `panda_mujoco` write `panda_limits.csv` from `PandaArm` (`apps/panda_limits.hpp`), so the plots never hold a second copy of the limits.

Only a few constants are copied into the plot and video scripts: the hardware bounds drawn as limit lines (`HardwareBounds`, `include/se3pf/panda.hpp:53-63`), k_t for one design curve, and the flange offset 0.107 m for the video. Each copy names its C++ source in a comment, and the `HardwareBounds` copies say "keep them in sync". `tools/mujoco_model_check.py` copies the DH table, the joint limits and 0.107 on purpose, as an independent oracle.

### Measured on this machine

| Command | Wall time | Result |
| --- | --- | --- |
| `./build-ci-release/tests` | 2.8 s | 132 test cases, 259 448 assertions, all pass |
| `./build-ci-release/rigid_body_sim <dir>` | 0.35 s | exit 0 |
| `./build-ci-release/panda_sim <dir>` | 0.70 s | exit 0 |
| `./build-ci-mujoco/tests_mujoco` | 2.0 to 2.1 s | 15 test cases, 4713 assertions, all pass |
| `./build-ci-mujoco/panda_mujoco <dir>` | 14.6 s | "ALL CHECKS PASSED", exit 0 |
| `./build-ci-mujoco/mujoco_smoke .../panda_nohand.xml` | 0.24 s | "torque checks (damping off): PASS", exit 0 |

These agree with `docs/MUJOCO.md`, which quotes about 15 s for `panda_mujoco` and about 2 s for `tests_mujoco`. Wall times depend on the machine and its load: an earlier measurement on a busy machine gave 21.6 s and 4.4 s. The numbers in the summaries do not change.
