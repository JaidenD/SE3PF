## The MuJoCo layer

The MuJoCo layer replaces the paper's double-integrator plant by the MuJoCo Menagerie Panda driven with joint torques, and checks every hardware margin before the robot moves. It is one class (`MujocoPanda`), one free function for the margins (`hardwareMargins`), one closed loop (`simulateMujoco`), one app that runs a kinematics check and twelve closed-loop runs (`panda_mujoco`), a smoke test without `se3pf` (`mujoco_smoke`) and one test program (`tests_mujoco`).

### Why a torque-level plant

In `panda_sim` the feedback eq:fb is assumed exact, so q̈ = q̈* and the plant is q ← q + Δt q̇ + ½Δt² q̈*. On the robot the torque goes into links with mass, rotor inertia (armature), joint friction and a payload, and libfranka adds its own G. MuJoCo adds these effects one at a time, so each one can be measured alone: first an exact model, then a held torque, then damping, then an unmodeled hand.

The plant equation, with MuJoCo's names under each term:

```latex
M(q)\,\ddot q + \underbrace{C(q,\dot q)\,\dot q + G(q)}_{\texttt{qfrc\_bias}} = \tau + \underbrace{(-D\,\dot q)}_{\texttt{qfrc\_passive}}, \qquad \tau = \texttt{ctrl}
```

M includes the joint armature (0.1 kg m² added on each diagonal entry). With the actuators turned into torque motors, `ctrl` is the joint torque τ itself.

### MujocoPanda: the class declaration

`MujocoPanda` owns one MuJoCo model and two MuJoCo data objects, and exposes only what the controller needs: state, MuJoCo's own kinematics, M, C q̇ + G, the passive force, and two ways to step.

```cpp
// sim/mujoco_panda.hpp:21-22, 46-60
typedef struct mjModel_ mjModel;
typedef struct mjData_ mjData;
// ...
    class MujocoPanda {
        public:
            static constexpr int kArm = 7;  // arm joints; panda.xml adds two finger joints after them

            enum class Integrator {
                Euler,  // MuJoCo's semi-implicit Euler: qdot += h qdd, then q += h qdot (with the new qdot); the
                        // damping is explicit in qdd (mjDSBL_EULERDAMP)
                RK4     // classic Runge-Kutta, with ctrl held over the step
            };

            struct Options {
                double timestep = 1e-3;                  // h, s (the Menagerie default is 2 ms)
                Integrator integrator = Integrator::Euler;
                bool damping = false;                    // joint damping 1 N m s/rad on or off (mjDSBL_DAMPER)
            };
```

- `typedef struct mjModel_ mjModel;` is a forward declaration. It tells the compiler that `mjModel` is a struct defined elsewhere, which is enough for pointers to it. The header can then declare `const mjModel* model()` without including `mujoco.h`, and MuJoCo's macros and thousands of declarations stay out of every file that includes `mujoco_panda.hpp`. It must spell the type exactly as `mujoco.h` does; repeating an identical `typedef` is legal C++.
- `static constexpr int kArm = 7;` is a compile-time constant that belongs to the class, not to an object. `constexpr` means the value is known while compiling, so it can size arrays and appear in `static_assert`.
- `enum class Integrator { Euler, RK4 }` is the choice of MuJoCo integrator for the plant (the file's `implicitfast` is never used).
- `struct Options` has default member initializers (`double timestep = 1e-3;`), so `MujocoPanda::Options o;` already holds the defaults. The test writes `MujocoPanda::Options{0.0, MujocoPanda::Integrator::Euler, false}`: aggregate initialization fills the members in declaration order (allowed for structs with default member initializers since C++14).

```cpp
// sim/mujoco_panda.hpp:65-73
            MujocoPanda(const std::string& xmlPath, const Options& options);
            // The default options. (Not a default argument "= Options()": a nested struct with default member
            // initializers cannot be used in its enclosing class before the class is complete; GCC says "default
            // member initializer required before the end of its enclosing class".)
            explicit MujocoPanda(const std::string& xmlPath) : MujocoPanda(xmlPath, Options()) {}
            // Owns its mjModel and mjData: a copy would free them twice. (The unique_ptr members also delete the
            // copy; saying so here is for the reader.)
            MujocoPanda(const MujocoPanda&) = delete;
            MujocoPanda& operator=(const MujocoPanda&) = delete;
```

- The second constructor delegates: `: MujocoPanda(xmlPath, Options())` runs the first constructor with default options. A default argument `const Options& options = Options()` would be shorter, but GCC rejects it. A default argument inside a class may not use the default member initializers of a nested struct before the enclosing class is complete; the comment quotes GCC's message.
- `explicit` forbids silent conversions. Without it, a function taking a `const MujocoPanda&` could be called with a `std::string`, and C++ would quietly load a temporary model from that path.
- `= delete` on the copy constructor and copy assignment forbids copying. A copy would hold the same raw MuJoCo pointers, and both copies would free them: a double free, which corrupts the heap. The `unique_ptr` members already make a copy impossible; the lines say it for the reader.
- A user-declared copy constructor, even a deleted one, also stops the compiler from generating a move constructor. So `MujocoPanda` can be neither copied nor moved; the first test case checks the copy part at compile time (`STATIC_REQUIRE_FALSE(std::is_copy_constructible_v<MujocoPanda>)` and the same for `is_copy_assignable_v`). Code that needs an optional instance holds it through `std::unique_ptr<MujocoPanda>`, as `simulateMujoco` does (`sim/mujoco_panda.cpp:344-347`).

```cpp
// sim/mujoco_panda.hpp:122-136
        private:
            // RAII: mj_deleteModel / mj_deleteData run when the object goes away, also if the constructor throws
            // half-way. The deleters are defined in the .cpp, where mujoco.h is included.
            struct ModelDeleter { void operator()(mjModel* m) const; };
            struct DataDeleter { void operator()(mjData* d) const; };

            Options options_;
            std::unique_ptr<mjModel, ModelDeleter> m_;
            std::unique_ptr<mjData, DataDeleter> d_;        // the plant
            std::unique_ptr<mjData, DataDeleter> scratch_;  // for gravity and flange: does not disturb the plant
            // Buffers of the model's size (nv = 7 or 9), allocated once in the constructor
            std::vector<double> fullM_;                     // nv x nv, for mj_fullM
            std::vector<double> jacp_, jacr_;               // 3 x nv, for mj_jac
            std::vector<double> vecIn_, vecOut_;            // nv, for mj_mulM
            int link7_ = -1;                                // body id of link7
```

This is RAII (resource acquisition is initialization): an object that acquires a resource releases it in its destructor. `std::unique_ptr<mjModel, ModelDeleter>` owns one pointer and calls `ModelDeleter{}(ptr)` when it is destroyed or reset. The plain `std::unique_ptr<mjModel>` would call `delete`, which is wrong for memory that `mj_loadXML` allocated; only `mj_deleteModel` may free it.

- The deleters are empty structs with an `operator()`, so the `unique_ptr` stays the size of one pointer. Their bodies live in the `.cpp` (`sim/mujoco_panda.cpp:83-84`), the only file that includes `mujoco.h`.
- What goes wrong without RAII: the constructor throws at `sim/mujoco_panda.cpp:98` if the file is not a Panda. By then the model is loaded. With a raw pointer it would leak. With `unique_ptr` members, C++ destroys every member already constructed when a constructor throws, so `mj_deleteModel` runs.
- Members are destroyed in reverse declaration order: `scratch_`, then `d_`, then `m_`. Both data objects go before the model they were made from.
- `fullM_`, `jacp_`, `jacr_`, `vecIn_`, `vecOut_` are `std::vector<double>` because their size depends on the model file (nv = 7 or 9). They are allocated once in the constructor, so no later call allocates.

### The constructor, step by step

```cpp
// sim/mujoco_panda.cpp:86-110
    MujocoPanda::MujocoPanda(const std::string& xmlPath, const Options& options) : options_(options)
    {
        if (!(options.timestep > 0.0))
            throw std::invalid_argument("MujocoPanda: the timestep must be positive");

        char error[1000] = "";
        m_.reset(mj_loadXML(xmlPath.c_str(), nullptr, error, sizeof(error)));
        if (!m_)
            throw std::runtime_error("MujocoPanda: cannot load " + xmlPath + ": " + error);
        mjModel* m = m_.get();
        link7_ = mj_name2id(m, mjOBJ_BODY, "link7");
        if (link7_ < 0 || !useTorqueMotors(m))
            throw std::runtime_error("MujocoPanda: " + xmlPath + " is not a Menagerie Panda (body link7, actuator i "
                                     "on joint i with unit gear)");

        m->opt.timestep = options.timestep;
        m->opt.integrator = options.integrator == Integrator::RK4 ? mjINT_RK4 : mjINT_EULER;
        if (!options.damping)
            m->opt.disableflags |= mjDSBL_DAMPER;
        // MuJoCo's Euler integrates joint damping implicitly by default: it integrates the acceleration
        // (M + h D)^-1 (tau - bias + passive), not the qacc = M^-1 (tau - bias + passive) it reports, an O(h)
        // difference (0.035 rad/s^2 at |qdot| ~ 0.3 rad/s). Explicit damping makes the reported qacc the integrated
        // one, so the exact step stays exact with the damping on. (RK4 is always explicit.)
        m->opt.disableflags |= mjDSBL_EULERDAMP;
        m->opt.disableflags |= mjDSBL_AUTORESET;  // a bad state stays visible (warning, NaN) instead of a reset
```

1. `if (!(options.timestep > 0.0))` rejects zero, negative values and NaN. Every comparison with NaN is false, so `!(x > 0)` is true for NaN, while `x <= 0` would let NaN through. The same idiom appears throughout the project.
2. `char error[1000] = "";` is a zero-filled buffer. `mj_loadXML(path, nullptr, error, sizeof(error))` returns a null pointer on failure and writes the reason into `error` (the `nullptr` means "read from disk, no virtual file system"). `m_.reset(...)` hands the pointer to the `unique_ptr`; `if (!m_)` tests for null.
3. `mj_name2id(m, mjOBJ_BODY, "link7")` returns the body's index, or −1 if there is none.
4. `useTorqueMotors(m)` checks and rewrites the actuators (next subsection). The constructor changes the loaded model in place before any `mjData` is made from it.
5. `m->opt.timestep` and `m->opt.integrator` replace the model's 2 ms (MuJoCo's default) and `implicitfast`.
6. `disableflags |= bit` sets one bit and leaves the others alone. Three bits are set:

| Flag | Set when | Effect | Why |
| --- | --- | --- | --- |
| `mjDSBL_DAMPER` | `Options::damping` is false (the default) | `qfrc_passive` = 0: the model's 1 N m s/rad joint damping is off | runs A and B test the controller without friction; C, C0, D and D-G switch it on |
| `mjDSBL_EULERDAMP` | always | the Euler integrator treats damping explicitly | so that the acceleration MuJoCo reports is the one it integrates (below) |
| `mjDSBL_AUTORESET` | always | no automatic reset of the state when MuJoCo detects a bad value | a blow-up stays visible as a warning and NaN, instead of a silent restart |

```cpp
// sim/mujoco_panda.cpp:112-126
        d_.reset(mj_makeData(m));
        scratch_.reset(mj_makeData(m));
        if (!d_ || !scratch_)
            throw std::runtime_error("MujocoPanda: cannot allocate mjData");
        resetHome(m, d_.get());
        resetHome(m, scratch_.get());

        const std::size_t nv = static_cast<std::size_t>(m->nv);
        fullM_.assign(nv * nv, 0.0);
        jacp_.assign(3 * nv, 0.0);
        jacr_.assign(3 * nv, 0.0);
        vecIn_.assign(nv, 0.0);
        vecOut_.assign(nv, 0.0);
        mj_forward(m, d_.get());
    }
```

7. Two `mjData`: `d_` is the plant; `scratch_` is a second state used by `gravity` and `flange`, so that those queries never disturb the plant.
8. `resetHome` puts both at the keyframe "home".
9. `assign(n, 0.0)` sizes each buffer from the model's nv.
10. `mj_forward` evaluates the model at the initial state, so every query is valid right after construction.

What the constructor throws: `std::invalid_argument` for a timestep that is not positive; `std::runtime_error` if the file cannot be loaded, has no body `link7`, fails the actuator checks, or `mj_makeData` returns null.

### useTorqueMotors: from position servos to torque motors

```cpp
// sim/mujoco_panda.cpp:25-48
        bool useTorqueMotors(mjModel* m)
        {
            if (m->nactuator < kArm || m->njnt < kArm || m->nv < kArm || m->nu < kArm)
                return false;
            for (int i = 0; i < kArm; ++i) {
                const int c = m->actuator_ctrladr[i];
                if (m->jnt_type[i] != mjJNT_HINGE || m->jnt_qposadr[i] != i || m->jnt_dofadr[i] != i
                    || m->actuator_trntype[i] != mjTRN_JOINT || m->actuator_trnid[2 * i] != i || c != i
                    || m->actuator_ctrlnum[i] != 1 || m->actuator_outadr[i] != i || m->actuator_gear[6 * i] != 1.0
                    || m->actuator_dyntype[i] != mjDYN_NONE || m->actuator_damping[i] != 0.0
                    || m->actuator_armature[i] != 0.0 || m->actuator_delay[i] != 0.0
                    || !m->actuator_forcelimited[i])
                    return false;
                m->actuator_gaintype[i] = mjGAIN_FIXED;
                m->actuator_biastype[i] = mjBIAS_NONE;
                std::fill(m->actuator_gainprm + i * mjNGAIN, m->actuator_gainprm + (i + 1) * mjNGAIN, 0.0);
                std::fill(m->actuator_biasprm + i * mjNBIAS, m->actuator_biasprm + (i + 1) * mjNBIAS, 0.0);
                m->actuator_gainprm[i * mjNGAIN] = 1.0;
                m->actuator_ctrllimited[c] = 1;
                m->actuator_ctrlrange[2 * c] = m->actuator_forcerange[2 * i];
                m->actuator_ctrlrange[2 * c + 1] = m->actuator_forcerange[2 * i + 1];
            }
            return true;
        }
```

The checks make sure that `ctrl[i]` becomes exactly τ_i on joint i, and that the index arithmetic of the wrapper is valid:

| Check | Meaning | What would break without it |
| --- | --- | --- |
| `nactuator`, `njnt`, `nv`, `nu` at least 7 | the model has seven of each | indexing 0..6 would read past the arrays |
| `jnt_type[i] == mjJNT_HINGE` | joint i is revolute | a slide or ball joint has other units or more coordinates |
| `jnt_qposadr[i] == i`, `jnt_dofadr[i] == i` | joint i is `qpos[i]` and `qvel[i]` | `setArm` and `armVector` copy indices 0..6 directly |
| `actuator_trntype[i] == mjTRN_JOINT`, `actuator_trnid[2 * i] == i` | actuator i acts on joint i | the torque would land on another joint |
| `c == i`, `actuator_ctrlnum[i] == 1`, `actuator_outadr[i] == i` | actuator i reads `ctrl[i]` only and writes output i | `holdStep` writes `ctrl[0..6]` |
| `actuator_gear[6 * i] == 1.0` | unit transmission | the joint torque would be gear × ctrl |
| `actuator_dyntype[i] == mjDYN_NONE`, `actuator_damping`, `actuator_armature`, `actuator_delay` all 0 | no actuator state, no extra damping, inertia or delay | the torque would act late or be filtered |
| `actuator_forcelimited[i]` | a force range exists | there would be no torque limit to clamp to |

Then the rewrite: gain type fixed with gain 1 and all other gain parameters 0, bias type none with all bias parameters 0. So MuJoCo's actuator force is 1 · ctrl instead of kp (ctrl − q) − kd q̇.

Finally `ctrlrange` (which held the joint range for the servo targets) is set to `forcerange` with `ctrllimited = 1`: MuJoCo clamps every control to ±87 or ±12 N m, the Franka limits. `withinTorqueLimits` later counts the periods in which that clamping would act.

`mjNGAIN` and `mjNBIAS` are the number of parameters per actuator; `actuator_gainprm + i * mjNGAIN` points at actuator i's block. `std::fill(first, last, 0.0)` zeroes a range given by two pointers.

`apps/mujoco_smoke.cpp:94-117` has an identical copy, because the smoke test avoids `se3pf` on purpose. Both comments say to keep the two in sync.

### resetHome and the small helpers

```cpp
// sim/mujoco_panda.cpp:52-61
        void resetHome(const mjModel* m, mjData* d)
        {
            const int key = mj_name2id(m, mjOBJ_KEY, "home");
            if (key >= 0)
                mj_resetDataKeyframe(m, d, key);
            else
                mj_resetData(m, d);
            for (int i = 0; i < kArm; ++i)
                d->ctrl[i] = 0.0;
        }
```

The keyframe's arm controls are servo targets in radians (−1.57079 for joint 4). As torques they would push joint 4 with −1.57 N m from the first step, so they are zeroed.

The finger control 255 stays: the finger actuator is still a position servo, and 255 opens the hand to 0.04 m. The first test case checks `qpos[7] == qpos[8] == 0.04` and `ctrl[7] == 255` for `panda.xml`.

The anonymous namespace (`namespace { ... }`, `sim/mujoco_panda.cpp:16-78`) gives these helpers internal linkage: no other file can see or collide with them. `armVector(const mjtNum* v)` copies the first seven entries of a MuJoCo array into a `Vec7`, and `setArm` copies back; `mjtNum` is MuJoCo's floating type, `double` in this build. `maxAbs(v)` is `v.cwiseAbs().maxCoeff()`, the infinity norm.

`setState(q, qd)` (`sim/mujoco_panda.cpp:138-143`) writes the arm's `qpos` and `qvel`, leaves the fingers as they are, and calls `mj_forward`. After it, every derived quantity (frames, M, `qfrc_bias`, `ncon`, `nefc`) belongs to the new state. `q()`, `qd()`, `qacc()` and `time()` read the plant (`sim/mujoco_panda.cpp:145-148`); `qacc()` is the acceleration of the last evaluation or step.

### flange: MuJoCo's kinematics, for a cross-check

`flange(q, &Jb)` computes the flange pose and the body Jacobian from MuJoCo's own model, to compare with `PandaArm::output`.

```cpp
// sim/mujoco_panda.cpp:173-190
    Pose MujocoPanda::flange(const Vec7& q, Mat67* Jb)
    {
        mjData* s = scratch_.get();
        setArm(s->qpos, q);
        mj_kinematics(m_.get(), s);
        mj_comPos(m_.get(), s);  // mj_jac needs the frames of mj_comPos

        // xmat is row-major: R(r, c) = xmat[3 r + c]; the flange is 0.107 m along link7's z-axis (column 2).
        const mjtNum* xm = s->xmat + 9 * link7_;
        Matrix3d R;
        R << xm[0], xm[1], xm[2],
             xm[3], xm[4], xm[5],
             xm[6], xm[7], xm[8];
        const Vector3d p = Vector3d(s->xpos[3 * link7_], s->xpos[3 * link7_ + 1], s->xpos[3 * link7_ + 2])
                           + PandaArm::kFlangeOffset * R.col(2);
        Pose g = Pose::Identity();
        g.block<3,3>(0,0) = R;
        g.block<3,1>(0,3) = p;
```

- `mj_kinematics` computes every body's position `xpos` and orientation `xmat`. `mj_comPos` computes the center-of-mass quantities (`subtree_com`, `cdof`) that `mj_jac` reads.
- `xmat` stores each 3 × 3 rotation row by row, nine numbers per body, so `R(r, c) = xm[3 r + c]`. Eigen's comma initializer `R << a, b, c, ...` also fills row by row.
- The flange (Franka frame F) is `link7` moved 0.107 m along its own z-axis, `R.col(2)`, with `link7`'s attitude. `panda_nohand.xml` does have a body `attachment` with its `attachment_site` at that point (`third_party/mujoco_menagerie/franka_emika_panda/panda_nohand.xml:188-190`), but turned 135° about z (`tools/mujoco_model_check.py` measures 135.000002°), so its attitude is not F's. In `panda.xml` the hand body sits there turned −45°.
- `PandaArm::kFlangeOffset` is the library's 0.107, so both sides share one constant and this cross-check alone cannot catch a wrong offset. `tools/mujoco_model_check.py` types 0.107 again on purpose, as an independent oracle, and the design doc's anchor FK(0) = (0.088, 0, 0.926) pins it in the tests.

```cpp
// sim/mujoco_panda.cpp:192-208
        if (Jb) {
```

`mj_jac(m, s, jacp, jacr, point, body)` returns two 3 × nv matrices in the world frame for a point fixed to a body: ṗ = jacp q̇ is the point's velocity and ω_s = jacr q̇ the body's angular velocity. The body twist the library uses is ζ = (g⁻¹ġ)^∨ with ω first:

```latex
g^{-1}\dot g = \begin{pmatrix} R^\top \dot R & R^\top \dot p \\ 0 & 0 \end{pmatrix}
\quad\Longrightarrow\quad
\zeta = \begin{pmatrix} \omega_b \\ v_b \end{pmatrix}
= \begin{pmatrix} R^\top J_{\mathrm{rot}}(q) \\ R^\top J_{\mathrm{pos}}(q) \end{pmatrix} \dot q = J_b(q)\,\dot q
```

So `jacr` goes on top and `jacp` below, both rotated by Rᵀ. Putting `jacp` first would give the (v, ω) order of Murray–Li–Sastry and of libfranka's `bodyJacobian`, and fail the cross-check by order one. `topRows<3>()` and `bottomRows<3>()` are fixed-size Eigen blocks: the 3 is a template argument, so the compiler knows the size and no memory is allocated.

`Mat67* Jb = nullptr` is the project's optional-output idiom, as in `PandaArm::output`: pass `&J` to receive the Jacobian, or nothing to skip the work. Everything happens in `scratch_`; the test checks that `arm.q()` is unchanged after a call.

Agreement measured: 2.0e-15 for the pose and 5.2e-15 for J_b at 1000 random q (`panda_mujoco` run (0)), and 6.4e-15 along the 20001 configurations of run A. The tests require below 1e-12 at 200 random q, also with `panda.xml`, whose link frames are the same.

### dynamics and gravity: M, C q̇ + G and the passive force

```cpp
// sim/mujoco_panda.cpp:150-171
    void MujocoPanda::dynamics(Mat<7, 7>& M, Vec7& bias, Vec7& passive)
    {
        mj_forward(m_.get(), d_.get());
        // MuJoCo keeps M sparse (there is no d->qM since 3.15); mj_fullM writes the dense nv x nv matrix, row-major.
        mj_fullM(m_.get(), d_.get(), fullM_.data());
        const int nv = m_->nv;
        for (int r = 0; r < kArm; ++r)
            for (int c = 0; c < kArm; ++c)
                M(r, c) = fullM_[static_cast<std::size_t>(r * nv + c)];
        bias = armVector(d_->qfrc_bias);       // C(q, qdot) qdot + G(q), by recursive Newton-Euler
        passive = armVector(d_->qfrc_passive); // -D qdot (zero with the damper switched off)
    }

    Vec7 MujocoPanda::gravity(const Vec7& q)
    {
        mjData* s = scratch_.get();
        setArm(s->qpos, q);
        for (int i = 0; i < m_->nv; ++i)
            s->qvel[i] = 0.0;
        mj_forward(m_.get(), s);
        return armVector(s->qfrc_bias);  // C qdot = 0 at rest, so the bias is G
    }
```

- `mj_forward` runs MuJoCo's whole forward pipeline at the current state without integrating.
- MuJoCo stores M in a sparse format; `mj_fullM` writes the dense nv × nv matrix row by row into `fullM_`, and the loop copies its 7 × 7 arm block into the fixed-size `Mat<7, 7>`. `static_cast<std::size_t>(r * nv + c)` converts the `int` index to the vector's index type.
- M includes the armature: `tools/mujoco_model_check.py` finds diag(`mj_fullM` − the RNE mass matrix) = 0.1 on every joint, and the test checks min diag M > 0.1.
- `qfrc_bias` is C(q, q̇)q̇ + G(q), computed by recursive Newton–Euler; `qfrc_passive` is −D q̇.
- With `panda.xml`, the 7 × 7 block includes the hand's inertia and `bias` its weight, but the coupling to the two finger joints is dropped.
- `gravity(q)` sets the scratch state to (q, 0) for all nv velocities, fingers included, and reads `qfrc_bias`: with q̇ = 0, C q̇ vanishes and only G is left. It costs one full `mj_forward`.

The outputs are reference parameters (`Mat<7, 7>& M`), not return values: the caller owns fixed-size storage, and the function fills it without allocating.

### Two ways to step: exactStep and holdStep

| | `exactStep(qdd)` | `holdStep(tau, substeps)` |
| --- | --- | --- |
| Runs | A, A2 | B, C, C0, D, D-G |
| Torque computed | at every MuJoCo step, from the plant's current state | once per control period, from the state at its start |
| Torque | τ = M q̈* + C q̇ + G − f_passive | τ = M q̈* + C q̇ + G; the passive force is not compensated |
| Integrator | semi-implicit Euler, through `mj_step1` / `mj_step2` | RK4 (or Euler) through `mj_step`, ctrl constant over the step |
| Result | `qacc` = q̈* to 4.3e-15 | q̈ = q̈* only at the start of the period |
| Models | `panda_nohand.xml` only | any; the torque may come from another model file |
| Shows | the dynamics are cancelled exactly; only integrator error is left | what the robot does: a zero-order hold at 1 kHz |

```cpp
// sim/mujoco_panda.cpp:211-229
    Vec7 MujocoPanda::exactStep(const Vec7& qdd)
    {
        mjModel* m = m_.get();
        mjData* d = d_.get();
        mj_step1(m, d);  // positions and velocities: M, qfrc_bias = C qdot + G, qfrc_passive

        // tau = M qdd + C qdot + G - passive (eq:fb, with MuJoCo's own model). The finger dofs of panda.xml (if
        // any) get zero acceleration in the product; the exact step is meant for panda_nohand.xml.
        std::fill(vecIn_.begin(), vecIn_.end(), 0.0);
        setArm(vecIn_.data(), qdd);
        mj_mulM(m, d, vecOut_.data(), vecIn_.data());
        Vec7 tau = Vec7::Zero();
        for (int i = 0; i < kArm; ++i) {
            tau[i] = vecOut_[static_cast<std::size_t>(i)] + d->qfrc_bias[i] - d->qfrc_passive[i];
            d->ctrl[i] = tau[i];
        }
        mj_step2(m, d);  // actuation, qacc, and one Euler step (mj_step1 / mj_step2 always integrate with Euler)
        return tau;
    }
```

`mj_step` is split in two so that user code can act between the halves. `mj_step1` evaluates everything that depends on positions and velocities: kinematics, M, collisions, `qfrc_bias`, `qfrc_passive`.

Then the code computes τ and writes `ctrl`. `mj_step2` evaluates the actuators, the acceleration and the constraints, and integrates one step.

- `mj_mulM(m, d, out, in)` multiplies by MuJoCo's own sparse M, the same matrix MuJoCo inverts a moment later, so the product is consistent to round-off. `vecIn_` is zeroed first, so the finger entries (if any) are 0.
- With this torque the plant's acceleration is q̈* exactly:

```latex
\ddot q = M^{-1}\left(\tau - C\dot q - G - D\dot q\right) = \ddot q^{*}
\quad\text{for}\quad
\tau = M\ddot q^{*} + C\dot q + G + D\dot q
```

- `mj_step2` never runs RK4: with the integrator set to RK4 it falls back to Euler. A scratch run here set the integrator to RK4 and to Euler and took 100 exact steps with each: the two states agree to 0. That is why `simulateMujoco` configures the plant with Euler for exact runs, so the configuration says what actually happens.
- Why `panda_nohand.xml` only: in `panda.xml` the finger dofs couple to the arm through the off-diagonal blocks of M. Setting their entries of `vecIn_` to 0 asks for zero finger acceleration, which the finger servo and equality constraint do not deliver, so `qacc` would not equal q̈*. `simulateMujoco` refuses that combination.

Semi-implicit Euler updates the velocity first and then the position with the new velocity:

```latex
\begin{aligned}
\text{MuJoCo:}\quad & \dot q_{k+1} = \dot q_k + h\,\ddot q^{*}, \qquad q_{k+1} = q_k + h\,\dot q_{k+1} = q_k + h\,\dot q_k + h^2\,\ddot q^{*} \\
\text{exact for a held } \ddot q^{*}:\quad & q_{k+1} = q_k + h\,\dot q_k + \tfrac12 h^2\,\ddot q^{*}
\end{aligned}
```

The extra ½h² q̈* per step adds up to ½ h t q̈* after time t: an O(h) position error, not a model error. `mujoco_smoke` shows it exactly: after 1 s at h = 1 ms with max |q̈*| = 1.2, the position error is 6.000e-4, equal to ½ · 1e-3 · 1 · 1.2. (The smoke test steps with the file's `implicitfast`, which with the damping off moves q exactly as semi-implicit Euler does.)

Why `mjDSBL_EULERDAMP` matters for the exact step. By default MuJoCo's Euler integrates joint damping implicitly:

```latex
\dot q_{k+1} = \dot q_k + h\,(M + hD)^{-1}\bigl(\tau - C\dot q - G - D\dot q\bigr)
\quad\text{instead of}\quad
\dot q_k + h\,M^{-1}\bigl(\tau - C\dot q - G - D\dot q\bigr)
```

The reported `qacc` is still the second, explicit value, so a check of `qacc` alone passes. A scratch run here cleared the flag and took 200 exact steps with the damping on, from |q̇| ≈ 0.3 rad/s. Then max |`qacc` − q̈*| = 5.8e-15, but the velocity misses q̇ + h q̈* by 2.8e-5 rad/s, that is h × 0.028 rad/s².

With the flag the miss is 6e-17. The constructor's comment quotes 0.035 rad/s² and `docs/MUJOCO.md` 0.030: the size depends on the random state, its O(h) nature does not. The test at `tests/mujoco/test_mujoco_panda.cpp:214-242` checks the velocity update for this reason.

```cpp
// sim/mujoco_panda.cpp:231-236
    void MujocoPanda::holdStep(const Vec7& tau, int substeps)
    {
        setArm(d_->ctrl, tau);
        for (int i = 0; i < substeps; ++i)
            mj_step(m_.get(), d_.get());
    }
```

`holdStep` writes τ into `ctrl` and calls `mj_step` `substeps` times. RK4 evaluates the dynamics four times per step with the same `ctrl`, so the torque is held constant over the whole period: a zero-order hold, as libfranka applies a 1 kHz torque command.

### hardwareMargins: the hardware section's margins at one instant

```cpp
// sim/mujoco_panda.cpp:264-281
    HardwareMargins hardwareMargins(const Vec7& q, const Vec7& qd, const Vec7& qdd, const Vec7& tau, const Vec7& G,
                                    const Vec7& tauPrev, const Vec7& GPrev, double dt)
    {
        HardwareMargins h;
        h.jointMargin = PandaArm::jointMargin(q, &h.marginJoint);
        // Each joint against its own limit (cwiseQuotient), never against one limit for all
        h.dqFrac = qd.cwiseAbs().cwiseQuotient(PandaArm::dqMax());
        h.ddqFrac = qdd.cwiseAbs().cwiseQuotient(PandaArm::ddqMax());
        h.tauFrac = tau.cwiseAbs().cwiseQuotient(PandaArm::tauMax());
        // libfranka is sent tau - G (it adds G itself), so the rate margin applies to that difference
        h.tauRateCmd = maxAbs((tau - G) - (tauPrev - GPrev)) / dt;
        h.tauRate = maxAbs(tau - tauPrev) / dt;
        Mat67 Jb = Mat67::Zero();
        PandaArm::output(q, &Jb);
        const Vec6 zeta = Jb * qd;  // body twist (omega, v) of the flange
        h.flangeSpeed = zeta.tail<3>().norm();
        return h;
    }
```

| Field | Formula | Bound (`HardwareBounds`) |
| --- | --- | --- |
| `jointMargin`, `marginJoint` | minᵢ distance of qᵢ to its limits, and which joint | ≥ 0.10 rad |
| `dqFrac` | \|q̇ᵢ\| / q̇_max,i, per joint | ≤ 50 % |
| `ddqFrac` | \|q̈*ᵢ\| / q̈_max,i, commanded, per joint | ≤ 30 % |
| `tauFrac` | \|τᵢ\| / τ_max,i, delivered, G included, per joint | ≤ 60 % |
| `tauRateCmd` | maxᵢ \|Δ(τᵢ − Gᵢ)\| / Δt | ≤ 0.6 × 1000 = 600 N m/s |
| `tauRate` | maxᵢ \|Δτᵢ\| / Δt | none: printed for comparison |
| `flangeSpeed` | \|v_b\|, the translational part of J_b q̇ | ≤ 0.5 m/s |

`HardwareBounds` (`include/se3pf/panda.hpp:53-63`) has three more bounds that `hardwareMargins` does not compute: |ξ| ≤ 0.04, |β| ≤ 0.05 rad and σ_min(A) ≥ 1e-3. The app and the tests check them on the run's peaks.

- `cwiseQuotient` divides entry by entry ("cwise" means coefficient-wise). Each joint is measured against its own limit, never one limit for all: the wrist joints have 12 N m against 87 N m, and their own velocity and acceleration limits.
- The rate margin applies to τ − G because libfranka is sent τ − G and adds G itself. The robot's 1000 N m/s limit is on that command. Including G would mix in the slow change of gravity as the arm moves.
- |v_b| = |Rᵀṗ| = |ṗ|, because a rotation keeps lengths. The body-frame speed is the flange's speed in the world.
- The previous values are backward differences over one period. Before t = 0 the arm rests under gravity compensation: the caller passes τ_prev = G_prev = G(q₀), so the first commanded rate is maxᵢ |τᵢ(0) − Gᵢ(0)| / Δt.

- `tau = M * qdd + bias` is eq:fb from the state at the start of the period. The passive force is not compensated: in runs C and D the damping plays the robot's unmodeled friction.

### What the runs mean for the hardware

Every uncompensated force acts on the outputs as a disturbance on μ. If the plant accelerates by q̈ = q̈* + δ, then the outputs obey ȳ̈ = A q̈ + Ȧq̇ = μ + Aδ. The tests' helper `dampingFelt` confirms δ = M⁻¹(−D q̇) in a 2 s version of run C with a least-squares factor of 0.9995. A PD law turns a slowly varying disturbance d = Aδ into a steady offset:

```latex
\ddot\xi = -K_p\,\xi - K_d\,\dot\xi + d_\xi \;\Rightarrow\; \xi_{ss} = \frac{d_\xi}{K_p} = \frac{d_\xi}{16},
\qquad
\ddot\eta = -k_t(\dot\eta - \nu_d) + d_\eta \;\Rightarrow\; \dot\eta_{ss} - \nu_d = \frac{d_\eta}{k_t} = \frac{d_\eta}{5}
```

and β_ss = d_β / K_p,β = d_β / 16 in the same way.

- **Friction leaves a steady error.** In run C, η̇ ends at 0.0643, so d_η ≈ 5 × (0.0643 − 0.08) = −0.079 there. Over the last 5 s η̇ wanders between 0.047 and 0.064, because the drag along the path changes with the configuration. |ξ| and |β| stay near 1e-2. Real joint friction will act the same way; integral action or friction compensation is ticket CTRL-1 in `TICKETS.md`.
- **An unmodeled payload makes the arm sag and stall.** At t = 0 the ramp makes μ = 0, so τ = G_arm and nothing holds the hand's 7.46 N. The arm falls: |ξ| reaches 0.215 at t = 0.706 s, and η̇ spikes to 0.43 at t = 0.697 s as the closest point γ(η) races along the path under the falling flange. Then η̇ decays to zero over the next few seconds and the arm stalls near η = 0.468: at η̇ = 0 the tangential law asks for at most k_t ν_d = 0.4, less than the hand's weight pulls back on that part of the path.
- **G with the payload fixes it.** Run D-G adds only the hand's weight to G, as libfranka does when the end effector is configured in Desk. Its last 5 s differ from run C's by under 5 %, and its torque peak is 29.5 % instead of 25.1 %. Before the first motion, configure the hand (or any tool) in Desk.
- **The ramp is necessary.** Without it the first command needs 49.4 % of joint 5's acceleration limit and a torque jump of 1164 N m/s.
- **The rate margin belongs on τ − G.** That is what libfranka receives; in run C it peaks at 1.3 N m/s, while the full torque, with G, changes at 5.9 N m/s.

What MuJoCo still cannot show (`docs/MUJOCO.md:221-246`):

- libfranka's own `franka::Model` instead of the Menagerie inertias;
- Coulomb friction and joint elasticity;
- filtered encoder velocities and torque-sensor noise, which the derivative terms K_d ξ̇ and the central difference for Ȧq̇ will see;
- late packets and jitter in the 1 kHz callback, and libfranka's optional rate limiting and low-pass filter;
- the robot's own reflexes, which stop it at its collision and limit thresholds.

Speed is not the issue. Measured here without the baseline and the log, a held-torque period (controller step, plant dynamics, G, four RK4 stages) took 40 µs and an exact period 22 µs, against a budget of 1000 µs. With the baseline's second controller step, run B took 54 µs per period and run A 38 µs.

### mujoco_smoke: the raw C API, without se3pf

`apps/mujoco_smoke.cpp` checks the facts the wrapper relies on with nothing but `mujoco.h`. Run it with the path of `panda_nohand.xml`:

1. `printModel` prints the model: version 3.15.0, nq = nv = nu = 7, timestep 0.002 s, `implicitfast`, each joint's range, armature 0.1, damping 1, friction loss 0, and each actuator's gain, bias, ctrl range and force range.
2. `printFlange` prints the flange at q = 0, (0.088, 0, 0.926) with R = diag(1, −1, −1), and at q_r, (0.306891, 0, 0.590282): the design doc's anchors.
3. It steps 1000 times with ctrl = 0 at the file's 2 ms, so 2 s. The servos then pull toward q = 0, clamped to each ctrl range: joint 4's target is its upper limit −0.0698, and it ends at −0.0696, 0.2 mrad past the soft limit.
4. In torque mode (`useTorqueMotors`, timestep set to 1 ms, the file's `implicitfast` kept) it runs two passes of `holdRest` and `constantAcceleration`. With the damping on and compensated through `qfrc_passive`, `qacc` matches q̈* (7.7e-15), but q̇ misses v₀ + t q̈* by 1.1e-2 rad/s after 1 s. `implicitfast` treats the damping implicitly, like MuJoCo's default Euler; the wrapper avoids both by running Euler or RK4 with `mjDSBL_EULERDAMP` set.

Exit code: 2 for a wrong number of arguments, 1 if the model does not load or a torque check fails (drift ≥ 1e-10, fall ≤ 1e-3, or `qacc` error ≥ 1e-10), 0 otherwise. With `panda.xml` (nv = 9) the torque checks are skipped and it exits 0, so `tools/ci.sh` passes `panda_nohand.xml`.

Three helpers recompute what the loop reports, from the log alone:

- `checkPeaks` (`tests/mujoco/test_mujoco_panda.cpp:503-551`) recomputes every margin peak from q, q̇, q̈*, τ and G, without calling `hardwareMargins`, and compares with the run's summary.
- `recomputeHoldTorque` (`tests/mujoco/test_mujoco_panda.cpp:556-573`) rebuilds τ = M q̈* + C q̇ + G with models of its own at each logged state, with the plant's G if `plantGravity`, and no passive term.
- `dampingFelt` measures how much of the damping reaches the arm:

```cpp
// tests/mujoco/test_mujoco_panda.cpp:581-603
    void dampingFelt(const MujocoRun& run, double& factor, double& residual, double& largest)
    {
        MujocoPanda::Options withDamping;
        withDamping.damping = true;
        MujocoPanda arm(run.options.plant, withDamping);
        Mat<7, 7> M = Mat<7, 7>::Zero();
        Vec7 bias = Vec7::Zero(), passive = Vec7::Zero();
        double num = 0.0, den = 0.0;
        residual = largest = 0.0;
        const double dt = run.options.dt;
        for (std::size_t k = 0; k + 1 < run.log.size(); ++k) {
            const MujocoLogRow& r = run.log[k];
            arm.setState(r.q, r.qd);
            arm.dynamics(M, bias, passive);  // passive = -D qdot
            const Vec7 damping = M.ldlt().solve(passive);
            const Vec7 excess = (run.log[k + 1].qd - r.qd) / dt - r.qdd;
            num += excess.dot(damping);
            den += damping.dot(damping);
            residual = std::max(residual, maxDiff(excess, damping));
            largest = std::max(largest, damping.cwiseAbs().maxCoeff());
        }
        factor = den > 0.0 ? num / den : 0.0;
    }
```

Over each period the plant's mean acceleration exceeds q̈* by the damping's own acceleration. The helper fits one factor c by least squares:

```latex
e_k = \frac{\dot q_{k+1} - \dot q_k}{\Delta t} - \ddot q^{*}_k, \qquad
a_k = M(q_k)^{-1}\bigl(-D\,\dot q_k\bigr), \qquad
c = \frac{\sum_k e_k^\top a_k}{\sum_k a_k^\top a_k}
```

c = 1 means the damping acts and is not compensated; c = 0 means it is absent or cancelled. A scratch run of the 2 s hardware-like loop here gives c = 0.9995 with the damping on (largest residual 3.07e-3 against 2.92 rad/s² of damping acceleration) and c = −0.0004 with it off. `M.ldlt().solve(passive)` solves M a = −D q̇ by an LDLᵀ factorization, the right choice for a symmetric positive definite M.

Two lessons sit in the tests' comments. At `tests/mujoco/test_mujoco_panda.cpp:155-157`, `flange` is called on its own line before its Jacobian is compared: the order in which function arguments are evaluated is unspecified, so in `std::max(maxDiff(flange(q, &J), g), maxDiff(J, Jb))` the compiler may read `J` before `flange` fills it. At `tests/mujoco/test_mujoco_panda.cpp:128-129`, the temporary MJCF file name contains the process id (`getpid()`), so two test programs run in parallel never share it.

`docs/MUJOCO.md` records why several checks are lower bounds. A review's mutation tests first found holes: the damping off in the plant or compensated, a torque rate against a stale previous torque, one torque limit for all joints, and runs D and D-G checked only by the app.

After those were closed, `docs/MUJOCO.md` reports that a second round of 24 mutants all fail `tests_mujoco`. Among them: half the damping compensated, the rate of τ for the rate of τ − G, the flange's angular speed for its linear speed, implicit Euler damping, and an exact run with the hand.

### Seeing the runs: render, view and the model check

`tools/render_mujoco.py` replays a run's q(t) in the Menagerie `scene.xml` (arm, hand, floor, lights) and writes an MP4:

- The path γ is a thin white polyline from `mujoco_path.csv` (every 4th sample, 500 segments). The target frame γ(η(t)) is a triad (x red, y green, z blue) at the nearest of the 2000 samples. The flange's trail over the last 2 s is drawn in the run's color. A text box shows the run's title and t, |ξ|, β and η̇.
- The hand is drawn translucent (alpha 0.3) in every run so the flange stays visible. Only runs D and D-G carry it in the plant.
- Frames: floor(T × fps) + 1, so 601 frames for a 20 s run at 30 fps. `--stills 0,5` also writes PNG frames at those times. `MUJOCO_GL=egl` renders without a window.

`tools/view_mujoco.py` plays the same overlays live in MuJoCo's viewer (`launch_passive`): space pauses, backspace restarts, `--speed` scales time and `--loop` repeats. `--dry-run` builds every frame's overlay without a window; for run C it reports 607 frames and 604 user geoms in the last one (500 path segments, 3 triad axes and a sphere, 100 trail segments).

`tools/mujoco_model_check.py` is an independent oracle written in numpy from the design doc's modified-DH table, with 0.107 typed again on purpose. At 200 random q it measures link frames to 6.7e-16 m and 8.1e-16 rad, the flange to 7.8e-16 m and the body Jacobian to 4.9e-15. It also finds the `attachment_site` turned 135.000002° about the flange z-axis.

At q_r with a random q̇ it prints the dynamics facts: diag(`mj_fullM` − RNE mass matrix) = 0.1, the armature, and `mj_inverse` equal to M q̈ + bias − passive − constraint to 8.9e-16. The script prints numbers for you to read; it has no pass or fail exit code.
