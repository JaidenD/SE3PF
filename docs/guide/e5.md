## Check yourself

These questions test whether you could have written the MuJoCo layer, the apps and the build yourself. Answer each in a few sentences before reading the answers below.

1. Run A's max ||ξ| − design| is 3.89e-5, while `panda_sim` gives 2.43e-5 for the same controller and start. Is MuJoCo's model of the arm wrong? Which number in the summary settles it, and why?
2. `MujocoPanda::flange` builds J_b as [Rᵀ·jacr; Rᵀ·jacp]. Why Rᵀ, why `jacr` on top, and why not use the `attachment_site` instead of `link7` plus 0.107 m?
3. The constructor sets `mjDSBL_EULERDAMP`. The test `exactStep gives qacc = qdd*` checks both `qacc` and the velocity update. Which of the two checks would fail without the flag, and by how much?
4. Why does `simulateMujoco` refuse an exact run with `panda.xml`, and why does it force the Euler integrator for every exact run?
5. `MujocoPanda` declares its copy constructor `= delete`. What would go wrong with a copy, can the class be moved, and how does `simulateMujoco` hold the optional second model?
6. The torque-rate margin is computed from τ − G, not from τ. Why, and what is the first sample of that rate compared with? What does run C0 show about it?
7. In run C, η̇ ends at 0.0643 instead of 0.08, and |ξ| and |β| settle near 1e-2. Explain this with the closed-loop output equations, and say what it predicts for the robot.
8. Run D violates three margins and stalls; run D-G keeps every margin. What is the only difference between the two, and what must you do on the robot because of it?
9. Why does `MujocoPanda` keep two `mjData` objects? Name the two functions that use the second one.
10. What does `SLOW_IN_DEBUG` expand to in Release and in Debug, and how do you run a hidden test? Why do the plain plot scripts never hold a copy of the joint limits?
11. Why are the warning flags carried by an `INTERFACE` target linked to each of our targets, instead of `add_compile_options`? Why does the CI also build with `-Werror` when it already greps the log?
12. You start `./build-rel/panda_mujoco` in a fresh shell with no `LD_LIBRARY_PATH`, and it finds `libmujoco.so.3.15.0`. Where does it find it, and when would that stop working?

### Answers

1. No. In run A the dynamics cancel to round-off: max |`qacc` − q̈*| is 4.3e-15. The difference is MuJoCo's semi-implicit Euler, which moves q by h² q̈* per step instead of the exact ½h² q̈*. The ratio check settles it: max |q_mj − q_kin| is 3.90e-4, 1.95e-4 and 9.74e-5 rad at h = 1, 0.5 and 0.25 ms (ratios 2.00), and the deviation falls to 3.08e-5 and 2.73e-5 on its way to the baseline's 2.43e-5. A model error would not halve with h.

2. `mj_jac` returns world-frame Jacobians: ṗ = jacp q̇ and ω_s = jacr q̇. The library's J_b gives the body twist (g⁻¹ġ)^∨ = (Rᵀω_s, Rᵀṗ), with ω first, so both blocks are rotated by Rᵀ and `jacr` goes on top. The `attachment_site` sits at the flange but is turned 135° about z, so its attitude is not Franka frame F. The flange is `link7` moved 0.107 m along its own z-axis with `link7`'s attitude, and MuJoCo then agrees with `PandaArm::output` to 6.4e-15 along run A.

3. The `qacc` check would still pass: MuJoCo reports the explicit acceleration M⁻¹(τ − bias + passive) = q̈*. The velocity check would fail. MuJoCo's default Euler integrates with (M + hD)⁻¹(...), so q̇ misses q̇ + h q̈* by h times a few hundredths of rad/s² (2.8e-5 rad/s per step in a scratch run here, h × 0.028 rad/s², against the 1e-12 bound). With the flag, the miss is about 6e-17.

4. In `panda.xml` the two finger dofs couple to the arm through the off-diagonal blocks of M. `exactStep` multiplies M by a vector whose finger entries are 0, which asks for zero finger acceleration; the finger servo and equality constraint do not deliver that, so `qacc` would not equal q̈*. The exact step is built on `mj_step1` / `mj_step2`, and `mj_step2` integrates with Euler even when the model says RK4 (a scratch run here gave identical states for both settings). Forcing Euler makes the configuration say what actually happens.

5. A copy would hold the same raw `mjModel*` and `mjData*`, and both destructors would free them: a double free. Because the copy constructor is user-declared, even as deleted, the compiler also generates no move constructor, so the class can be neither copied nor moved (the first test checks the copy part at compile time). `simulateMujoco` holds the optional model as `std::unique_ptr<MujocoPanda>`, built with `std::make_unique`, and binds `MujocoPanda& model` to it or to the plant.

6. libfranka is sent τ − G and adds its own G, and the robot's 1000 N m/s rate limit applies to that command. Before t = 0 the arm rests under gravity compensation, so the previous τ and G both start at G(q₀), and the first commanded rate is maxᵢ |τᵢ(0) − Gᵢ(0)| / Δt. Without the ramp (C0) that is |M q̈*(0)| / Δt = 1164 N m/s, above the 600 N m/s margin. With the quintic ramp the first command is exactly zero and the peak is 1.3 N m/s.

7. The damping is in the plant and not in the torque, so q̈ = q̈* + M⁻¹(−D q̇); the tests' helper `dampingFelt` measures the factor 0.9995. In output coordinates this adds d = A M⁻¹(−D q̇) to μ. A PD law leaves a steady offset: ξ_ss = d_ξ / 16, β_ss = d_β / 16, and η̇ − ν_d = d_η / k_t with k_t = 5. The controller has no integral action, so a constant drag gives a constant error. Real joint friction will do the same; ticket CTRL-1 covers integral action or friction compensation.

8. Both runs carry the 0.76 kg hand in the plant and compute M and C q̇ from the arm-only model. D-G alone replaces the arm's G by the plant's G, which includes the hand's 7.46 N. In D, nothing holds that weight while the ramp starts at μ = 0: |ξ| reaches 0.215, |q̈*| 110 % and |q̇| 60 % of their limits, and the arm stalls with η̇ → 0. On the robot, configure the end effector in Desk, so that libfranka's G includes it.

9. The plant `d_` must only move by stepping. Evaluating G at some other q, or MuJoCo's flange pose for a cross-check, would overwrite its positions and derived quantities. `gravity(q)` and `flange(q, Jb)` work in `scratch_` instead, and the test checks that `arm.q()` is unchanged after a `flange` call.

10. In Release (`NDEBUG` defined) it expands to `"[slow]"`, an ordinary tag, so those tests run by default. In Debug it expands to `"[.slow]"`: the leading dot hides them, and `./build-dbg/tests "[slow]"` runs them; `"[.timing]"` works the same way. The plot scripts read `panda_limits.csv`, which `panda_sim` and `panda_mujoco` write from `PandaArm` with 10 significant digits, and `plot_panda.py` even checks that the file reproduces the logged `joint_margin` column to 1e-8.

11. `add_compile_options` applies to every target in the directory tree, including Catch2, which `FetchContent` adds as a subproject. With `-Werror`, a warning in Catch2 would break our build. The `INTERFACE` target applies the flags only to targets that link it, and `PRIVATE` linking keeps them from spreading to consumers. A grep alone misses warnings in files that an incremental build did not recompile; `-Werror` fails the first build that sees the warning.

12. In the run path recorded in the executable. `cmake/mujoco.cmake` adds `-Wl,-rpath,<mujoco>/lib` to every executable that links `mujoco::mujoco`, and `readelf -d` shows `RUNPATH [.../third_party/mujoco-3.15.0/lib]`. The path is absolute, so it stops working if that MuJoCo directory is moved or deleted; rebuilding records the new location.
