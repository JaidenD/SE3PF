## Extension projects

Each project below extends the code the way a reviewer would accept it: a goal, the files it touches, a design that fits the existing layers, the tests that prove it, and acceptance criteria with numbers. Where the text quotes numbers, they come from prototypes and small programs run in scratch copies for this guide; the project itself was not changed.

### Project 1: integral action with clamped integrators (CTRL-1)

Goal: remove the steady errors that unmodeled joint damping leaves (MuJoCo run C over the last 5 s: |ξ| up to 1.05e-2, |β| up to 1.32e-2, and η̇ between 0.047 and 0.064, final 0.0643, instead of ν_d = 0.08), without changing the paper's closed loop when the new gains are zero.

Files to touch:

| File | Change |
| --- | --- |
| `include/se3pf/controller.hpp` | new fields in `Gains` (default 0), integrator state in `Controller`, zeroed in `reset`, used in `step` |
| `sim/mujoco_panda.hpp`, `sim/mujoco_panda.cpp` | a gains override in `MujocoRunOptions`; optionally a viscous compensation D̂ q̇ in the held torque |
| `apps/panda_mujoco.cpp` | a run "C-I" with the new terms, and its checks in the summary |
| `tests/test_controller.cpp`, `tests/mujoco/test_mujoco_panda.cpp` | the tests below |

Design. Add one integrator per channel and feed it back through μ, so the controller still returns q̈* and knows no dynamics:

```latex
z_\parallel = \int e_v\,dt,\quad z_\xi = \int \xi\,dt,\quad z_\beta = \int \beta\,dt,\qquad \mu_\parallel \mathrel{-}= k_I\,z_\parallel,\quad \mu_\pitchfork \mathrel{-}= K_I\,z_\xi,\quad \mu_\beta \mathrel{-}= K_{I,\beta}\,z_\beta
```

Each channel is still decoupled after feedback linearization, so stability is a one-line check. The transverse channel becomes s³ + K_d s² + K_p s + K_I, which Routh–Hurwitz keeps stable for K_I < K_d K_p (128 for the paper's 16 and 8). The tangential one becomes s² + k_t s + k_I, critically damped at k_I = k_t²/4 (6.25 for k_t = 5).

The μ terms go next to the existing ones:

```cpp
// include/se3pf/controller.hpp:292-296
                VecN mu = VecN::Zero();
                mu[0] = muPar;
                mu.template segment<5>(1) = -gains_.Kp * out.xi - gains_.Kd * xiDot;  // eq:transverse
                if constexpr (n == 7)
                    mu[6] = -gains_.KpBeta * out.beta - gains_.KdBeta * yDot[6];  // eq:beta-law
```

The prototype used for the numbers below added `double kiTan = 0.0, KiXi = 0.0, KiBeta = 0.0; double integralLimit = 0.5;` to `Gains`, a `Vec5 zXi_` and two doubles to the private members, and this update after every check of `step` had passed, just before the prediction:

```cpp
// include/se3pf/controller.hpp, CTRL-1 prototype sketch (scratch copy only, not in the file)
                auto integrate = [&](double z, double e, double k) {
                    if (!(k > 0.0))
                        return 0.0;
                    if (r < 1.0)  // conditional integration: not while the ramp is on (no windup at the start)
                        return z;
                    const double zMax = gains_.integralLimit / k;
                    return std::clamp(z + e * dt, -zMax, zMax);
                };
                zTan_ = integrate(zTan_, st.eTan, gains_.kiTan);
                for (int i = 0; i < 5; ++i)
                    zXi_[i] = integrate(zXi_[i], out.xi[i], gains_.KiXi);
                if constexpr (n == 7)
                    zBeta_ = integrate(zBeta_, out.beta, gains_.KiBeta);
```

Four design points. The clamp bounds each term |K_I z| by `integralLimit`, so a long saturation cannot wind up. Integrating only after the ramp keeps the start transient (|ξ₀| = 0.031 for about a second) out of the integrators. The update comes after the checks, so a failed step leaves the state untouched. Friction compensation, if you add it, belongs with M, C and G in the torque (`sim/mujoco_panda.cpp:445` here, the driver on the robot), not in the controller.

Integral action alone did not reach the target in any configuration tried. The damping torque −D q̇ changes along the path with the joint velocities, so it acts like a periodic disturbance rather than a constant one, and raising the bandwidth enough runs into the 30 % acceleration margin. Expect CTRL-1 to need friction compensation identified to about 10 %, with integral action for the rest; that is a finding to put in the ticket.

Tests to write:

- With every new gain 0, the existing 132 test cases pass unchanged (the paper's numbers to their last digit).
- `reset` zeroes the integrators: a step after `reset` equals the step of a fresh controller.
- The clamp: hold a constant ξ for many steps and check |K_I z| ≤ `integralLimit` exactly.
- No integration while r < 1, and integration from the first step with r = 1.
- A joint-acceleration-level loop with a constant disturbance d added to the plant (q̈ = q̈* + d): the outputs then see A d on top of μ, so without the integrators the steady ξ, β and e_v sit near the matching rows of A d divided by K_p (ξ, β) and k_t (e_v), and with them they go to 0.
- "step does not allocate" still passes, in Release and in Debug.
- In `tests_mujoco`, a 20 s run C with the new terms (tagged `SLOW_IN_DEBUG`).

Acceptance (TICKETS.md, CTRL-1): in MuJoCo run C, last 5 s |ξ| < 1e-3 and η̇ within 2 % of ν_d, with every `HardwareBounds` margin kept, ramp included; with the new terms off, every existing test passes unchanged; the integrators are clamped and reset with `Controller::reset`; run D-G still keeps every margin. (The prototype's D-G with exact compensation and the paper's gains kept them: last 5 s |ξ| 7.3e-4, η̇ 0.07983 to 0.08038.)

### Project 2: a new closed path

Goal: add a closed path the Panda can follow, with constant speed in the product metric, and run the whole pipeline on it: tube, lift, kernel frame, start configuration and the 20 s loop.

A good candidate, verified for this guide, is the coning circle with k cone revolutions per loop: R(θ) = R₀ R_z(kθ) A R_z(−kθ), p(θ) = c + r(cos θ, sin θ, 0). Its body velocity has constant norm for every integer k:

```latex
\tilde\omega(\theta) = k\,R_z(k\theta)\,w_0,\qquad \tilde\omega'(\theta) = k^2 R_z(k\theta)\,(e_3\times w_0),\qquad \sigma^2 = w_R\,k^2\,\|w_0\|^2 + w_p\,r^2,\quad \|w_0\| = 2\sin(\alpha/2)
```

Files to touch: `include/se3pf/path.hpp` and `src/path.cpp` (a class `WobblingCircle`, or an `int k = 1` parameter of `ConingCircle`); `tests/test_path.cpp` (the `checkArcLengthPath` helper at `tests/test_path.cpp:16-36` already tests everything a path must satisfy); a fixture and tests for its tube and lift; and a way to run the loop on it. `simulate` takes a `PandaExample`, whose members are fixed to the paper's path, so either give `PandaExample` a path parameter or write a small loop like the one in `src/panda_example.cpp:126-199`.

Design notes:

- With k = 1 the new class must reproduce the paper exactly; the prototype did (L = 0.77008765, angles 0.161182 and 8.008e-5, tube radius 0.1250, lift margin 0.3592 rad, max ||ξ| − design| 2.434e-5).
- The constructor must call the constant-speed check, which throws `std::invalid_argument("Path: the speed is not constant in this metric")` otherwise.

```cpp
// src/path.cpp:28-38
        template <class BodyVelocity>
        double constantSpeed(const BodyVelocity &zetaTilde, const Metric &W)
        {
            const double sigma = W.norm(zetaTilde(0.0));
            for (int k = 1; k < 16; ++k) {
                const double th = 2.0 * EIGEN_PI * k / 16.0;
                if (std::abs(W.norm(zetaTilde(th)) - sigma) > 1e-12 * sigma)
                    throw std::invalid_argument("Path: the speed is not constant in this metric");
            }
            return sigma;
        }
```

What breaks without constant speed: s = σθ is then not arc length, ‖ζ_γ‖_W ≠ 1, and the transport (eq:transport) no longer keeps N W-orthonormal and normal: its comment at `src/tube.cpp:20-22` relies on ‖ζ_γ‖_W = 1. φ′ = −1 on the path fails too, and ν_d is no longer a speed. A figure-eight such as p = c + r(sin θ, sin θ cos θ, 0) needs numerical arc length (design doc, path: S(θ) by Gauss–Legendre on a grid, inverted by Newton, θ(s) in a C² quintic spline, since ζ_γ′ needs θ″).

A free insight: the tube is left-invariant. A constant pose h applied to the whole path (γ_h = h γ) has the same body velocity ζ_γ. The prototype wrapped the paper's circle in a path whose `pose(s)` returns h γ(s) and whose `velocity` and `acceleration` return the circle's own values, with h the rotation by 0.3 rad about the x-axis through the circle's centre. It got the same N(s), bit for bit, and the same holonomy angles; only the lift changed, to a margin of 0.3630 rad.

Numbers to reproduce (Panda, l = 0.1 m, centre (0.40, 0, 0.45), r = 0.12, α = 0.25, 2000 intervals; the loop is the paper's: ν_d = 0.08, start Ψ(0.1, ξ₀) with β = 0, 1 ms, no ramp):

Tests to write: `checkArcLengthPath` on the new path for two metrics; k = 1 against `ConingCircle` to 1e-15; L for k = 2 as a reference value; the tube's holonomy, closure and frame properties; the lift's closure, margins and minimum check; the closed loop's designed response, and that halving dt halves its deviation.

Acceptance: all path, tube and lift tests pass; tube closure below 1e-9; lift closure below 1e-6 with every joint at least 0.10 rad from its limits; the 20 s loop follows |ξ₀|(1 + 4t)exp(−4t) to within 3e-5 with one Newton update per cycle; with the 1 s ramp, the peak command stays below 30 % of the acceleration limits (k = 2: 39.4 % without the ramp, 8.7 % with it; the deviation from the designed response is then not a criterion, since that response assumes no ramp).

### Project 3: the coupled lift q₃ = q₁ as a second Lift objective

Goal: let `Lift` build either the paper's lift (nearest the rest posture q_r) or the coupled lift (joint 3 equal to joint 1), so the two can be compared on the same path. That is the design doc's open decision "which lift the paper reports".

### Project 4: a general left-invariant metric W (milestone 11)

Goal: let `Metric` accept any symmetric positive definite W, computing Exp_I and Γ from the geodesic ODEs and Log_I by Newton's method, while the product type keeps its closed forms.

Files to touch: `include/se3pf/metric.hpp`, `src/metric.cpp`, `tests/test_metric.cpp`; `src/path.cpp` only if a curve loses constant speed. The constructor that refuses everything else today:

```cpp
// src/metric.cpp:12-20
    Metric::Metric(const Mat6& W) : W_(W)
    {
        const double wR = W(0, 0), wp = W(3, 3);
        Mat6 P = Mat6::Zero();
        P.diagonal() << wR, wR, wR, wp, wp, wp;
        if (!(wR > 0.0) || !(wp > 0.0) || !W.allFinite() || (W - P).cwiseAbs().maxCoeff() > 1e-12 * std::max(wR, wp))
            throw std::invalid_argument("Metric: only the product type W = diag(wR I, wp I), wR, wp > 0, is "
                                        "implemented (Example 1)");
    }
```

Design (design doc, Module: se3 and metric). Integrate the body velocity z, the pose c = (R, p) and the six variation pairs, stored as two 6 × 6 matrices S and D, over t in [0, 1] with a fixed number of RK4 steps (32):

```latex
\dot z = W^{-1}\mathrm{ad}_z^\top W z,\quad \dot R = R\hat\omega_z,\quad \dot p = R\,v_z,\quad \dot S = W^{-1}\bigl(\mathrm{ad}_S^\top W z + \mathrm{ad}_z^\top W S\bigr),\quad \dot D = S - \mathrm{ad}_z D
```

```latex
z(0) = \zeta,\quad c(0) = I,\quad S(0) = I,\quad D(0) = 0,\qquad \mathrm{Exp}_I(\zeta) = c(1),\qquad \Gamma(\zeta) = D(1)
```

- Project R back onto SO(3) once at the end (SVD, as the tube does for H at `src/tube.cpp:187-188`).
- Log_I by Newton: x ← x + Γ(x)⁻¹ (log of Exp_I(x)⁻¹ g)^∨, started from the product-type log. A fixed step count makes Exp_I a smooth map, so Log_I is its exact inverse.
- Keep a flag for the product type and its closed forms: about 56 µs per Exp and Γ (design doc) is fine offline and in simulation, but three projections with Newton inside are too slow for the 1 kHz loop.
- `ad` finally gets a caller (mutation drill 1).

What else changes, and what does not:

- `poseError` in the lift is chart-independent (`src/lift.cpp:24-36`): unchanged.
- `RigidBody::retract` only needs some curve with the right velocity: unchanged.
- The bound in `estimateTubeRadius` stays valid: W ≥ λ_min I makes every curve at least √λ_min times as long, so dist_W ≥ √λ_min dist_I for any W.
- `constantSpeed` becomes live: with W = diag(1, 1, 2, 1, 1, 1) the example curves keep constant speed (comment at `tests/test_metric.cpp:49`); with a W that couples rotation and translation they may not (project 2).

Tests to write:

- The strong test of the design doc: with W = M = diag(J, m I), geodesics are free rigid-body motions. With ad_ζ = [ω̂ 0; v̂ ω̂], W⁻¹ad_ζᵀWζ is exactly M⁻¹(Jω × ω, m v × ω), Euler's equations of `src/rigid_body.cpp`. So Exp_I(ζ) must equal one second of `RigidBody::integrate` from the identity with velocity ζ and u = 0.
- For a product W, the ODE path reproduces the closed forms (Exp, Γ) to 1e-10.
- Log(Exp(ζ)) = ζ to 1e-10 below the injectivity radius; Γ against central differences of Exp (h = 1e-6, to 1e-8); GammaInv·Gamma = I.
- "Metric accepts only the product type" becomes a test of what is now accepted: an API change, so update the design doc and TICKETS.md.

Acceptance: every existing test passes with the product type, also with its fast path switched off (except the timing tests); the W = M test to 1e-10; the tube and both examples build with W = diag(1, 1, 2, 1, 1, 1).

### Project 5: the libfranka 0.9.2 driver against a mock (HW-1)

Goal: an executable that runs the paper's motion through libfranka's control loop, built first against a mock of the few libfranka classes it uses, and compiling against the real libfranka 0.9.2 headers. The Panda (FER) needs 0.9.x; libfranka 0.10 and later support only the FR3.

Files to touch:

| File | Content |
| --- | --- |
| `apps/robot_driver.cpp` | the driver: setup, kinematics check, torque loop, log written after the run |
| `mock/franka/robot.h`, `model.h`, `robot_state.h`, `control_types.h`, `duration.h`, `exception.h` | the mock; the earlier repository's `~/Desktop/panda_path_following/mock/franka/` (375 lines) is a working template |
| `CMakeLists.txt` | `option(SE3PF_WITH_LIBFRANKA ...)` off by default, choosing the real library or the mock include path; the `se3pf` library still includes no libfranka header |
| `tests/` | a driver test program run against the mock |

Design, in the order the driver runs:

1. Offline: build `PandaExample` (tube, lift, starts), the controller with `setRampTime(1.0)`, and a log buffer reserved for every row.
1. Kinematics check: compare `PandaArm::output(q)` with `model.pose(franka::Frame::kFlange, state)` and `model.bodyJacobian(franka::Frame::kFlange, state)`. Both return column-major `std::array`s (16 and 42 entries), so `Eigen::Map<const Eigen::Matrix4d>` and `Eigen::Map<const Mat67>` read them directly. The Jacobian's rows are (v, ω): swap the two 3-row blocks before comparing with (ω, v). Use neither `kEndEffector` (it includes the load offset set in Desk) nor `zeroJacobian` (base frame).
1. Torque loop: `robot.control(callback)`, where the callback receives `(const franka::RobotState&, franka::Duration)` and returns `franka::Torques`. Map `state.q` and `state.dq`, call `controller.step`, and compute τ = M q̈* + C q̇ from `model.mass(state)` (49 entries, column-major) and `model.coriolis(state)` (7). The robot adds G itself. Write one log row, return the torques; on a failed step, return `franka::MotionFinished` with damping τ = −D q̇ (HW-2 refines this).
1. After the loop: write the log as CSV, as `apps/panda_sim.cpp` does.

The callback runs every millisecond inside libfranka's real-time thread. So it must not allocate, print, throw or lock: everything it touches is built before `control` is called, as in `simulate` (`src/panda_example.cpp:119-123`).

Tests to write:

- The kinematics check on mocked states, with the rows swapped, to 1e-5 (and with the swap left out, to see it fail).
- A mock run of the paper's motion. With a mock plant that integrates q̈ = q̈* exactly (held acceleration), it must reproduce the joint-acceleration numbers (max ||ξ| − design| 2.43e-5 without the ramp). With the ramp and a held torque it must stay within MuJoCo run B and C's O(dt) bounds.
- The callback does not allocate: the counting `operator new` of `tests/test_controller.cpp:52-72`, read before and after 1000 callbacks.
- The build with `-DSE3PF_WITH_LIBFRANKA=ON` compiles against the real 0.9.2 headers (`-DFranka_DIR=.../libfranka-0.9.2/build`).

Acceptance (TICKETS.md, HW-1): builds against the mock and compiles against the real headers; the kinematics check agrees to 1e-5 with the rows swapped; the mock run reproduces the numbers above; the 1 kHz callback does not allocate. Motion on the robot is HW-3, after the preflight and the safety monitor of HW-2.
