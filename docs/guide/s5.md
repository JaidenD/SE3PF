## Ownership and lifetimes

Two example classes own every long-lived object; everything else either copies what it needs or holds a reference that must not outlive its owner. The compiler does not track reference lifetimes. So the code uses declaration order, deleted overloads and deleted copies to make the dangerous cases fail to compile.

### Who owns what

| Class | Holds | As | Consequence |
| --- | --- | --- | --- |
| `PandaExample` | metric, R0, path, tube, lift, kernel frame, `LiftRedundancy`, `CouplingRedundancy`, two starts | values (members) | owns everything for the Panda; not copyable or movable |
| `RigidBodyExample` | metric, path, tube, body | values | owns everything for the rigid body; not copyable or movable |
| `Tube` | the path | `const Path& path_` (`include/se3pf/tube.hpp:93`) | the path must outlive the tube |
| `Tube` | the metric | `Metric metric_`, a copy (`include/se3pf/tube.hpp:94`) | a temporary metric is fine |
| `Tube` | N and N′ at the nodes | `PeriodicHermite<Mat65> N_`, owns two `std::vector`s | 0.96 MB on the heap, freed with the tube |
| `Lift`, `KernelFrame` | node values and derivatives | own `std::vector`s, no references | may be built from a temporary path or lift |
| `LiftRedundancy` | the lift and the kernel frame | `const Lift&`, `const KernelFrame&` (`include/se3pf/lift.hpp:140-141`) | both must outlive it |
| `Controller<System>` | the tube | `const Tube& tube_` (`include/se3pf/controller.hpp:331`) | the tube (and its path) must outlive the controller |
| `Controller<System>` | gains, reference | copies (`Gains gains_`, `TangentialReference reference_`) | temporaries are fine |
| `Controller<System>` | the redundancy output | `const RedundancyOutput* redundancy_` (`include/se3pf/controller.hpp:334`) | must outlive the controller; null for n = 6 |
| `TangentialReference` | the reference function | `std::function` holding a lambda; the library's lambdas capture by value | nothing to outlive |

```cpp
// include/se3pf/tube.hpp:93-98
            const Path& path_;
            Metric metric_;
            double L_;
            int n_;
            PeriodicHermite<Mat65> N_;
            TubeDiagnostics diag_;
```

Why a reference to the path but a copy of the metric? `Path` is an abstract class, so the tube cannot hold one by value without knowing the concrete type. A reference to the base class keeps the tube general, while `Metric` is a concrete 288-byte class whose copy removes one lifetime to worry about.

The controller takes the redundancy output by pointer, not by reference, because it is optional. The rigid body passes nothing (the default `nullptr`). The constructor throws if n = 7 gets null or n = 6 gets non-null (`include/se3pf/controller.hpp:176-179`).

The function objects of the references capture by value, for example `[nu]` in `constantVelocity` (`include/se3pf/controller.hpp:69`) and `[L]` in `RigidBodyExample::reference` (`src/rigid_body_example.cpp:42`). Capturing `[&]` there would keep a reference to the parameter `nu` or the local `L`, which die when the factory returns, so the reference would dangle at once. Capturing `this` would tie it to the example's lifetime.

### Declaration order is construction order

C++ constructs members in the order they are declared in the class, whatever order the initializer list is written in. Destruction runs in the reverse order. So the members of `PandaExample` are declared in dependency order:

```cpp
// include/se3pf/panda_example.hpp:103-114
        private:
            Metric metric_;
            Matrix3d R0_;
            ConingCircle path_;
            Tube tube_;
            Lift lift_;
            KernelFrame kernel_;  // X of Lemma 3 (tube_ holds the normal frame N)
            LiftRedundancy beta_;
            CouplingRedundancy coupling_;
            Vec7 paperStart_;
            Vec7 selfMotionStart_;
    };
```

```cpp
// src/panda_example.cpp:31-44
    // Members are initialized in the order of their declaration, which is the order of the list below.
    PandaExample::PandaExample(double l)
        : metric_(exampleMetric(l)),
          R0_(restAttitude()),
          path_(R0_, center(), radius, cone, metric_),
          tube_(path_, metric_),
          lift_(path_, PandaArm::restPosture()),
          kernel_(lift_),
          beta_(lift_, kernel_),
          coupling_(),
          paperStart_(start(beta_, xi0(), 0.0)),
          selfMotionStart_(start(beta_, Vec5::Zero(), selfMotionBeta0))
    {
    }
```

Each initializer reads only members declared above it: `path_` reads `metric_` and `R0_`, `tube_` reads `path_`, and `paperStart_` calls `start`, which uses `lift_` and `tube_`. If `tube_` were declared before `path_`, the tube constructor would call `path.length()` on an object not yet built: undefined behaviour. `length()` is virtual, so the call goes through a vtable pointer that is not set yet; it may crash or return garbage.

The list is written in the same order as the declarations. GCC's `-Wreorder` (part of `-Wall`) warns otherwise, and `tools/ci.sh` builds with warnings as errors.

The reverse destruction order is safe too: `beta_` dies before `lift_` and `kernel_`, and `tube_` before `path_`. `RigidBodyExample` follows the same rule with `metric_`, `path_`, `tube_`, `body_` (`include/se3pf/rigid_body_example.hpp:59-62`).

### Deleted rvalue overloads: no temporaries where a reference is kept

A `const T&` parameter accepts a temporary, and the temporary dies at the end of the full expression. Any class that stores that reference then dangles. Without the deleted overload, this compiles without a warning under GCC 11 with `-Wall -Wextra` (checked with a scratch compile):

```cpp
// example, not in the project: refused by the deleted Tube(const Path&&, ...) overload
Tube tube(ConingCircle(R0, center, 0.12, 0.25, W), W);  // the ConingCircle dies at the semicolon
double eta = 0.0; Vec5 xi;
tube.outputs(g, 0.1, eta, xi);                           // reads the destroyed path: undefined behaviour
```

The constructor itself would succeed, because the path is alive while the frame is built, so only later calls fail, often silently. The fix is an overload that takes `const T&&` and is deleted.

Overload resolution prefers to bind a temporary (an rvalue) to an rvalue reference. So it picks the deleted overload, and the compiler stops with "use of deleted function 'se3pf::Tube::Tube(const se3pf::Path&&, const se3pf::Metric&, int)'".

```cpp
// include/se3pf/tube.hpp:55-56
            Tube(const Path& path, const Metric& metric, int gridIntervals = 2000);
            Tube(const Path&& path, const Metric& metric, int gridIntervals = 2000) = delete;  // no temporaries
```

| Class | Deleted overloads | Arguments refused |
| --- | --- | --- |
| `Tube` | `include/se3pf/tube.hpp:56` | a temporary path |
| `Controller<System>` | `include/se3pf/controller.hpp:182-183` | a temporary tube |
| `LiftRedundancy` | `include/se3pf/lift.hpp:130-132` | a temporary lift, a temporary kernel frame, or both (three overloads, one per combination) |
| `PandaExample` accessors | `include/se3pf/panda_example.hpp:70-76` | `metric()`, `path()`, `tube()`, `lift()`, `kernelFrame()`, `redundancy()`, `coupling()` on a temporary example |
| `RigidBodyExample` accessors | `include/se3pf/rigid_body_example.hpp:40-42` | `metric()`, `path()`, `tube()` on a temporary example |

`LiftRedundancy` needs three overloads because each of its two reference parameters can independently be a temporary. The metric parameter of `Tube` has no deleted twin, because the tube copies it.

The accessors use ref-qualifiers. `tube() const&` is chosen for a named example and `tube() const&& = delete` for a temporary one, so `PandaExample().tube()` does not compile. Without that, `Controller<PandaArm> c(PandaExample().tube(), ...)` would build a whole example (25 ms), keep a reference into it, and destroy it at the semicolon.

The tests check all of this at compile time with `std::is_constructible_v` and a small detection idiom (`tests/test_tube.cpp:159-162`, `tests/test_lift.cpp:240-246`, `tests/test_controller.cpp:460-463`, `tests/test_panda_example.cpp:166-189`).

```cpp
// include/se3pf/panda_example.hpp:65-72
            const Tube& tube() const& { return tube_; }
            const Lift& lift() const& { return lift_; }
            const KernelFrame& kernelFrame() const& { return kernel_; }
            const LiftRedundancy& redundancy() const& { return beta_; }      // beta = X^T (q - q*), the paper's
            const CouplingRedundancy& coupling() const& { return coupling_; }  // beta = q_3 - q_1
            const Metric& metric() const&& = delete;
            const ConingCircle& path() const&& = delete;
            const Tube& tube() const&& = delete;
```

The pointer to the redundancy output needs no such guard. `&PandaExample().redundancy()` is already refused by the deleted accessor, and taking the address of a plain temporary does not compile at all.

### Non-copyable owners

`PandaExample` and `RigidBodyExample` delete their copy constructor and copy assignment (`include/se3pf/panda_example.hpp:34-35`, `include/se3pf/rigid_body_example.hpp:32-33`). Without that, the compiler would generate a member-wise copy, and a copied reference member still refers to the original object.

A scratch test of a class with members `Metric`, `ConingCircle`, `Tube` confirms it: after `Owner b = a;`, `b.tube.path()` is `a.path`, not `b.path`. When `a` is destroyed, `b` dangles.

A declared copy constructor, even a deleted one, stops the compiler from generating a move constructor. So these classes cannot be moved either (`tests/test_panda_example.cpp:180-182` checks both for `PandaExample`). `MujocoPanda` deletes its copies for a different reason: it owns `mjModel` and `mjData` through `std::unique_ptr`, so a copy would free them twice (`sim/mujoco_panda.hpp:72-73`). The `unique_ptr` members already make the class non-copyable; the explicit `= delete` documents it for the reader, as its comment says.

The smaller classes stay copyable on purpose, since `Metric`, `Gains`, `RigidBody`, `Lift` and `KernelFrame` own their data. `Tube` and `Controller` can be copy-constructed but not assigned, because a reference member cannot be reseated. Such a copy shares the same path or tube, which is harmless while the owner lives.

### Function-local statics in the tests

The tests build the expensive objects once per program run. A function-local `static` is constructed the first time control passes through it, and C++11 guarantees that this initialization is thread-safe.

```cpp
// tests/panda_fixture.hpp:8-14
    // An inline function, so its static is one object across all translation units. Built on first use, so a test
    // program that never asks for it does not build it.
    inline const se3pf::PandaExample& pandaExample()
    {
        static const se3pf::PandaExample ex;
        return ex;
    }
```

`inline` matters here: three files of the `tests` program include this header (`test_controller.cpp`, `test_lift.cpp`, `test_panda_example.cpp`), and an `inline` function is one function program-wide, so all of them share one `ex`. A fourth, `tests/mujoco/test_mujoco_panda.cpp`, belongs to the separate `tests_mujoco` program, which builds its own. `testing::rng()` (`tests/test_helpers.hpp:46-50`) uses the same pattern for one shared random generator.

In `tests/tube_fixture.hpp:13-19` three statics are declared in a row (`W`, `path`, `tube`). Statics are destroyed in reverse order at program exit, so the path outlives its tube there too.

A related choice in the library: `PandaArm::qMin()` and the other limits are functions returning a `Vec7`, not `static const Vec7` members (`include/se3pf/panda.hpp:37-44`). Static objects in different files are initialized in an unspecified order, so another file's static initializer could read them before they are set.

### The rule for your own code

Build every long-lived object as a named variable that lives for the whole run, and build it before anything that refers to it. `apps/panda_sim.cpp:110` does exactly this, `const PandaExample example;`, and then passes `example` by reference to `simulate`. Inside `simulate` the controller is a local (`src/panda_example.cpp:91-92`), so it dies before the example it refers to.

Temporaries are fine only where the receiver copies. That covers a `Metric` passed to `Tube`, `Gains` and `TangentialReference` passed to `Controller`, a path passed to `Lift`, and a lift passed to `KernelFrame`. If the compiler says "use of deleted function" about an overload with `&&`, you have passed a temporary where a reference is kept: give it a name.
