## Walkthrough

This section walks through every function of the layer in file order: the code, what it computes, and what it does at the edges. Numbers quoted here come from scratch programs linked against `build-ci-release/libse3pf.a` and compiled with the Release flags (`-O3 -DNDEBUG`).

### types.hpp: names for the sizes

`types.hpp` gives every matrix size of the project a short name, so a signature says what it holds: `Vec5` is ξ, `Mat65` is N, `Mat67` is the Panda's J_b.

```cpp
// include/se3pf/types.hpp:1-21
#pragma once
#include <Eigen/Dense>

namespace se3pf {
    using Vec5 = Eigen::Matrix<double, 5, 1>;
    using Vec6 = Eigen::Matrix<double, 6, 1>;
    using Vec7 = Eigen::Matrix<double, 7, 1>;
    using Mat5 = Eigen::Matrix<double, 5, 5>;
    using Mat6 = Eigen::Matrix<double, 6, 6>;
    using Mat65 = Eigen::Matrix<double, 6, 5>;  // normal frame N
    using Mat67 = Eigen::Matrix<double, 6, 7>;  // Panda body Jacobian
    using Pose = Eigen::Matrix4d;

    // Sizes that depend on the system (n = 6 or 7)
    template <int R, int C> using Mat = Eigen::Matrix<double, R, C>;
    template <int N> using Vec = Eigen::Matrix<double, N, 1>;

    using Eigen::Matrix3d;
    using Eigen::Matrix4d;
    using Eigen::Vector3d;
}
```

- `#pragma once` makes the compiler skip the file if it was already included in this translation unit. For `types.hpp` a second copy happens to be harmless: repeating an alias to the same type is allowed, and g++ accepts the double inclusion. A second copy of `metric.hpp` fails with "redefinition of 'class se3pf::Metric'" (checked with g++). Every header carries the guard, so a header can be included any number of times.
- `using Vec6 = Eigen::Matrix<double, 6, 1>;` is a type alias: a second name, not a new type. The size is a template argument, so the 6 doubles live inside the object itself; creating, copying or returning a `Vec6` never allocates.
- `template <int R, int C> using Mat = ...` is an alias template. The controller writes `Mat<6, n>` with n = `System::kDof` (`include/se3pf/controller.hpp:139`, used at `include/se3pf/controller.hpp:218`) and gets a 6 × 6 or 6 × 7 matrix depending on the system.
- `using Eigen::Matrix3d;` (a using-declaration) brings one Eigen name into `se3pf`, so the headers can write `Matrix3d` without the `Eigen::` prefix.

Because `Pose` is only another name for `Matrix4d`, the compiler cannot tell a pose from an se(3) element. `vee(g)` on a pose compiles and returns meaningless numbers; the names document intent but do not enforce it.

### se3.cpp: hat and vee on R³

`hat` builds ω̂ as a linear combination of the three generators of so(3); `vee` reads the three independent entries back.

```cpp
// src/se3.cpp:8-31
    Matrix3d hat(const Vector3d &w)
    {
        Matrix3d e1 = Matrix3d::Zero(), e2 = Matrix3d::Zero(), e3 = Matrix3d::Zero();

        e1(1,2) = -1.0;
        e1(2,1) = 1.0;

        e2(2,0) = -1.0;
        e2(0,2) = 1.0;

        e3(0,1) = -1.0;
        e3(1,0) = 1.0;

        return w[0] * e1 + w[1] * e2 + w[2] * e3;
    }

    Vector3d vee(const Matrix3d &S)
    {
        Vector3d v = Vector3d::Zero();
        v(0) = S(2,1);
        v(1) = S(0,2);
        v(2) = S(1,0);
        return v;
    }
```

- Each entry of the result is ±w_i plus exact zeros, so `hat` is exact: the test measures a skew error of 0 and `vee(hat(w)) == w` bit for bit.
- `w[0] * e1 + w[1] * e2 + w[2] * e3` is an Eigen expression. It is evaluated into the declared return type `Matrix3d` on `return`, so no dangling expression escapes.
- `vee` does not check skewness and does not average S(2,1) with −S(1,2). Its one caller in the library is `logSO3`, which passes R − Rᵀ: exactly skew, since each pair is computed as a − b and b − a. The tests also apply `vee` to finite-difference matrices that are skew only to O(h²) plus rounding; their tolerances absorb that.

Parameters are `const Vector3d&`, a reference to const. The function reads the caller's vector without copying it and cannot modify it.

### se3.cpp: expSO3

`expSO3` is Rodrigues' formula with a series for tiny angles.

```cpp
// src/se3.cpp:33-45
    Matrix3d expSO3(const Vector3d &w)
    {
        const double theta = w.norm();
        const Matrix3d K = hat(w);

        // for small angles: sin(theta)/theta ~ 1, (1-cos(theta))/theta^2 ~ 1/2
        if (theta < 1e-8)
            return Matrix3d::Identity() + K + 0.5 * K * K;

        // Rodrigues' formula
        return Matrix3d::Identity() + (std::sin(theta) / theta) * K
             + ((1.0 - std::cos(theta)) / (theta * theta)) * K * K;
    }
```

The branch exists for θ = 0, where `sin(theta) / theta` is 0/0 and gives NaN (measured). Below 1e-8 the series I + K + K²/2 drops terms of size θ³/6 ≈ 1.7e-25, far below double precision.

At and above 1e-8 the closed form is accurate even though (1 − cos θ)/θ² loses digits to cancellation. That coefficient multiplies K² of size θ², so its absolute error stays near 1e-16. Against a long double reference, the worst entry error over θ ∈ [1e-8, 1e-2] is 1.1e-16.

### se3.cpp: logSO3

`logSO3` returns the rotation vector θn of R, with θ ∈ [0, π]. It has three branches: tiny angles, angles near π, and the general case.

```cpp
// src/se3.cpp:47-68
    Vector3d logSO3(const Matrix3d &R)
    {
        const Vector3d s = 0.5 * vee(Matrix3d(R - R.transpose()));  // = sin(theta) * axis
        const double c = 0.5 * (R.trace() - 1.0);          // = cos(theta)
        const double theta = std::atan2(s.norm(), c);         // angle in [0, pi], accurate at every angle

        if (theta < 1e-6)  // small angle: theta / sin(theta) = 1 + theta^2/6 + ...
            return (1.0 + theta * theta / 6.0) * s;

        if (theta > EIGEN_PI - 1e-4) {  // near pi, sin(theta) ~ 0, so s no longer carries the axis
            // symmetric part: (R + R^T)/2 = cos(theta) I + (1 - cos(theta)) n n^T
            const Matrix3d nnT = (0.5 * (R + R.transpose()) - c * Matrix3d::Identity()) / (1.0 - c);
            Index j;
            nnT.diagonal().maxCoeff(&j);           // largest |n_j| gives the most accurate column
            Vector3d n = nnT.col(j).normalized();
            if (n.dot(s) < 0.0)                    // sign of the axis from s (at exactly pi, either sign is valid)
                n = -n;
            return theta * n;
        }

        return (theta / s.norm()) * s;  // s.norm() = sin(theta)
    }
```

Line 49 converts `R - R.transpose()` to `Matrix3d` explicitly because `vee` is overloaded. `R - R.transpose()` is not a `Matrix3d` but an Eigen expression object (`CwiseBinaryOp<...>`) that computes entries on demand. Both `vee(const Matrix3d&)` and `vee(const Matrix4d&)` accept it through Eigen's converting constructor, so g++ reports "call of overloaded 'vee(...)' is ambiguous" and lists both candidates.

The angle comes from `atan2(|s|, c)`, not `acos(c)`. Near θ = 0 and θ = π, acos has an infinite slope and amplifies rounding in c. The table gives the worst absolute angle error over the 20 axes the logSO3 test draws:

| θ | error of acos(c) | error of atan2(‖s‖, c) |
| --- | --- | --- |
| 1e-8 | 1.0e-8 (returns 0) | 1.7e-24 |
| 1e-6 | 4.4e-11 | 2.1e-22 |
| 1e-4 | 2.6e-13 | 2.7e-20 |
| π − 1e-6 | 7.3e-10 | 8.9e-16 |

The atan2 errors are a single rounding of θ (relative error below 3e-16); the acos errors are 1e5 to 1e8 times larger than that.

The small-angle branch (θ < 1e-6) uses θ/sin θ = 1 + θ²/6 + 7θ⁴/360. The dropped relative term is below 2e-26. Like in `expSO3`, the branch is needed only at the identity, where the general formula divides 0 by 0.

The near-π branch (θ > π − 1e-4) exists because s = sin θ · n is computed from entries with absolute rounding near 1e-16. When sin θ ≈ π − θ is small, the axis s/‖s‖ has a relative error of about 1e-16/(π − θ). The symmetric part divides by 1 − c ≈ 2 instead. Worst round-trip error |log(exp(w)) − w| over the 20 axes of the logSO3 test:

| Angle | this code | without the near-π branch |
| --- | --- | --- |
| π − 1e-3 (general formula) | 3.4e-13 | 3.4e-13 |
| π − 1e-6 | 6.7e-16 | 3.0e-10 |
| π − 1e-8 | 4.4e-16 | 3.2e-8 |

The switch at π − 1e-4 is a compromise. Just below it the general formula is still in use and loses digits: at π − 1.01e-4 the worst round-trip error over 1000 random axes is 4.9e-12, against 8.9e-16 just above the switch.

- `Index j; nnT.diagonal().maxCoeff(&j);` finds the largest n_j². Column j of nnᵀ is n_j n, and its length |n_j| ≥ 1/√3, so the normalization never divides by a small number. `Index` is Eigen's signed index type (`std::ptrdiff_t`), visible here through `using namespace Eigen;` at `src/se3.cpp:4`.
- The sign of n comes from s, since s = sin θ · n points along +n for θ < π. At exactly π, s is zero and either sign is a valid logarithm.
- `EIGEN_PI` is a `long double` literal in Eigen 3.4, so `EIGEN_PI - 1e-4` is computed in long double. The comparison with a double works by promotion.

`logSO3` never fails: at exactly π it returns one of the two valid answers. Refusing a rotation by π is a decision of `Metric::Log`, not of this function.

### se3.cpp: Jr and JrInv

`Jr(w)` is the right Jacobian of exp: d/dt exp(ŵ) = exp(ŵ)(J_r(w)ẇ)^. `JrInv` is its inverse in closed form.

```cpp
// src/se3.cpp:70-82
    Matrix3d Jr(const Vector3d &w)
    {
        const double theta = w.norm();
        const Matrix3d K = hat(w);

        // small angles: (1 - cos(theta))/theta^2 ~ 1/2, (theta - sin(theta))/theta^3 ~ 1/6
        if (theta < 1e-6)
            return Matrix3d::Identity() - 0.5 * K + (1.0 / 6.0) * K * K;

        return Matrix3d::Identity()
             - ((1.0 - std::cos(theta)) / (theta * theta)) * K
             + ((theta - std::sin(theta)) / (theta * theta * theta)) * K * K;
    }
```

The series I − K/2 + K²/6 drops the term (θ²/24)K, of size below 4.2e-20 for θ < 1e-6. Just above the threshold the closed form is less accurate than it looks.

The coefficient (1 − cos θ)/θ² multiplies K, which has size θ, not θ². Its cancellation error of about 1e-16/θ² therefore reaches the result as about 1e-16/θ. Against a long double reference the worst `Jr` error is about 5e-11, just above θ = 1e-6 (4.4e-11 at θ = 1.01e-6 along (1, 2, 3)/√14; 5.1e-11 over 20 random axes); at θ = 1e-3 it is 6.3e-15.

The identity 1 − cos θ = 2 sin²(θ/2) has no cancellation: at θ = 1.1e-6 it gives 0.49999999999995 where the code's form gives 0.49996738. The 5e-11 error is harmless for the controller, but it is the largest error of the SO(3) functions; the next largest is `logSO3` just below its near-π switch (4.9e-12).

```cpp
// src/se3.cpp:84-96
    Matrix3d JrInv(const Vector3d &w)
    {
        const double theta = w.norm();
        const Matrix3d K = hat(w);

        // small angles: 1/theta^2 - (1 + cos(theta)) / (2 theta sin(theta)) ~ 1/12
        if (theta < 1e-6)
            return Matrix3d::Identity() + 0.5 * K + (1.0 / 12.0) * K * K;

        return Matrix3d::Identity()
             + 0.5 * K
             + (1.0 / (theta * theta) - (1.0 + std::cos(theta)) / (2.0 * theta * std::sin(theta))) * K * K;
    }
```

`JrInv` has a similar cancellation that does no harm. At θ = 1.1e-6, just above the switch, the K² coefficient comes out 0.08313 instead of 1/12 = 0.08333, but it multiplies K² of size θ² ≈ 1.2e-12. The K term is exactly ½K, so the worst measured matrix error over θ ∈ [1e-8, 1e-2] stays at about 4e-16.

- Near π the coefficient is finite: (1 + cos θ)/sin θ = cot(θ/2) → 0, so `JrInv(π e₁)` has entries up to π/2 = 1.571.
- At |ω| = 2π, J_r is singular and `JrInv` returns entries of 2.6e16. The library calls `JrInv` only on a logarithm, with |ω| ≤ π (`GammaInv` at `src/tube.cpp:253`), and on one integrator step's rotation, which is tiny (`src/rigid_body.cpp:105`), so it never asks near 2π.

### se3.cpp: hat and vee on R⁶

These are the se(3) versions: ζ̂ = [ω̂ v; 0 0] and its inverse.

```cpp
// src/se3.cpp:98-112
    Matrix4d hat(const Vec6 &z)
    {
        Matrix4d X = Matrix4d::Zero();
        X.block<3,3>(0,0) = hat(Vector3d(z.head<3>()));
        X.block<3,1>(0,3) = z.tail<3>();
        return X;
    }

    Vec6 vee(const Matrix4d &g)
    {
        Vec6 z = Vec6::Zero();
        z.head<3>() = vee(Matrix3d(g.block<3,3>(0,0)));
        z.tail<3>() = g.block<3,1>(0,3);
        return z;
    }
```

- `z.head<3>()` and `z.tail<3>()` are fixed-size views of the first and last three entries. The `<3>` is a template argument, so the size is known at compile time and the view itself copies nothing.
- `hat(Vector3d(z.head<3>()))` converts explicitly for the same reason as in `logSO3`. `hat` has a `Vector3d` and a `Vec6` overload, and a call with the bare view is ambiguous (verified with g++).
- `X.block<3,3>(0,0)` is a writable 3 × 3 view starting at row 0, column 0. Assigning to it writes into X.
- The 4 × 4 `vee` ignores the bottom row, so it returns the twist of any matrix with the se(3) layout.

### se3.hpp and se3.cpp: poses and the inverse

A pose is a 4 × 4 homogeneous matrix. `makePose` assembles it, `rotation` and `translation` read its blocks, and `inverse` inverts it in closed form.

```cpp
// include/se3pf/se3.hpp:19-22
    Pose makePose(const Matrix3d& R, const Vector3d& p);
    inline Matrix3d rotation(const Pose& g) { return g.block<3, 3>(0, 0); }     // R of g = (R, p)
    inline Vector3d translation(const Pose& g) { return g.block<3, 1>(0, 3); }  // p of g = (R, p)
    Pose inverse(const Pose& g);        // (R^T, -R^T p), in closed form
```

`rotation` and `translation` are defined in the header, so they are marked `inline`. That keyword allows one identical definition in every `.cpp` that includes the header; without it the linker reports a multiple-definition error.

```cpp
// src/se3.cpp:114-129
    Pose makePose(const Matrix3d &R, const Vector3d &p)
    {
        Pose g = Pose::Identity();

        g.block<3,3>(0,0) = R;
        g.block<3,1>(0,3) = p;

        return g;
    }

    Pose inverse(const Pose &g)
    {
        const Matrix3d Rt = g.block<3,3>(0,0).transpose();
        const Vector3d p = g.block<3,1>(0,3);
        return makePose(Rt, -Rt * p);
    }
```

- `makePose` starts from `Pose::Identity()`, so the bottom row is exactly (0, 0, 0, 1).
- `inverse` uses g⁻¹ = (Rᵀ, −Rᵀp): one transpose and one matrix-vector product. Eigen's general `Matrix4d::inverse()` computes the cofactors of all 16 entries and divides by the determinant; the test compares the two to 8.9e-16.

### se3.cpp: ad and Ad

`ad(z)` is the matrix of the Lie bracket b ↦ [z, b]; `Ad(g)` is the matrix of ζ ↦ (gζ̂g⁻¹)^∨. Both use the (ω, v) block order.

```cpp
// src/se3.cpp:131-155
    Mat6 ad(const Vec6 &z)
    {
        const Vector3d w = z.head<3>();
        const Vector3d v = z.tail<3>();

        Mat6 A = Mat6::Zero();
        A.block<3,3>(0,0) = hat(w);
        A.block<3,3>(3,3) = hat(w);
        A.block<3,3>(3,0) = hat(v);

        return A;
    }

    Mat6 Ad(const Pose &g)
    {
        const Matrix3d R = g.block<3,3>(0,0);
        const Vector3d p = g.block<3,1>(0,3);

        Mat6 A = Mat6::Zero();
        A.block<3,3>(0,0) = R;
        A.block<3,3>(3,3) = R;
        A.block<3, 3>(3, 0) = hat(p) * R;

        return A;
    }
```

- In (ω, v) order, the coupling block sits lower-left: v̂ in `ad`, p̂R in `Ad`. In Murray–Li–Sastry's (v, ω) order it sits upper-right; copying a formula from that book without reordering is the classic bug here.
- `Ad` is used at `src/tube.cpp:253` and `src/tube.cpp:330` (moving ζ_γ into the frame of g_err or Exp_I(Nξ)) and at `src/panda.cpp:66` (J_b = Ad_{g⁻¹}J_s).
- `ad` is not called by the library. It is tested and kept for the geodesic ODE of a general W.

### metric.hpp: the class

`Metric` is a class: it holds W privately and exposes only the operations the paper uses.

```cpp
// include/se3pf/metric.hpp:9-33
    class Metric {
        public:
            // Throws std::invalid_argument unless W = diag(wR, wR, wR, wp, wp, wp) with wR > 0 and wp > 0 (to a
            // relative 1e-12).
            explicit Metric(const Mat6& W);
            static Metric product(double wR, double wp);

            double inner(const Vec6& v, const Vec6& w) const;       // <v, w>_W = v^T W w
            Vec6 flat(const Vec6& v) const;                         // flat map: W v, the covector <v, .>_W
            double norm(const Vec6& v) const;                       // |v|_W
            const Mat6& matrix() const { return W_; }

            // Shorthands for inner and flat: W(v, w) = W.inner(v, w), W(v) = W.flat(v). The named forms read better.
            double operator()(const Vec6& v, const Vec6& w) const { return inner(v, w); }
            Vec6 operator()(const Vec6& v) const { return flat(v); }

            Pose Exp(const Vec6& z) const;                          // Exp_I
            bool Log(const Pose& g, Vec6& z) const;                 // Log_I; false if the rotation angle is pi
            Mat6 Gamma(const Vec6& z) const;                        // derivative of Exp_I (eq:Gamma)
            Mat6 GammaInv(const Vec6& z) const;
            double distance(const Pose& g1, const Pose& g2) const;  // |Log_I(g1^-1 g2)|_W (eq:dist); NaN if Log fails

        private:
            Mat6 W_;
    };
```

- `public:` members are the interface; `private:` `W_` can be read only by member functions. Callers get W through `matrix()`, which returns a `const Mat6&`, a read-only reference without a copy.
- The `const` after a member function's parameter list promises that the function does not modify the object. Only such functions can be called on a `const Metric`. `Tube` stores its own copy (`Metric metric_;`, `include/se3pf/tube.hpp:94`), and inside `Tube`'s `const` member functions such as `Psi` that copy is `const`, so `metric_.Exp` must be `const` to be callable there.
- `explicit` forbids silent conversion from `Mat6` to `Metric`. Without it, passing a named `Mat6` where a `const Metric&` is expected would construct a temporary `Metric`, and possibly throw, at the call site.
- `static Metric product(double, double)` is a static member function: it needs no object and is called as `Metric::product(0.01, 1.0)`. It is a named constructor for the common case.
- `operator()` is overloaded twice, so `W(v, w)` and `W(v)` read like the paper's notation.

### metric.cpp: the constructor and product

The constructor stores W and refuses every W that is not diag(w_R I, w_p I) with w_R, w_p > 0.

```cpp
// src/metric.cpp:10-28
    // Only the product type has the closed forms below. A W that is not, e.g. diag(1, 1, 2, 1, 1, 1), would be
    // accepted by everything else and silently give the wrong geodesics, so refuse it here.
    Metric::Metric(const Mat6& W) : W_(W)
    {
        const double wR = W(0, 0), wp = W(3, 3);
        Mat6 P = Mat6::Zero();
        P.diagonal() << wR, wR, wR, wp, wp, wp;
        if (!(wR > 0.0) || !(wp > 0.0) || !W.allFinite() || (W - P).cwiseAbs().maxCoeff() > 1e-12 * std::max(wR, wp))
            throw std::invalid_argument("Metric: only the product type W = diag(wR I, wp I), wR, wp > 0, is "
                                        "implemented (Example 1)");
    }

    Metric Metric::product(double wR, double wp)
    {
        Mat6 W = Mat6::Identity();
        W.diagonal().head<3>() *= wR;
        W.diagonal().tail<3>() *= wp;
        return Metric(W);
    }
```

- `: W_(W)` is the member initializer list: `W_` is constructed from `W` before the body runs. If the body then throws, the object never exists, so a non-product `Metric` cannot be observed.
- `!(wR > 0.0)` is written instead of `wR <= 0.0` because every comparison with NaN is false. `wR <= 0.0` would let a NaN through; `!(wR > 0.0)` rejects it.
- `!W.allFinite()` catches NaN or infinity in any entry. It comes before the `maxCoeff` check, whose result is unspecified when NaN is present, and `||` stops at the first true condition. It is needed even for an infinite w_R: the tolerance 1e-12 · max(w_R, w_p) would then be infinite, and the last check could never fire.
- The tolerance is relative, 1e-12 · max(w_R, w_p): 1e-12 absolute for both examples. A change of 1e-15 (rounding) passes; a change of 1e-9 throws (both tested).
- `std::invalid_argument` comes from `<stdexcept>`. Construction is offline, where throwing is the project's way to report a bad input.

`product` scales the two halves of the identity's diagonal: `W.diagonal()` is a writable view of the diagonal, and `head<3>()` its first three entries. It then calls the checking constructor, so `Metric::product(0.0, 1.0)` throws too.

### metric.cpp: inner, flat, norm

These three are the inner product, the flat map and the norm of W.

```cpp
// src/metric.cpp:30-43
    double Metric::inner(const Vec6 &v, const Vec6 &w) const
    {
        return v.dot(W_ * w);
    }

    Vec6 Metric::flat(const Vec6 &v) const
    {
        return W_ * v;
    }

    double Metric::norm(const Vec6 &v) const
    {
        return std::sqrt(inner(v, v));
    }
```

`inner` computes vᵀ(Ww) with a full 6 × 6 product, although the product type would allow w_R ωᵀω′ + w_p vᵀv′. The general form costs 36 multiplications for Ww plus 6 for the dot product, and keeps the interface ready for a general W.

### metric.cpp: Exp

`Exp` is Exp_I of Example 1: rotate by exp(ω̂) and translate by v.

```cpp
// src/metric.cpp:45-51
    // Example 1: Exp_I(z) = (exp(hat(omega)), v). The translation is v itself, not the screw motion's J_l(omega) v.
    Pose Metric::Exp(const Vec6 &z) const
    {
        const Vector3d w = z.head<3>();
        const Vector3d v = z.tail<3>();
        return makePose(expSO3(w), v);
    }
```

The geodesic t ↦ Exp_I(tζ) = (exp(tω̂), tv) moves the position on a straight line while the attitude turns. That is because the product-type metric w_R‖RᵀṘ‖² + w_p‖ṗ‖² is the product metric of SO(3) × R³, whose geodesics are products of geodesics.

### metric.cpp: Log

`Log` inverts `Exp` and returns `false` when the rotation angle is too close to π.

```cpp
// src/metric.cpp:53-62
    // Example 1: Log_I(g) = (log(R), p) when tr(R) != -1, i.e. rotation angle below pi.
    bool Metric::Log(const Pose &g, Vec6 &z) const
    {
        const Matrix3d R = g.block<3,3>(0,0);
        if (R.trace() < -1.0 + 1e-12)  // angle pi: two minimizing geodesics, no unique logarithm
            return false;
        z.head<3>() = logSO3(R);
        z.tail<3>() = g.block<3,1>(0,3);
        return true;
    }
```

Since tr R = 1 + 2 cos θ, tr R + 1 = 2(1 − cos(π − θ)) ≈ (π − θ)². The guard tr R < −1 + 1e-12 therefore refuses every angle with π − θ below 1e-6; at exactly 1e-6 the rounding of the trace decides. Measured on rotations exp((π − d)n):

| π − θ | tr R + 1 | `Log` |
| --- | --- | --- |
| 1e-5 | 1.0e-10 | true |
| 1.01e-6 | 1.02e-12 | true |
| 1e-6 | 1.000e-12, ± 2e-15 by axis | true for 592 of 1000 random axes (true about e₁) |
| 0.99e-6 | 9.8e-13 | false |

At θ = π there are two minimizing geodesics (axis +n and −n), so Log_I is not defined there. The margin keeps e_g away from that jump. On failure `z` is left unchanged, and the bool return tells the caller not to read it.

### metric.cpp: Gamma and GammaInv

`Gamma(z)` is the body-coordinate derivative of Exp_I at z (eq:Gamma); `GammaInv` is its inverse, block by block.

```cpp
// src/metric.cpp:64-81
    // Example 1: Gamma(z) = diag(Jr(omega), exp(hat(omega))^T).
    Mat6 Metric::Gamma(const Vec6 &z) const
    {
        const Vector3d w = z.head<3>();
        Mat6 G = Mat6::Zero();
        G.block<3,3>(0,0) = Jr(w);
        G.block<3,3>(3,3) = expSO3(w).transpose();
        return G;
    }

    Mat6 Metric::GammaInv(const Vec6 &z) const
    {
        const Vector3d w = z.head<3>();
        Mat6 G = Mat6::Zero();
        G.block<3,3>(0,0) = JrInv(w);
        G.block<3,3>(3,3) = expSO3(w);
        return G;
    }
```

The rotation block is J_r(ω) by the definition of J_r. The translation block is exp(ω̂)ᵀ: moving z along δ moves the position by δ_v in space, and the body velocity is Rᵀδ_v. The inverse blocks are J_r(ω)⁻¹ and exp(ω̂), since the inverse of a rotation is its transpose.

### metric.cpp: distance

`distance` is ‖Log_I(g₁⁻¹g₂)‖_W (eq:dist), or NaN when Log_I fails.

```cpp

The tube-radius test at `src/tube.cpp:368` writes `!(W.distance(gp, g) >= limit)` instead, so there a NaN counts as closer, the safe side for a radius estimate.

### path.hpp: the interface

`Path` is an abstract base class with four pure virtual functions; each curve is a subclass.

```cpp
// include/se3pf/path.hpp:12-19
    class Path {
        public:
            virtual ~Path() = default;
            virtual double length() const = 0;              // L
            virtual Pose pose(double s) const = 0;          // gamma(s)
            virtual Vec6 velocity(double s) const = 0;      // zeta_gamma(s), unit W-norm
            virtual Vec6 acceleration(double s) const = 0;  // zeta_gamma'(s)
    };
```

- `virtual` makes a call through a `Path&` run the subclass's version, chosen at run time through a table of function pointers (the vtable).
- `= 0` makes a function pure virtual: `Path` has no implementation and cannot be instantiated, only subclassed.
- `virtual ~Path() = default;` makes deleting a subclass through a `Path*` (or `std::unique_ptr<Path>`) run the subclass's destructor. Without it that delete is undefined behaviour. g++ `-Wall` warns about a raw `delete` through the base pointer (`-Wdelete-non-virtual-dtor`), but not when the delete happens inside `std::unique_ptr<Path>` (checked with g++ 11).

### path.cpp: the helpers

The helpers live in an unnamed namespace, so they are invisible outside `path.cpp`.

```cpp
// src/path.cpp:10-23
    namespace {
        // Rotation by th about the z-axis.
        Matrix3d Rz(double th)
        {
            return expSO3(Vector3d(0.0, 0.0, th));
        }

        // Stack (omega, v) into a twist.
        Vec6 twist(const Vector3d &w, const Vector3d &v)
        {
            Vec6 z;
            z << w, v;
            return z;
        }
```

- `namespace { ... }` gives its contents internal linkage: the linker never sees them. If another `.cpp` of the library also defined `se3pf::twist(const Vector3d&, const Vector3d&)` with external linkage, the link would fail with a duplicate symbol. Six of the nine `src/*.cpp` files keep their helpers this way.
- `z << w, v;` is Eigen's comma initializer: it fills `z` with the entries of `w` and then those of `v`.

```cpp
// src/path.cpp:25-38
        // Speed sigma = |zeta~(0)|_W, checked to be constant along the curve: the s <-> theta conversion below
        // assumes it. Both curves have constant speed in every product-type W (the only kind Metric accepts), so
        // this is a safeguard for a new curve or a future general W.
        template <class BodyVelocity>
        double constantSpeed(const BodyVelocity &zetaTilde, const Metric &W)
        {
            const double sigma = W.norm(zetaTilde(0.0));
            for (int k = 1; k < 16; ++k) {
                const double th = 2.0 * EIGEN_PI * k / 16.0;
                if (std::abs(W.norm(zetaTilde(th)) - sigma) > 1e-12 * sigma)
                    throw std::invalid_argument("Path: the speed is not constant in this metric");
            }
            return sigma;
        }
```

`constantSpeed` computes σ = ‖ζ̃(0)‖_W and checks it at 15 more angles θ_k = 2πk/16 to a relative 1e-12. If any differs, s = σθ would not be arc length, so it throws `std::invalid_argument`.

- `template <class BodyVelocity>` makes it a function template: it accepts any callable taking a `double` and returning a `Vec6`. A lambda has a unique unnamed type, so accepting one takes a template or a type-erased `std::function`.
- With today's `Metric`, this check cannot fail: |ω̃| and |ṽ| = r are constant for both curves, so ‖ζ̃‖_W is constant for every product-type W. It is a safeguard for a new curve or a future general W.
- It does not reject σ = 0. A coning circle with r = 0 and α = 0 is a point: it builds with L = 0, and `velocity` then returns NaN (measured).

### path.cpp: ConingCircle

The coning circle stores R₀, A = exp(αê₁), the center p₀ (`c_`), w₀, r and σ.

```cpp
// include/se3pf/path.hpp:21-36
    // Panda example: R = R0 Rz(th) A Rz(-th), A = exp(cone * e1^), p = center + r (cos th, sin th, 0)
    class ConingCircle final : public Path {
        public:
            ConingCircle(const Matrix3d& R0, const Vector3d& center, double radius, double cone, const Metric& W);
            double length() const override;
            Pose pose(double s) const override;
            Vec6 velocity(double s) const override;
            Vec6 acceleration(double s) const override;

        private:
            Matrix3d attitude(double th) const;   // R(theta), shared by the three functions above
            Matrix3d R0_, A_;
            Vector3d c_, w0_;                     // w0 = A^T e3 - e3
            double r_;
            double sigma_;                        // constant speed in the metric: s = sigma * theta
    };
```

- `final` forbids further subclasses. The compiler may then resolve a call on a `ConingCircle` directly, without the vtable.
- `override` asks the compiler to check that the function really overrides a base virtual. A typo in the signature (say, a missing `const`) then fails to compile instead of declaring a new, never-called function.
- `attitude` is private: it is shared by `pose`, `velocity` and `acceleration` but is not part of the `Path` interface.

```cpp
// src/path.cpp:45-55
    ConingCircle::ConingCircle(const Matrix3d &R0, const Vector3d &center, double radius, double cone,
                               const Metric &W)
        : R0_(R0), A_(expSO3(Vector3d(cone, 0.0, 0.0))), c_(center), r_(radius)
    {
        w0_ = A_.transpose() * Vector3d::UnitZ() - Vector3d::UnitZ();
        auto zetaTilde = [this](double th) {
            const Vector3d pd = r_ * Vector3d(-std::sin(th), std::cos(th), 0.0);
            return twist(Rz(th) * w0_, attitude(th).transpose() * pd);
        };
        sigma_ = constantSpeed(zetaTilde, W);
    }
```

- The initializer list builds `R0_`, `A_`, `c_` and `r_` in declaration order. `w0_` is assigned in the body, before the lambda first runs.
- `[this](double th) { ... }` is a lambda that captures the object's `this` pointer, so it can call `attitude` and read `r_` and `w0_`. It computes ζ̃(θ), the θ-velocity, which is `velocity` times σ.
- `auto zetaTilde = ...` is the right use of `auto`: a lambda's type has no name. The project's "no `auto`" rule (`docs/DESIGN.md:41`) is about Eigen results, where `auto` would store an unevaluated expression.
- The `Metric` is used only here, to compute σ; the path does not store it. A tube must be built with the same metric as its path, or ζ_γ is not unit speed in the tube's W.

```cpp
// src/path.cpp:57-71
    double ConingCircle::length() const
    {
        return 2.0 * EIGEN_PI * sigma_;
    }

    Matrix3d ConingCircle::attitude(double th) const
    {
        return R0_ * Rz(th) * A_ * Rz(-th);
    }

    Pose ConingCircle::pose(double s) const
    {
        const double th = s / sigma_;
        return makePose(attitude(th), c_ + r_ * Vector3d(std::cos(th), std::sin(th), 0.0));
    }
```

- `length` is 2πσ. `EIGEN_PI` is long double, so the product is computed in long double and rounded to double on return.
- `pose` converts s to θ = s/σ and never wraps it: cos and sin are periodic, so `pose(-0.1)` equals `pose(L - 0.1)` to 1.3e-16 or better on all three test paths (0 on the Panda path, measured).
- `attitude` costs two `expSO3` calls and three 3 × 3 products.

```cpp
// src/path.cpp:73-91
    Vec6 ConingCircle::velocity(double s) const
    {
        const double th = s / sigma_;
        const Vector3d pd = r_ * Vector3d(-std::sin(th), std::cos(th), 0.0);  // dp/dtheta
        return twist(Rz(th) * w0_, attitude(th).transpose() * pd) / sigma_;
    }

    Vec6 ConingCircle::acceleration(double s) const
    {
        const double th = s / sigma_;
        const Matrix3d R = attitude(th);
        const Vector3d w = Rz(th) * w0_;                                 // omega~
        const Vector3d dw = Rz(th) * Vector3d::UnitZ().cross(w0_);       // d omega~ / d theta
        const Vector3d pd = r_ * Vector3d(-std::sin(th), std::cos(th), 0.0);
        const Vector3d pdd = -r_ * Vector3d(std::cos(th), std::sin(th), 0.0);
        const Vector3d v = R.transpose() * pd;                           // v~
        const Vector3d dv = R.transpose() * pdd - w.cross(v);            // d v~ / d theta
        return twist(dw, dv) / (sigma_ * sigma_);
    }
```

`velocity` returns ζ̃(θ)/σ; `acceleration` returns ζ̃′(θ)/σ². The derivative of ω̃ = R_z(θ)w₀ is R_z(θ)ê₃w₀ = R_z(θ)(e₃ × w₀), which is line 85.

Line 89 is the term that is easy to drop: ṽ′ = Rᵀp″ − ω̃ × ṽ. It comes from differentiating Rᵀ, which turns with the body. Along the Panda path the norm of ω̃ × ṽ/σ² reaches 1.99, against 8.47 for the whole translational part of ζ_γ′.

### spline.hpp: build

`PeriodicHermite<T>` is a class template: the compiler generates one class per type `T` it is used with (`double`, `Vec7`, `Mat65`).

```cpp
// include/se3pf/spline.hpp:16-31
    template <class T>
    class PeriodicHermite {
        public:
            // n + 1 samples; sample n must repeat sample 0 (it is overwritten with it, so the spline closes exactly).
            void build(double L, std::vector<T> y, std::vector<T> dy)
            {
                if (!(L > 0.0) || y.size() < 2 || dy.size() != y.size())
                    throw std::invalid_argument("PeriodicHermite: need L > 0 and n + 1 >= 2 values and derivatives");
                n_ = static_cast<int>(y.size()) - 1;
                L_ = L;
                h_ = L / n_;
                y_ = std::move(y);
                dy_ = std::move(dy);
                y_[n_] = y_[0];
                dy_[n_] = dy_[0];
            }
```

- `y` and `dy` are taken by value and then moved into the members. A caller that passes `std::move(Y)` (`src/tube.cpp:210`) hands over its buffer without a copy; a caller that passes a named vector gets a copy and keeps its own.
- `std::move` only marks an object as "may be emptied"; the vector's move assignment then takes over the buffer. After line 27 the parameter `y` is valid but unspecified (in practice empty), and the code never reads it again.
- `!(L > 0.0)` rejects NaN as well as L ≤ 0. Fewer than two values, or mismatched sizes, also throw `std::invalid_argument`.
- Lines 29-30 overwrite node n with node 0, so the spline closes exactly whatever the caller computed at s = L.

### spline.hpp: eval

`eval` finds the interval of s, computes t ∈ [0, 1], and combines the four Hermite basis polynomials.

```cpp
// include/se3pf/spline.hpp:33-54
            // y = interpolant at s; if dy is not null, *dy = its derivative with respect to s. Online: no allocation,
            // no exceptions. A non-finite s gives NaN in every entry of y and *dy (the weights below are NaN), never
            // an out-of-range node index. Call build first (checked by an assert in Debug builds).
            void eval(double s, T &y, T *dy = nullptr) const
            {
                assert(n_ > 0 && "PeriodicHermite::eval before build");
                const bool finite = std::isfinite(s);
                double x = finite ? std::fmod(s, L_) : 0.0;  // in (-L, L)
                if (x < 0.0)
                    x += L_;
                int k = static_cast<int>(x / h_);
                if (k >= n_)  // rounding can land exactly on L
                    k = n_ - 1;
                const double t = finite ? x / h_ - k : std::numeric_limits<double>::quiet_NaN();
                const double t2 = t * t, t3 = t2 * t;

                y = (2 * t3 - 3 * t2 + 1) * y_[k] + ((t3 - 2 * t2 + t) * h_) * dy_[k]
                  + (-2 * t3 + 3 * t2) * y_[k + 1] + ((t3 - t2) * h_) * dy_[k + 1];
                if (dy != nullptr)
                    *dy = ((6 * t2 - 6 * t) / h_) * y_[k] + (3 * t2 - 4 * t + 1) * dy_[k]
                        + ((-6 * t2 + 6 * t) / h_) * y_[k + 1] + (3 * t2 - 2 * t) * dy_[k + 1];
            }
```

1. `assert(n_ > 0 && "...")` stops a Debug build if `build` was never called. A string literal is a non-null pointer and so is true; `&&` leaves the condition unchanged and puts the message in the failure text. With `NDEBUG` (Release) the assert disappears.
2. `std::fmod(s, L_)` returns a remainder with the sign of s, in (−L, L). Adding L to a negative remainder puts x in [0, L].
3. `static_cast<int>(x / h_)` truncates toward zero, which is the floor for x ≥ 0.
4. The clamp handles x = L. For s = −1e-17 with L = 0.77 and n = 100, fmod gives −1e-17, adding L rounds to exactly L, and x/h is exactly 100 = n. The clamp gives k = n − 1 and t = 1, so eval returns node n, which is node 0 (measured: bit for bit).
5. The weights are the Hermite basis at t. The derivative weights carry 1/h on the value terms; the slope terms need none, because h·y′_k times 1/h is y′_k.

The NaN guard matters because `static_cast<int>` of NaN or infinity is undefined behaviour; on x86 it gives INT_MIN, and `y_[k]` would read far outside the vector. With the guard, x = 0 and k = 0 are valid, and t = NaN makes every weight NaN. NaN times any finite value is NaN, so every entry of y and *dy is NaN, which the callers' `allFinite` checks catch.

- `T *dy = nullptr` is an optional output with a default argument. Callers that need only the value write `eval(s, y)`; the derivative costs nothing then.
- The only operations used on `T` are scalar times `T` and `T + T`, so any fixed-size Eigen type works. Each weight is a scalar computed first, inside parentheses, so every term costs one scalar-times-`T` product.
- For Eigen types, the whole right side of line 49 is one expression evaluated straight into `y`: no temporaries and no heap allocation.

### spline.hpp: centralDifferences, accessors and storage

`centralDifferences` estimates node derivatives from node values with the fourth-order periodic stencil.

```cpp
// include/se3pf/spline.hpp:56-78
            double length() const { return L_; }
            int intervals() const { return n_; }

            // Fourth-order periodic central differences of node values y_0..y_n (y_n = y_0) on the grid of length L:
            // y'_k ~ (y_{k-2} - 8 y_{k-1} + 8 y_{k+1} - y_{k+2}) / (12 h). For q*' and X' at the lift's nodes.
            static std::vector<T> centralDifferences(const std::vector<T> &y, double L)
            {
                const int n = static_cast<int>(y.size()) - 1;
                if (n < 4)
                    throw std::invalid_argument("PeriodicHermite::centralDifferences: need at least 5 samples");
                const double h = L / n;
                auto at = [&](int k) -> const T & { return y[((k % n) + n) % n]; };
                std::vector<T> d(y.size());
                for (int k = 0; k < n; ++k)
                    d[k] = (1.0 / (12.0 * h)) * (at(k - 2) - 8.0 * at(k - 1) + 8.0 * at(k + 1) - at(k + 2));
                d[n] = d[0];
                return d;
            }

        private:
            double L_ = 1.0, h_ = 1.0;
            int n_ = 0;
            std::vector<T> y_, dy_;
```

- `length()` and `intervals()` return L and n. Nothing in the project calls them today; they are accessors for diagnostics.
- `static` means it needs no `PeriodicHermite` object: `src/lift.cpp:177` calls `PeriodicHermite<Vec7>::centralDifferences(Q, L_)`.
- `((k % n) + n) % n` wraps an index into [0, n). C++'s `%` keeps the sign of the left operand, so −1 % n is −1, not n − 1.
- The lambda `at` captures everything by reference (`[&]`) and declares its return type `-> const T &`. Without the trailing return type, a lambda deduces its return type like `auto` and would return a copy of each `Mat65`.
- Only nodes 0 to n − 1 are read, since node n repeats node 0; `d[n] = d[0]` closes the result.
- n < 4 throws, so n = 4 (five samples) is accepted. At n = 4 the outer points k − 2 and k + 2 are the same node, their terms cancel, and the stencil degenerates to (y_{k+1} − y_{k−1})/(1.5h), 4/3 times the ordinary central difference (measured: 5.33 for f = sin 2πs at s = 0, where f′ = 6.28). Five distinct nodes need n ≥ 5. The lift uses n = 2000, so this edge is never reached.

The defaults `L_ = 1.0, h_ = 1.0, n_ = 0` make an unbuilt spline trip the assert in Debug. In Release, `eval` on an unbuilt spline computes k = 0, clamps it to n − 1 = −1 and reads out of range, so calling `build` first is the caller's duty.
