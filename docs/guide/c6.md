## The tests

The 45 test cases of this part check three kinds of claim. Each formula is the derivative or the law it claims to be (finite differences, recomputed values); each failure path returns false without side effects; the closed loops reproduce the paper's numbers. Each entry below says what a test proves and which bug it would catch.

### Catch2 in five lines

- `TEST_CASE("name", "[tag]")` defines a test; `SECTION` splits one into parts that each run from the top.
- `REQUIRE(x)` stops the test case on failure; `CHECK(x)` records the failure and continues. `CHECK_THAT(x, WithinAbs(v, tol))` compares a double with an absolute tolerance.
- `CAPTURE(a, b)` prints the values if a later check fails; the tests wrap small errors in `sci(...)` (`tests/test_helpers.hpp:71-76`) so 3e-12 does not print as 0.0000000000.
- `STATIC_REQUIRE(expr)` is a compile-time check: if `expr` is false, the test file does not compile.
- A tag that starts with a dot (`"[.timing]"`, `"[.slow]"`) hides the test from the default run.

The random inputs come from `testing::randn` and `testing::uniform` (`tests/test_helpers.hpp:53-67`), and `tests/rng_listener.cpp` reseeds the generator with 12345 before every run of a test case (each leaf `SECTION`). A failing test therefore fails identically when run alone.

```bash
./build-ci-release/tests "Controller*"            # the 19 test cases whose names start with Controller
./build-ci-release/tests "RigidBody*,simulate:*"  # the 18 rigid-body and rigid-body-example test cases
./build-ci-release/tests "[.timing]"              # the 5 timing tests of the program (Release only)
./build-ci-release/tests "Controller<RigidBody>: step returns*" -s   # -s prints every check with its captured numbers
./build-ci-debug/tests "[slow]"                   # the hidden 20 s loops in Debug (slow)
```

### The infrastructure of test_controller.cpp

The file replaces the global `operator new` of the whole test program, so it can count every allocation:

```cpp
// tests/test_controller.cpp:46-58
namespace {
    // Atomic: a test may allocate on a thread of its own (started with std::async, say), and unsynchronized
    // increments of a plain long from two threads would be a data race. Relaxed order is enough for a counter.
    std::atomic<long> gNewCalls{0};
}

void* operator new(std::size_t size)
{
    gNewCalls.fetch_add(1, std::memory_order_relaxed);
    if (void* p = std::malloc(size == 0 ? 1 : size))
        return p;
    throw std::bad_alloc();
}
```

```cpp
// tests/test_controller.cpp:60-72
void* operator new(std::size_t size, std::align_val_t alignment)
{
    gNewCalls.fetch_add(1, std::memory_order_relaxed);
    const std::size_t a = static_cast<std::size_t>(alignment);
    if (void* p = std::aligned_alloc(a, (size + a - 1) / a * a))  // the size must be a multiple of the alignment
        return p;
    throw std::bad_alloc();
}

void operator delete(void* p) noexcept { std::free(p); }
void operator delete(void* p, std::size_t) noexcept { std::free(p); }
void operator delete(void* p, std::align_val_t) noexcept { std::free(p); }
void operator delete(void* p, std::size_t, std::align_val_t) noexcept { std::free(p); }
```

- Defining `operator new(std::size_t)` at global scope replaces the library's version for the entire program: every `new`, in every test file and inside `std::vector` or `std::function`, now goes through it. Only the difference of the counter across a window matters.
- `std::atomic<long>` makes the increment safe if another thread allocates at the same time; `memory_order_relaxed` is enough because nothing else is ordered by the counter.
- `size == 0 ? 1 : size`: `new` must return a unique pointer even for zero bytes, and `malloc(0)` may return null.
- The aligned form (C++17 `std::align_val_t`) serves over-aligned types. `std::aligned_alloc` requires the size to be a multiple of the alignment, hence the rounding.
- All four `operator delete` forms are replaced too, so memory from the new `operator new` (which comes from `malloc`) is always released with `free`.

The fixtures (`tests/test_controller.cpp:76-338`) are designed so that a wrong term cannot hide:

- `oddGains()` (95-106) gives the seven gains the values 11, 7, 3, 5, 2, 13, 3, so a gain used in the wrong law changes the result. Only k_t and K_d,β share a value (3), so a swap of those two would go unseen.
- `velocityTest` (110-127) uses ν_d(t, η) = 0.4 + 0.1 sin t + 0.05 cos(2πη/L), so ∂ν_d/∂t and ∂ν_d/∂η are both nonzero; `positionTest` (130-141) uses η_d(t) = 1 + 0.3t + 0.2 sin t, which is past L at t = 40 (η_d(40) = 13.15, L = 10.88 on the rigid tube).
- `screw` (156-161) is a second curve through g with velocity ζ, and `curve` is overloaded for `Pose` and `Vec7` (163-164): overload resolution picks the right one from the argument type.
- `ybar` (166-179) returns ȳ with η measured relative to a reference point by `arcDiff` (`tests/test_helpers.hpp:118-126`), a deliberately separate rewrite of `wrapSymmetric`, so the tests do not share code with what they check.
- `expectedMu` (221-237) recomputes μ from the `Status` and the reference formulas.

The independent Ȧq̇ is a fourth-order difference along the other curve:

```cpp
// tests/test_controller.cpp:181-200
    // Adot qdot by a fourth-order central difference along curve(), not along System::retract:
    // (-A(2h) + 8 A(h) - 8 A(-h) + A(-2h)) qdot / 12h, independent of the controller's own second-order difference.
    // The frame spline N(s) is only C^1: N'' jumps at the grid nodes, and so does the derivative of A along the
    // motion. A stencil that spans a node mixes the two one-sided values (an error up to about 1e-6), so h is small
    // (the stencil moves eta by about 4h eta_dot) and the tests put eta well inside a grid interval.
    template <class System>
    Vec<System::kDof> adotQdot(const Controller<System>& c, const typename System::Config& q,
                               const Vec<System::kDof>& dq, double eta)
    {
        constexpr int n = System::kDof;
        const double h = 1e-4;
        Mat<n, n> sum = Mat<n, n>::Zero();
        const double steps[4] = {-2.0, -1.0, 1.0, 2.0}, weights[4] = {1.0, -8.0, 8.0, -1.0};
        for (int i = 0; i < 4; ++i) {
            typename Controller<System>::OutputState o;
            REQUIRE(c.outputs(curve(q, dq, steps[i] * h), eta, o));
            sum += weights[i] * o.A;
        }
        return (sum * dq) / (12.0 * h);
    }
```

It differs from the controller's computation in the stencil (fourth order with h = 1e-4, instead of second order with h = 1e-5) and, for the rigid body, also in the curve (screw instead of `retract`; for the Panda both curves are q + h q̇). Both start their projections from the projected η. Agreement therefore means the controller's Ȧq̇ is right, not merely self-consistent.

The Jacobian check is the finite-difference test of eq:A:

```cpp
// tests/test_controller.cpp:202-219
    // A is the Jacobian of ybar (eq:A): (ybar(retract(q, w, h)) - ybar(retract(q, w, -h))) / 2h = A w for random w.
    template <class System>
    void checkJacobian(const Controller<System>& c, const typename System::Config& q, double guess, double scale)
    {
        constexpr int n = System::kDof;
        typename Controller<System>::OutputState o;
        REQUIRE(c.outputs(q, guess, o));
        for (int i = 0; i < 6; ++i) {
            const Vec<n> w = randn<Vec<n>>(scale);
            const double h = 1e-6;
            const Vec<n> fd = (ybar(c, System::retract(q, w, h), o.eta) - ybar(c, System::retract(q, w, -h), o.eta))
                            / (2.0 * h);
            const Vec<n> Aw = o.A * w;
            const double err = maxDiff(fd, Aw);
            CAPTURE(i, sci(err), fd.transpose(), Aw.transpose());
            CHECK(err < 1e-6);
        }
    }
```

With h = 1e-6 and six random directions per configuration, A w must match the central difference of ȳ to 1e-6. `ybar` wraps the η difference, which matters near the seam s = 0 = L.

`WavyCouplingOutput` exists because the coupling β = q₃ − q₁ ignores η and dη entirely:

```cpp
// tests/test_controller.cpp:256-276
    class WavyCouplingOutput final : public RedundancyOutput {
        public:
            static constexpr double kAmplitude = 0.2, kWavenumber = 8.0;  // a and k

            // The part a sin(k eta) and its derivative a k cos(k eta), for the tests' own expected values
            static double wave(double eta) { return kAmplitude * std::sin(kWavenumber * eta); }
            static double waveSlope(double eta) { return kAmplitude * kWavenumber * std::cos(kWavenumber * eta); }

            void evaluate(const Vec7& q, double eta, const Vec7& deta, double& beta, Vec7& dbeta) const override
            {
                beta = q[2] - q[0] + wave(eta);
                dbeta = Vec7::Unit(2) - Vec7::Unit(0) + waveSlope(eta) * deta;
            }

            // At a fixed eta, {beta = value} is the hyperplane q3 - q1 = value - a sin(k eta).
            void levelSet(double eta, double value, Vec7& p, double& b) const override
            {
                p = Vec7::Unit(2) - Vec7::Unit(0);
                b = value - wave(eta);
            }
    };
```

With the coupling alone, a controller that passed the wrong row of J_Ψ⁻¹J_b as dη, or evaluated β at the Newton guess instead of the projected η, would still pass every test. Adding 0.2 sin(8η) makes β depend on η, so dβ gets the term 1.6 cos(8η) dη, which changes row 6 of A by more than 0.3. `final` on the class forbids further derivation; `override` makes the compiler check that `evaluate` really overrides the base's virtual function (a typo in the signature becomes an error instead of a new, unused function).

`StuckBody` (325-338) is a test-only `System` whose J_b is the identity with its last diagonal entry set to 1e-12. It shows that any class with the four members works as a `System`, and it produces an A that is singular to working precision but not exactly, so the LU solve returns finite garbage.

`pandaConfiguration` (284-314) finds a Panda configuration with a given flange pose and q₃ − q₁ = β by Newton's method on the square system [J_b; pᵀ] dq = (e, β − pᵀq), with steps capped at 0.2 rad and a tolerance of 1e-13. `pandaStart()` stores the result in a function-local `static`, computed once.

The no-allocation window is worth reading in full:

```cpp
// tests/test_controller.cpp:823-844
    c.reset(0.1);
    bool allOk = true;
    double sink = 0.0;
    Vec6 qdd = Vec6::Zero();
    RigidController::Status st;
    // No Catch2 macros inside the window: they allocate.
    const long before = gNewCalls.load(std::memory_order_relaxed);
#ifdef EIGEN_RUNTIME_NO_MALLOC
    Eigen::internal::set_is_malloc_allowed(false);
#endif
    for (int k = 0; k < 1000; ++k) {
        allOk = c.step(poses[k % 10], twists[k % 10], 0.002 * k, 0.002, qdd, st) && allOk;
        sink += qdd[0];
    }
#ifdef EIGEN_RUNTIME_NO_MALLOC
    Eigen::internal::set_is_malloc_allowed(true);
#endif
    const long after = gNewCalls.load(std::memory_order_relaxed);
    CAPTURE(before, after, sink);
    CHECK(allOk);
    REQUIRE(after == before);
}
```

The states are computed before the window, because the plant and the `std::vector`s are not under test. Inside the window there are no Catch2 macros, because Catch2 allocates for its messages; the result is accumulated in `allOk` and `sink` and checked after. `sink += qdd[0]` uses the result so that the optimizer cannot drop the calls. The `#ifdef EIGEN_RUNTIME_NO_MALLOC` lines switch Eigen's own allocation check on and off around the loop.

The timing test calls `c.reset(0.1)` before every step so that each call does the same work as a closed-loop step (one Newton update per projection), runs 20000 calls, and reports the mean with `WARN`. Under `#ifndef NDEBUG` it calls `SKIP`: a Debug build is 30 to 100 times slower (`tests/test_helpers.hpp:15`) and its timing means nothing.

The energy check alone cannot see a sign error in Cζ, since both signs do no work. That is why the momentum check and the closed-form motion exist: a sign error changes the precession direction while keeping the energy.

### test_rigid_body_example.cpp

A 20 s loop takes about 16 s in a Debug build (the file's own comment) and about 0.12 s in Release (measured here; the whole 20 s pose test case takes 0.16 s). The macro `SLOW_IN_DEBUG` hides the slow ones in Debug only:

```cpp
// tests/test_helpers.hpp:19-23
#ifdef NDEBUG
#define SLOW_IN_DEBUG "[slow]"
#else
#define SLOW_IN_DEBUG "[.slow]"
#endif
```

`NDEBUG` is defined in Release builds, so the tag is `"[slow]"` there (runs by default) and `"[.slow]"` in Debug (hidden). Two test cases carry it: the 20 s velocity loop and the Δt-halving test. The 20 s pose loop is not tagged, so it runs in Debug too, and the 20 s velocity loop has a 1 s stand-in (line 243) that holds its largest deviation and largest input.

The file detects at compile time whether `tube()` can be called on a temporary:

```cpp
// tests/test_rigid_body_example.cpp:30-34
    // Whether ex.tube() compiles for an expression ex of type T (not for a temporary: deleted &&-overload)
    template <class T, class = void>
    struct HasTube : std::false_type {};
    template <class T>
    struct HasTube<T, std::void_t<decltype(std::declval<T>().tube())>> : std::true_type {};
```

This is the detection idiom. The primary template says "no". The specialization is chosen only if `decltype(std::declval<T>().tube())` is a valid expression; `std::void_t` turns any valid type into `void`, and an invalid expression silently discards the specialization (SFINAE: substitution failure is not an error). `std::declval<T>()` pretends to produce a `T` (an rvalue for a plain `T`) without constructing one. So `HasTube<const RigidBodyExample&>` is true and `HasTube<RigidBodyExample>` is false, because the rvalue overload is deleted.
