## The System interface and RigidBody

A System gives the controller exactly two functions, `output` and `retract`, and `RigidBody` is the smallest real system that provides them: its output is the pose itself and its curve is g Exp_I(hζ). Everything else in `RigidBody` (mass, Coriolis term, integrator) exists for the simulator, not for the controller.

### output: Π(q) and J_b(q)

`output` returns the pose g = Π(q) and, through a pointer, the body Jacobian J_b with ζ = J_b(q) q̇, rows (ω, v) in the tool frame. The pointer is optional on purpose: a caller that only needs the pose passes `nullptr` and skips the Jacobian. The controller always asks for it:

```cpp
// include/se3pf/controller.hpp:218-219
                Mat<6, n> Jb = Mat<6, n>::Zero();
                const Pose g = System::output(q, &Jb);
```

`Mat<6, n>` is an alias template from `include/se3pf/types.hpp:15`. For n = 6 it names exactly the same type as `Mat6`, and for n = 7 the same type as `Mat67`. An alias is not a new type, so `&Jb` matches `RigidBody::output(const Pose&, Mat6*)` and `PandaArm::output(const Vec7&, Mat67*)` without any conversion.

### retract: why any curve through q with velocity q̇ works

The controller needs Ȧq̇, the time derivative of A(q(t)) along the motion, multiplied by q̇. It has no formula for Ȧ, so it differentiates A numerically along some curve c with c(0) = q and c′(0) = q̇. Expanding A(c(h)) in h shows why the choice of curve does not matter:

```latex
A(c(h)) = A(q) + h\,DA(q)[\dot q]
        + \tfrac{h^2}{2}\Bigl(D^2A(q)[\dot q,\dot q] + DA(q)[c''(0)]\Bigr) + O(h^3),
\qquad
\frac{A(c(h)) - A(c(-h))}{2h} = DA(q)[\dot q] + O(h^2).
```

The curve's second derivative c″(0) appears only in the even h² term, which the central difference cancels. What remains is DA(q)[q̇] = d/dt A(q(t)) at t = 0, and multiplying by q̇ gives Ȧq̇. So `retract` only has to be some smooth curve through q with velocity q̇; c″ changes the size of the O(h²) error, not the limit.

Why a curve at all, instead of q + h q̇? Because for the rigid body `Config` is a `Pose`, a 4 × 4 matrix in SE(3), and g + hζ is not a pose (and has the wrong shape anyway). The curve has to stay on the group. For the Panda the joint space is a vector space, and `PandaArm::retract` is plain q + h q̇ (`include/se3pf/panda.hpp:26-27`).

A scratch check (not in the repository) confirms the claim. At the rigid-body start pose g₀ with a body twist of norm 0.7, the central difference with h = 1e-5 along the screw motion g exp(hζ̂), which differs from `retract` at second order, is 3.5e-10 from a sixth-order reference; along the controller's own curve it is 2.1e-10. Both are at the rounding floor (the reference itself is good to about 7e-11). The 20 s closed loops then end with the same maximum deviation to all seven printed digits: 9.508595e-4 (velocity reference) and 9.685430e-4 (pose reference). The test file uses the same idea on purpose: its `adotQdot` (`tests/test_controller.cpp:186-200`) differentiates along `curve`, which for a `Pose` is `screw` (`tests/test_controller.cpp:156-164`), so it does not repeat the controller's computation.

### The RigidBody class

```cpp
// include/se3pf/rigid_body.hpp:14-27
    class RigidBody {
        public:
            static constexpr int kDof = 6;
            using Config = Pose;

            // J: inertia about the centre of mass in body coordinates, m: mass. Throws std::invalid_argument
            // unless J is finite, symmetric positive definite and m is positive and finite. A J that is symmetric
            // only up to rounding (relative 1e-12) is accepted, and its symmetric part (J + J^T) / 2 is used.
            RigidBody(const Matrix3d& J, double m);
            static RigidBody example();  // the paper's example: J = diag(1.0, 1.2, 0.8) kg m^2, m = 2 kg

            // System interface (see the design doc, The system interface)
            static Pose output(const Pose& g, Mat6* Jb);                     // Pi(g) = g; *Jb = I if Jb != nullptr
            static Pose retract(const Pose& g, const Vec6& zeta, double h);  // g Exp_I(h zeta), product metric
```

The second half declares the dynamics, which only the simulator uses, and the private data:

```cpp
// include/se3pf/rigid_body.hpp:29-41
            // Dynamics, eq:EL (used by the simulator, not by the controller)
            Mat6 mass() const;                                      // M = diag(J, m I)
            Vec6 coriolis(const Vec6& zeta) const;                  // C(g, zeta) zeta
            Vec6 acceleration(const Vec6& zeta, const Vec6& u) const;  // zeta' = M^-1 (u - C zeta), since G = 0

            // One RK4 step of length h with u held constant; updates g and zeta in place. R stays in SO(3).
            void integrate(Pose& g, Vec6& zeta, const Vec6& u, double h) const;

        private:
            Matrix3d J_;     // (J + J^T) / 2: exactly symmetric
            Matrix3d Jinv_;  // J_^-1, computed once in the constructor
            double m_;
    };
```

- `static constexpr int kDof = 6;` is a compile-time constant that belongs to the class, not to an object. `constexpr` means the value is fixed at compile time, so it can size Eigen matrices (`Vec<kDof>`).
- `using Config = Pose;` is a type alias inside the class; outside it is written `RigidBody::Config`.
- The `static` functions are the System interface; the non-static `const` functions need J and m and are the dynamics.
- The configuration is g = (R, p) ∈ SE(3), the generalized velocity is the body twist ζ = (ω, v) at the centre of mass, the input is the body wrench u = (τ, f).

### The constructor: validation in one place

```cpp
// src/rigid_body.cpp:22-37
    RigidBody::RigidBody(const Matrix3d& J, double m)
        : J_(0.5 * (J + J.transpose())), Jinv_(Matrix3d::Identity()), m_(m)
    {
        if (!J.allFinite() || (J - J.transpose()).cwiseAbs().maxCoeff() > 1e-12 * J.cwiseAbs().maxCoeff())
            throw std::invalid_argument("RigidBody: the inertia J must be finite and symmetric");

        // A symmetric matrix has a Cholesky factorization exactly when it is positive definite.
        const Eigen::LLT<Matrix3d> llt(J_);
        if (llt.info() != Eigen::Success)
            throw std::invalid_argument("RigidBody: the inertia J must be positive definite");

        if (!(m > 0.0) || !std::isfinite(m))  // !(m > 0) also rejects NaN
            throw std::invalid_argument("RigidBody: the mass m must be positive and finite");

        Jinv_ = llt.solve(Matrix3d::Identity());
    }
```

- The member initializer list (after the colon) builds the members before the body runs. Members are always built in declaration order (`J_`, `Jinv_`, `m_` at `include/se3pf/rigid_body.hpp:38-40`), whatever order the list is written in; GCC's `-Wreorder` (part of `-Wall`) warns if the two disagree.
- Symmetry is checked to a relative 1e-12 of the largest entry. A J computed as Q D Qᵀ is already off by one ulp (5.6e-17 in the test at `tests/test_rigid_body.cpp:122-123`), and a J read from a file can be off by more. Exact symmetry would reject such good inputs. "Relative" means the same J in g·cm² (1e7 times larger) passes too (`tests/test_rigid_body.cpp:130`).
- After the check only `J_` = (J + Jᵀ)/2 is used, so `mass()`, `coriolis()` and `acceleration()` all describe one exactly symmetric matrix.
- `Eigen::LLT` is the Cholesky factorization J = LLᵀ. For a symmetric matrix it succeeds exactly when the matrix is positive definite, so `llt.info() != Eigen::Success` is the positive-definiteness test (indefinite, singular and zero J are all rejected by the test at `tests/test_rigid_body.cpp:108-110`).
- `!(m > 0.0)` instead of `m <= 0.0`: every comparison with NaN is false, so `m <= 0.0` would let NaN through, while `!(m > 0.0)` rejects it. You will see this idiom throughout the code.
- `Jinv_ = llt.solve(Matrix3d::Identity())` computes J⁻¹ once, from the same factorization, so the integrator's four stages per substep never factor J again.
- Failure is an exception here because construction is offline: a bad inertia is a programming or input error, found before any loop runs. If the constructor throws, no object exists, so no half-built `RigidBody` can be used.

`example()` is a static factory for the paper's body:

```cpp
// src/rigid_body.cpp:39-42
    RigidBody RigidBody::example()
    {
        return RigidBody(Matrix3d(Vector3d(1.0, 1.2, 0.8).asDiagonal()), 2.0);
    }
```

`asDiagonal()` returns a lightweight "diagonal matrix" expression; `Matrix3d(...)` turns it into a dense 3 × 3 matrix with zeros off the diagonal.

### output and retract for the rigid body

```cpp
// src/rigid_body.cpp:44-61
    Pose RigidBody::output(const Pose& g, Mat6* Jb)
    {
        if (Jb != nullptr)
            *Jb = Mat6::Identity();  // Pi = id: the body velocity of the output is zeta itself
        return g;
    }

    // g Exp_I(h zeta) with the product-type Exp_I of Example 1: (R exp(h omega^), p + h R v). A curve through g
    // with velocity zeta, which is all the controller's central difference of A needs. The closed form does not
    // depend on w_R and w_p, so no Metric is needed.
    Pose RigidBody::retract(const Pose& g, const Vec6& zeta, double h)
    {
        const Matrix3d R = g.block<3,3>(0,0);
        const Vector3d p = g.block<3,1>(0,3);
        const Vector3d w = zeta.head<3>();
        const Vector3d v = zeta.tail<3>();
        return makePose(R * expSO3(Vector3d(h * w)), p + h * R * v);
    }
```

- `g.block<3,3>(0,0)` is the 3 × 3 block starting at row 0, column 0 (R); `g.block<3,1>(0,3)` is the column p. The sizes are template arguments, so they are fixed at compile time. Here no `.template` keyword is needed because `g` has a concrete type (`Pose`); inside the controller template it is (see "Design decisions and C++").
- For the product metric, Exp_I(ζ) = (exp(ω̂), v) (Example 1), so g Exp_I(hζ) = (R exp(hω̂), p + hRv). It does not depend on w_R or w_p, which is why no `Metric` is passed. The test at `tests/test_rigid_body.cpp:214-237` checks c(0) = g, (g⁻¹c′(0))^∨ = ζ to 1e-8, and equality with `W.Exp` for w_R = 0.01 to 1e-13.
- No failure path: a NaN in g or ζ propagates into the result, and the controller's projection then refuses it.

### Dynamics: M and Cζ

The paper's eq:EL is M ζ̇ + C(g, ζ)ζ + G = u. Euler's equations in body coordinates are J ω̇ = Jω × ω + τ and m v̇ = m v × ω + f. Moving the gyroscopic terms to the left side flips their sign:

```latex
M = \begin{bmatrix} J & 0 \\ 0 & mI \end{bmatrix}, \qquad
C(g,\zeta)\,\zeta = -\begin{bmatrix} J\omega\times\omega \\ m\,v\times\omega \end{bmatrix}, \qquad
G = 0, \qquad
\dot\zeta = M^{-1}\bigl(u - C(g,\zeta)\,\zeta\bigr).
```

The translational line comes from ṗ = Rv: m d/dt(Rv) = Rf gives m(Rω̂v + Rv̇) = Rf, so m v̇ = −m ω × v + f = m v × ω + f.

```cpp
// src/rigid_body.cpp:63-80
    Mat6 RigidBody::mass() const
    {
        Mat6 M = Mat6::Zero();
        M.block<3,3>(0,0) = J_;
        M.block<3,3>(3,3) = m_ * Matrix3d::Identity();
        return M;
    }

    // C(g, zeta) zeta = -(J omega x omega, m v x omega): moving Euler's equations (see the header) to the left
    // side of eq:EL flips their sign. Both parts are orthogonal to zeta, so they do no work.
    Vec6 RigidBody::coriolis(const Vec6& zeta) const
    {
        const Vector3d w = zeta.head<3>();
        const Vector3d v = zeta.tail<3>();
        Vec6 c;
        c << -(J_ * w).cross(w), -m_ * v.cross(w);
        return c;
    }
```

- `Mat6 M = Mat6::Zero();` matters: an Eigen matrix declared without an initializer holds garbage, and `mass()` writes only the two diagonal blocks.
- `c << a, b;` is Eigen's comma initializer: it fills `c` with the 3-vector `a` followed by the 3-vector `b`.
- "Both parts are orthogonal to ζ": ωᵀ(Jω × ω) = 0 and vᵀ(v × ω) = 0, so ζᵀCζ = 0 and free motion keeps its energy. The test at `tests/test_rigid_body.cpp:159-168` checks this to 1e-13. Energy cannot reveal a sign error in Cζ, because both signs do no work; the closed-form motion test (`tests/test_rigid_body.cpp:252-289`) and the momentum checks of `checkFreeMotion` can (see "The tests").
- `coriolis` takes only ζ even though the paper writes C(g, ζ): for the free body in body coordinates, C does not depend on g.

```cpp
// src/rigid_body.cpp:82-89
    // eq:EL with G = 0 solved for zeta'. M is block diagonal, so M^-1 = diag(J^-1, I / m).
    Vec6 RigidBody::acceleration(const Vec6& zeta, const Vec6& u) const
    {
        const Vec6 rhs = u - coriolis(zeta);
        Vec6 a;
        a << Jinv_ * rhs.head<3>(), rhs.tail<3>() / m_;
        return a;
    }
```

`acceleration` solves eq:EL for ζ̇ with the block inverse M⁻¹ = diag(J⁻¹, I/m): `Jinv_` from the constructor times the torque part, and the force part divided by m. It calls `coriolis`, so the simulated plant and the simulator's input u = M q̈* + Cζ (`src/rigid_body_example.cpp:103`) use the same Cζ.

### integrate: RK4 in exponential coordinates around R_k

One call advances (g, ζ) by h with u held constant. The pose is not integrated as a matrix. Instead, within the step, the attitude is written as the starting attitude R_k times the exponential of a vector φ that starts at zero:

```latex
R(t) = R_k \exp(\hat\varphi(t)), \quad \varphi(0) = 0, \qquad
\dot\varphi = J_r(\varphi)^{-1}\,\omega, \qquad
\dot p = R\,v = R_k \exp(\hat\varphi)\,v, \qquad
\dot\zeta = M^{-1}\bigl(u - C\zeta\bigr).
```

The φ equation comes from the right Jacobian: d/dt exp(φ̂) = exp(φ̂)(J_r(φ)φ̇)^, so Ṙ = R(J_r(φ)φ̇)^. The body velocity requires Ṙ = Rω̂, hence J_r(φ)φ̇ = ω. Now φ, p and ζ all live in vector spaces, where RK4's weighted sums of stage values make sense.

```cpp
// src/rigid_body.cpp:95-109
    void RigidBody::integrate(Pose& g, Vec6& zeta, const Vec6& u, double h) const
    {
        const Matrix3d Rk = g.block<3,3>(0,0);
        const Vector3d pk = g.block<3,1>(0,3);

        // Right-hand side at a stage. p does not appear on it, so it is not an argument.
        auto rates = [&](const Vector3d& phi, const Vec6& z) -> Rates {
            const Vector3d w = z.head<3>();
            const Vector3d v = z.tail<3>();
            Rates r;
            r.phi = JrInv(phi) * w;
            r.p = Rk * expSO3(phi) * v;
            r.zeta = acceleration(z, u);
            return r;
        };
```

- `auto rates = [&](...) -> Rates { ... };` is a lambda: an unnamed function object defined in place. `[&]` captures `Rk` and `u` by reference, and implicitly the `this` pointer, so the body can call `acceleration`. That is safe because the lambda never outlives `integrate`. `-> Rates` states the return type. `auto` is fine here because a lambda's type has no name you could write; the Eigen rule "no `auto`" is about Eigen expressions.
- `Rates` is a small struct defined in an anonymous namespace (`src/rigid_body.cpp:10-17`). An anonymous namespace gives it internal linkage: it is private to this `.cpp` file and cannot clash with another `Rates`.
- At the first stage φ = 0, where J_r(0)⁻¹ = I, so k1.φ = ω.

```cpp
// src/rigid_body.cpp:111-121
        const Rates k1 = rates(Vector3d::Zero(), zeta);
        const Rates k2 = rates(0.5 * h * k1.phi, zeta + 0.5 * h * k1.zeta);
        const Rates k3 = rates(0.5 * h * k2.phi, zeta + 0.5 * h * k2.zeta);
        const Rates k4 = rates(h * k3.phi, zeta + h * k3.zeta);

        const double c = h / 6.0;
        const Vector3d phi = c * (k1.phi + 2.0 * k2.phi + 2.0 * k3.phi + k4.phi);
        const Vector3d p = pk + c * (k1.p + 2.0 * k2.p + 2.0 * k3.p + k4.p);
        zeta += c * (k1.zeta + 2.0 * k2.zeta + 2.0 * k3.zeta + k4.zeta);
        g = makePose(Rk * expSO3(phi), p);
    }
```

- These are the classical RK4 stages with weights (1, 2, 2, 1)/6. Since φ(0) = 0, the final φ is just the weighted sum, with no starting value added.
- The new attitude is R_k exp(φ̂): a product of two rotation matrices, so it is a rotation up to rounding, whatever h is and however many steps are taken. That is the point of the construction.
- Why not RK4 on R directly? A weighted sum of rotation matrices is not a rotation, so R drifts off SO(3). A scratch comparison over 100 s of free motion of the example body (from the state of the free-motion test, ζ₀ = (1, −0.7, 0.5, 0.4, 0.1, −0.3)) shows the effect. With h = 0.5 ms both methods stay at rounding level (‖RᵀR − I‖ below 1e-13). With h = 2 ms the naive method reaches 2.5e-13, and with h = 10 ms it reaches 7.0e-11 after 10 s and 7.4e-10 after 100 s: it keeps growing with time. The exponential coordinates stay below 4e-14 at both step sizes. The test at `tests/test_rigid_body.cpp:239-250` holds ‖RᵀR − I‖ below 1e-12 over 20000 steps.
- RK4 has local error O(h⁵) and global error O(h⁴). That is why 1, 4 and 16 substeps per 2 ms control period give the same closed loop to 1e-10 after 1 s (`tests/test_rigid_body_example.cpp:262-286`).
- No failure path: the integrator assumes finite inputs, and the simulator only calls it after a successful control step.
