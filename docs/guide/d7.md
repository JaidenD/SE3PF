## The tests

This layer has 42 test cases in three files (10 in `tests/test_panda.cpp`, 18 in `tests/test_lift.cpp`, 14 in `tests/test_panda_example.cpp`), all sharing one fixture. Each checks a defining property, a finite difference, or a number from an independent computation, and most tolerances sit one to five orders of magnitude above the measured error, so a real bug fails them and round-off does not.

### How the tests are written

- `TEST_CASE("name", "[tags]")` declares a test. `CHECK(cond)` records a failure and continues; `REQUIRE(cond)` stops the test case, used when later lines would be meaningless (for example, a failed solve). `STATIC_REQUIRE` checks a compile-time constant, so it fails when the test is compiled.
- `CAPTURE(x)` prints x if a later check fails. `testing::sci(err)` formats it in scientific notation, because Catch2 prints doubles with 10 fixed decimals and would show 3e-12 as 0.0.
- `testing::maxDiff(a, b)` is the largest absolute entry of a − b. Eigen's `isApprox` is relative and never passes against an exact zero, so the tests use absolute tolerances throughout.
- `CHECK_THAT(x, WithinAbs(expected, tol))` compares scalars. `CHECK_THROWS_MATCHES(expr, type, MessageMatches(ContainsSubstring("...")))` checks both the exception type and its message, so a test cannot pass on the wrong throw.
- Random inputs are reproducible: `tests/rng_listener.cpp` reseeds the shared generator with `kRngSeed = 12345` before every run of a test case (each leaf section), so a test sees the same numbers alone, in the full run or in random order.
- Tags: `SLOW_IN_DEBUG` expands to `"[slow]"` in Release and to the hidden `"[.slow]"` in Debug, where a 20 s loop takes a minute; each hidden loop has a short stand-in that always runs. `"[.timing]"` tests are hidden everywhere, run on request, and skip themselves in Debug.

### The fixture

```cpp
// tests/panda_fixture.hpp:6-14
namespace testing {

    // An inline function, so its static is one object across all translation units. Built on first use, so a test
    // program that never asks for it does not build it.
    inline const se3pf::PandaExample& pandaExample()
    {
        static const se3pf::PandaExample ex;
        return ex;
    }
```

Building the example takes about 0.03 s in Release but about 4 s in Debug, so every test file shares one. Two C++ rules make that work:

- A function-local `static` is built the first time control passes through it, and only once; since C++11 that initialization is thread-safe. A test program that never calls `pandaExample()` never builds it.
- The function is `inline` in a header. Each `.cpp` file that includes it gets a copy of the definition, and the linker merges them into one function with one static object. Without `inline`, two test files would define the same function twice and fail to link; with `static` at namespace scope instead, each file would build its own example.

Each test file wraps the parts it needs in small functions (`lift()`, `tube()`, `beta()`, `example()`). The returned references are safe because the fixture lives until the program ends.

### Where the expected values come from: the oracle

Numbers from the paper have two or three digits; the tests need six. They come from `docs/DESIGN.md` (each recomputed independently) and, for the closed loops, from `tools/oracle/panda_oracle.cpp`. The oracle is a separate program built against the earlier library `pf` (`~/Desktop/panda_path_following/include`), which is not in this repository, so CMake does not build it. Its header gives the build line:

```bash
g++ -O2 -std=c++17 -I ~/Desktop/panda_path_following/include tools/oracle/panda_oracle.cpp -o /tmp/panda_oracle
/tmp/panda_oracle
```

`pf` has no rest-posture lift, so the oracle adds the paper's lift condition h(q) = x(q)ᵀ(q − q_r) as a `LiftCondition`, with its gradient by central differences of the kernel vector:

```cpp
// tools/oracle/panda_oracle.cpp:24-44
class RestPosture final : public LiftCondition {
 public:
  explicit RestPosture(const Vec7& qr) : qr_(qr) {}
  double value(const Vec7& q) const override { return dot(panda::kernelVector(panda::bodyJacobian(q)), q - qr_); }
  Vec7 gradient(const Vec7& q) const override {
    const Vec7 x = panda::kernelVector(panda::bodyJacobian(q)), e = q - qr_;
    Vec7 g;
    constexpr double d = 1e-6;
    for (std::size_t j = 0; j < 7; ++j) {
      Vec7 u;
      u[j] = d;
      const Vec7 dx =
          (panda::kernelVector(panda::bodyJacobian(q + u)) - panda::kernelVector(panda::bodyJacobian(q - u))) / (2.0 * d);
      g[j] = dot(dx, e) + x[j];
    }
    return g;
  }

 private:
  Vec7 qr_;
};
```

`gradient` is ∇h = Dxᵀ(q − q_r) + x, computed column by column with step 1e-6: exactly what the square system of the design doc needs, and `pf`'s `Lift` solves that system with a 0.2 rad step cap, and takes q*′ from the implicit-function system instead of central differences. The oracle then runs both loops with this example's settings (W = diag(0.01 I, I), the coning circle, gains 16/8 and k_t = 5, ν_d = 0.08, no ramp, Δt = 1 ms, the held-acceleration update) and prints the numbers that `tests/test_panda_example.cpp` uses: 2.43388e-5, 1.52440e-5, 1.51035e-4, 1.24497e-6, 9.932e-6 and 1.3024e-5 (rebuilt and rerun for this guide: it prints exactly these). Different lift solver, different matrix code, same results to 6–7 significant digits: that agreement is the evidence that both implement the paper and not a shared bug.

### tests/test_lift.cpp: helpers

The file's helpers are written independently of `lift.cpp`, so a test never shares code with what it checks:

- `poseGap(g, target)` recomputes the pose error (log R, p) of g⁻¹·target and returns its largest entry.
- `kernelJacobian(q)` is Dx by central differences, step 1e-6.
- `exactLiftDerivative(s, q)` solves [J_b; ∇hᵀ] q*′ = (ζ_γ(s), 0) with the full ∇h = Dxᵀ(q − q_r) + x: the implicit-function-theorem derivative.
- `outputsAt(q, guess)` computes η, ξ and dη = row 0 of J_Ψ⁻¹J_b as the controller does; `betaAt(q, guess)` evaluates β with η = η(Π(q)), the function whose differential dβ is.
- `startAt(s0, xi0, beta0)` wraps `startConfiguration` from q*(s₀) with a `REQUIRE`.
- `OpenArc` is a `Path` that returns the paper's circle but reports 90 % of its length, so γ(L) ≠ γ(0). It is not a valid path; it exists to reach the closure check. It stores a copy of the circle, not a reference.

### tests/test_panda_example.cpp: helpers

- `paperRun()`, `paperFirstSecond()`, `selfMotionRun()`, `selfMotionFirstHalfSecond()` each hold a function-local `static const PandaRun`: a run is computed the first time a test needs it and shared after that.
- `checkLog(run, rows)` checks a whole run. Every row has t = kΔt exactly, `xiNorm = xi.norm()`, `eTan = etaDot − ref` and a consistent joint margin. Every summary extreme and the start and final values are recomputed from the rows and must match exactly. A successful run has `capacity() == size()`, proof that the log never grew inside the loop. Consecutive rows obey the held-acceleration update to 1e-14 (relative to max(1, |q|); measured 2e-16); dropping the ½Δt² term would be off by about 1e-6.
- `rowDifference(a, b)` is the largest difference of η, η̇, ξ, β, q, q̇ and q̈* over the common rows. The tests require exactly 0.0 between a run and its stand-in, so the short run is bit for bit the start of the long one: the loop does not depend on T.
- `outputsAt(q, out)` computes η, ξ and β of a configuration as the controller does.

The non-copy test needs to ask "does `ex.tube()` compile?" without a compile error when the answer is no. That is SFINAE (substitution failure is not an error):

```cpp
// tests/test_panda_example.cpp:165-176
namespace {
    // Whether ex.tube() and ex.redundancy() compile for an expression ex of type T (the deleted &&-overloads make them
    // fail on a temporary, whose parts a controller would keep references to)
    template <class T, class = void>
    struct HasTube : std::false_type {};
    template <class T>
    struct HasTube<T, std::void_t<decltype(std::declval<T>().tube())>> : std::true_type {};
    template <class T, class = void>
    struct HasRedundancy : std::false_type {};
    template <class T>
    struct HasRedundancy<T, std::void_t<decltype(std::declval<T>().redundancy())>> : std::true_type {};
}
```

- The primary template `HasTube<T, void>` derives from `std::false_type`.
- The partial specialization applies only if `std::declval<T>().tube()` is a valid expression. `std::declval<T>()` names a value of type T without building one: an rvalue for T = `PandaExample`, an lvalue for T = `const PandaExample&`. `std::void_t<...>` turns any valid type into `void`, so the specialization then matches `HasTube<T, void>`.
- For an rvalue, `.tube()` selects the deleted `const&&` overload, which makes the expression ill-formed. The specialization silently drops out, and the primary template answers `false`.
