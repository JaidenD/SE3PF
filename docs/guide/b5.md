## Design decisions and C++

This section explains each C++ choice in `tube.hpp` and `tube.cpp`: what the mechanism does, why it is used here, and what breaks without it. Read it with the code open; every point names its line.

### A reference to the Path, a copy of the Metric

The tube stores `const Path& path_` but `Metric metric_` (`include/se3pf/tube.hpp:93-94`). The two members are treated differently on purpose.

```cpp
// include/se3pf/path.hpp:12-19
    class Path {
        public:
            virtual ~Path() = default;
            virtual double length() const = 0;              // L
            virtual Pose pose(double s) const = 0;          // gamma(s)
            virtual Vec6 velocity(double s) const = 0;      // zeta_gamma(s), unit W-norm
            virtual Vec6 acceleration(double s) const = 0;  // zeta_gamma'(s)
    };
```

`Path` is an abstract base class: its functions are pure virtual (`= 0`), and `ConingCircle` and `TumblingCircle` override them. A `virtual` function is chosen at run time from the object's real type, so `path_.velocity(s)` calls the coning circle's formula when the tube was built on one. An abstract class cannot be stored by value: you cannot create a `Path`, and copying a `ConingCircle` into a `Path` member would "slice" it down to the base, losing the override.

So the tube refers to the caller's path. A reference needs no heap, cannot be null, and costs nothing per call. The price is that the caller owns the lifetime: the path must live at least as long as the tube.

`Metric` is a small concrete class holding one `Mat6` (288 bytes, checked with `sizeof`). Copying it once costs nothing, and the tube then owns its metric. That is why `Tube tube(path, Metric::product(1.0, 1.0));` is safe: the temporary metric is copied in the initializer list before it dies at the end of the statement.

A reference member has one side effect: the class has no copy assignment. A reference cannot be re-seated, so the compiler deletes `operator=`. `Tube b = a;` (copy construction) compiles, `b = a;` does not; both facts are checked with `std::is_copy_constructible_v` and `std::is_copy_assignable_v`.

The copy `b` refers to the same path as `a` and gets its own copy of the 960 KB of spline nodes.

### The deleted rvalue constructor and its default argument

The second constructor exists only to be deleted:

```cpp
// include/se3pf/tube.hpp:54-56
            // Builds N(s) on gridIntervals uniform intervals; throws std::runtime_error if the construction fails.
            Tube(const Path& path, const Metric& metric, int gridIntervals = 2000);
            Tube(const Path&& path, const Metric& metric, int gridIntervals = 2000) = delete;  // no temporaries
```

The guard prevents a dangling reference. `Tube tube(ConingCircle(R0, p0, r, a, W), W);` passes a temporary path.

A temporary is destroyed at the end of the full expression, after the constructor has run. The frame is built correctly, and then `path_` refers to a destroyed object: every later `Psi`, `outputs` or `JPsi` is undefined behaviour, with garbage numbers or a crash.

Deletion turns that into a compile error. A temporary is an rvalue, and in overload resolution, binding an rvalue to an rvalue reference (`const Path&&`) beats binding it to an lvalue reference (`const Path&`). So the deleted overload is chosen, and g++ reports "use of deleted function 'se3pf::Tube::Tube(const se3pf::Path&&, const se3pf::Metric&, int)'".

A named path is an lvalue and binds only to `const Path&`, so normal use is unaffected.

Why `const Path&&` and not `Path&&`. The `const` version also catches a const temporary, for example the result of a function returning `const ConingCircle`.

The default argument `= 2000` on a deleted function matters. Without it, the deleted overload needs three arguments, so the common two-argument call `Tube(ConingCircle(...), W)` matches only the `const Path&` constructor and compiles silently. Measured by removing the default from `tube.hpp`: the two-argument call compiles under `-Wall -Wextra` with no warning, and the test below fails to build.

The test checks both forms at compile time:

```cpp
// tests/test_tube.cpp:157-163
TEST_CASE("Tube: a temporary path does not compile (the tube keeps a reference)")
{
    STATIC_REQUIRE(std::is_constructible_v<Tube, const ConingCircle&, const Metric&>);
    STATIC_REQUIRE(std::is_constructible_v<Tube, const TumblingCircle&, const Metric&, int>);
    STATIC_REQUIRE_FALSE(std::is_constructible_v<Tube, ConingCircle, const Metric&>);
    STATIC_REQUIRE_FALSE(std::is_constructible_v<Tube, TumblingCircle&&, const Metric&, int>);
}
```

`std::is_constructible_v<T, Args...>` is a compile-time `bool` from `<type_traits>`: true if `T(Args...)` would compile. A deleted constructor counts as not constructible. `STATIC_REQUIRE` checks it while compiling; if it fails, the test program does not build.

The same guard appears wherever a class keeps a reference: `Controller` deletes `Controller(const Tube&&, ...)` (`include/se3pf/controller.hpp:182-183`). `PandaExample` uses ref-qualified accessors for the same reason: `const Tube& tube() const&` works on a named example, and `const Tube& tube() const&& = delete;` refuses a temporary one (`include/se3pf/panda_example.hpp:65`, `include/se3pf/panda_example.hpp:72`).

### The fixture: function-local statics

The test fixture builds each path and tube once per test program and keeps them alive until it exits.

```cpp
// tests/tube_fixture.hpp:12-19
    // Panda path (coning circle, p0 = (0.40, 0, 0.45), r = 0.12, alpha = 0.25), l = 0.1 m: W = diag(0.01 I, I)
    inline const se3pf::Tube& pandaTube()
    {
        static const se3pf::Metric W = se3pf::Metric::product(0.01, 1.0);
        static const se3pf::ConingCircle path(restAttitude(), Vector3d(0.40, 0.0, 0.45), 0.12, 0.25, W);
        static const se3pf::Tube tube(path, W);
        return tube;
    }
```

A `static` local variable is constructed the first time control reaches it and destroyed at program exit, in reverse order of construction. So `W` and `path` are built before `tube` and destroyed after it, and the path outlives the tube by construction. Since C++11 this initialization is thread-safe.

The function is `inline`, so every file that includes the header shares one function and one set of statics. Each tube costs about 4 to 5 ms once, and `test_tube.cpp` and `test_controller.cpp`, both linked into the same `tests` program, share it.

If the constructor throws, the static counts as not initialized, and the next call tries again. That is why a broken constructor makes nearly every tube test fail, each with the same exception.

### Private helpers and the anonymous namespace

Helpers that no caller needs are hidden in two ways.

`newton` is a private member function (`include/se3pf/tube.hpp:91`). It needs `path_`, `metric_` and `wrap`, so it belongs to the class. It is private because `outputs` and `globalProject` are the entry points; a caller of `newton` would get η without ξ.

`transportRate`, `initialFrame`, `identityDistance`, `radiusPasses` and the alias `RowVec5` live in an unnamed namespace:

```cpp
// src/tube.cpp:15-18
namespace se3pf {

    namespace {
        using RowVec5 = Eigen::Matrix<double, 1, 5>;
```

A `namespace { ... }` without a name gives its contents internal linkage: they exist only inside `tube.cpp`. Another file of the library can define its own `initialFrame` without a clash at link time, and the header stays free of implementation details. The file opens the unnamed namespace twice (`src/tube.cpp:17` and `src/tube.cpp:338`); both blocks are the same namespace, reopened next to the code that uses it.

`using namespace Eigen;` appears in the `.cpp` only (`src/tube.cpp:13`). In a header it would leak every Eigen name into every file that includes it.

### std::array in RotationPlanes

`RotationPlanes` stores its planes in `std::array<Vec5, 2>` and `std::array<double, 2>` with a separate `count` (`include/se3pf/tube.hpp:19-27`). `rotationPlanes` keeps its found vectors in `std::array<Vec5, 4> used` (`src/tube.cpp:92`).

`std::array<T, N>` is a fixed-size array with value semantics: it lives inside the struct, needs no heap, and copies with the struct. The size is known: a rotation of R⁵ has at most two planes, so two slots always suffice and `count` says how many are valid. A `std::vector` would allocate and track a size the type already knows.

The arrays are initialized with `= {Vec5::Zero(), Vec5::Zero()}`. An Eigen vector declared without an initializer holds whatever bytes were in memory, so unused slots would otherwise be garbage.

### Structs for diagnostics and options

`TubeDiagnostics` and `RadiusOptions` are aggregates: plain structs with public fields and default member initializers (`include/se3pf/tube.hpp:37-45`, `include/se3pf/tube.hpp:102-110`). Both satisfy `std::is_aggregate_v` (checked by compiling).

`TubeDiagnostics` is filled once in the constructor and returned by `const TubeDiagnostics&`, so the tests read fields by name (`d.closureGap`) with no copy and no getters. `RadiusOptions` replaces a function with seven positional numbers.

The default argument `const RadiusOptions& options = {}` creates a temporary from the empty braces. For an aggregate that is aggregate initialization with no values, so every field takes its default member initializer. A test changes only what it needs, such as `opt.footPoints = 8;`.

### Status by return value, results by reference

The online functions return a `bool` status and write results through references: `bool outputs(const Pose& g, double guess, double& eta, Vec5& xi, int* iterations = nullptr) const`. Optional results are pointers with a `nullptr` default.

This pattern fits a real-time loop. It returns several Eigen values without allocation, and the status is checked with a plain `if`. Exceptions are kept for the offline constructor and `estimateTubeRadius`, where a failure is a programming or configuration error that should stop the program.

The `const` at the end of each online function promises not to change the tube. That lets the controller, which holds a `const Tube&` (`include/se3pf/controller.hpp:331`), call them.

### Why not Eigen's unsupported MatrixFunctions

The design document allowed `Mat5 Phi = Hr.log();` from `unsupported/Eigen/MatrixFunctions` (`docs/DESIGN.md:202`). The code uses the invariant planes instead, for four reasons:

1. Correctness at π: for H = diag(R(π), 1, 1, 1), `log()` returns the zero matrix, whose exponential misses H by 2.0 (measured, Eigen 3.4.0). The planes return an exact logarithm (test "rotationPlanes: a rotation by pi has a logarithm too").
2. Cost: step 5 needs exp(−(s/L)Φ) at 2001 nodes. The planes give it with one `cos` and one `sin` per plane; `exp()` would run a scaling-and-squaring Padé approximation each time.
3. Stability of the API: the `unsupported` modules are outside Eigen's supported interface and may change between versions.
4. Diagnostics: the planes give the rotation angles directly, which the tests compare with the anchors 0.161182, 8.0e-5 and so on.

### Eigen pitfalls avoided, line by line

The design document lists five Eigen pitfalls (`docs/DESIGN.md:39-45`). Here is where `tube.cpp` avoids each.

| Pitfall | What goes wrong | Where it is avoided |
| --- | --- | --- |
| `auto` for Eigen results | `auto k1 = A * B;` stores an unevaluated expression, recomputed at each use or pointing at destroyed temporaries | every result is typed: `const RowVec5 row` (`src/tube.cpp:27`), `const Mat65 k1` to `k4` (`src/tube.cpp:169-172`), `const Mat5 H` (`src/tube.cpp:177`), `const Vec6 de` (`src/tube.cpp:253`) |
| No zero initialization | `Mat5 Phi;` holds garbage, and `Phi += ...` adds to it | `Mat5 Phi = Mat5::Zero();` (`src/tube.cpp:63`), `Mat65 N0 = Mat65::Zero();` (`src/tube.cpp:51`), `Vec5 v = Vec5::Zero();` (`src/tube.cpp:115`), `std::vector<Mat65> N0(n_ + 1, Mat65::Zero())` (`src/tube.cpp:162`), `Vec6 e = Vec6::Zero();` (`src/tube.cpp:285`, `src/tube.cpp:314`), `Mat6 J = Mat6::Zero();` (`src/tube.cpp:329`) |
| Aliasing | `M = 0.5 * (M - M.transpose());` overwrites entries before reading them | updates read a scalar first: `x -= W.inner(b, x) * b;` (`src/tube.cpp:39`) and `x -= used[j].dot(x) * used[j];` (`src/tube.cpp:97`) compute the dot product before touching `x`; products go into new objects (`Y[k] * Phi`, `src/tube.cpp:205`) |
| Relative comparisons | `isApprox` is relative and never passes against zero | absolute errors as `(A - B).cwiseAbs().maxCoeff()` (`src/tube.cpp:179`, `src/tube.cpp:196-197`, `src/tube.cpp:208`); the tests use `maxDiff`, the same idea (`tests/test_helpers.hpp:35-39`) |
| Alignment | old Eigen needed `aligned_allocator` for a `std::vector` of fixed-size vectorizable types | none needed: C++17 and Eigen 3.4 handle `std::vector<Mat65>` (`src/tube.cpp:162`, `src/tube.cpp:201`) and `std::vector<Pose>` (`src/tube.cpp:409`) |

A few more Eigen details worth knowing:

- `JacobiSVD<Mat5> svd(H, ComputeFullU | ComputeFullV)` (`src/tube.cpp:187`): for a fixed-size matrix only the full U and V are allowed.
- `SelfAdjointEigenSolver<Mat6> eigW(..., EigenvaluesOnly)` (`src/tube.cpp:413`) skips the eigenvectors when only λ_min is needed.
- `logSO3(Matrix3d(g.block<3,3>(0,0)))` (`src/tube.cpp:344`) turns the 3 × 3 block expression into a real `Matrix3d` before the call. The conversion would also happen implicitly, because `logSO3` takes a `const Matrix3d&`; writing it out makes the copy visible.
- `(0.5 * h) * k1` (`src/tube.cpp:170`) multiplies the two scalars once and then scales the matrix. Written as `0.5 * (h * k1)`, the expression could multiply each of the 30 entries twice.
- `Vec6::Unit(i)` and `Vec5::Unit(i)` (`src/tube.cpp:46`, `src/tube.cpp:396`) build the basis vector eᵢ with zero-based i: e₁ is `Unit(0)`.

### NaN-safe comparisons

Every comparison with NaN is `false`, so `x <= 0` and `!(x > 0)` differ exactly when x is NaN. The code picks the form that sends NaN to the safe branch:

| Line | Code | NaN goes to |
| --- | --- | --- |
| `src/tube.cpp:82` | `!(H.determinant() > 0.0)` | the throw |
| `src/tube.cpp:307` | `if (d < best)` | never chosen as the best sample |
| `src/tube.cpp:368` | `return !(W.distance(gp, g) >= limit);` | counted as closer (ε fails) |
| `src/tube.cpp:390` | `!(opt.startFraction > 0.0)` | the `invalid_argument` throw |
| `src/tube.cpp:243` | `!std::isfinite(s)` | `false` |

One comparison is not NaN-safe: the step-3 guard `std::abs(diag_.detH - 1.0) > 1e-6 || diag_.orthogonalityError > 1e-6` (`src/tube.cpp:182`) lets a NaN holonomy through. The check at line 82 then catches it, so a NaN path still ends in an exception.
