## Build and CI

One `CMakeLists.txt` builds the library, the two plain apps and the unit tests by default, and an optional block adds everything that needs MuJoCo. `tools/ci.sh` is the definition of done: a change is finished when it passes. This section walks through both files line by line, then the helpers around them, and ends with the commands you will type every day.

### CMakeLists.txt: project, standard, build type

```bash
# CMakeLists.txt:1-10
cmake_minimum_required(VERSION 3.18)
project(se3pf LANGUAGES CXX)
set(CMAKE_CXX_STANDARD 17)
set(CMAKE_CXX_STANDARD_REQUIRED ON)

# Release unless asked otherwise: a build without -O runs the tests about 100 times slower (unoptimized Eigen), and
# the closed-loop tests tagged SLOW_IN_DEBUG are hidden in Debug. Use -DCMAKE_BUILD_TYPE=Debug for Eigen's checks.
if(NOT CMAKE_BUILD_TYPE AND NOT CMAKE_CONFIGURATION_TYPES)
    set(CMAKE_BUILD_TYPE Release CACHE STRING "Build type: Debug or Release" FORCE)
endif()
```

- `cmake_minimum_required(VERSION 3.18)` refuses older CMake. 3.18 is also the first version with `list(SORT ... COMPARE NATURAL)`, which `cmake/mujoco.cmake` uses. This machine has CMake 3.22.1 and GCC 11.4.
- `CMAKE_CXX_STANDARD 17` with `CMAKE_CXX_STANDARD_REQUIRED ON` makes C++17 mandatory; without `REQUIRED`, CMake would quietly fall back to an older standard on an old compiler. The generated flag is `-std=gnu++17`: CMake enables GNU extensions unless `CMAKE_CXX_EXTENSIONS` is OFF.
- The build-type block. With a single-configuration generator (Makefiles, Ninja) an empty `CMAKE_BUILD_TYPE` means no optimization flag at all. Unoptimized Eigen runs the tests about 100 times slower, so the default becomes Release. `CMAKE_CONFIGURATION_TYPES` is set only by multi-configuration generators (Visual Studio, Ninja Multi-Config), which choose the type at build time; the block leaves those alone.
- `CACHE STRING ... FORCE` writes the value into the cache file `CMakeCache.txt` of the build directory, where later runs and `cmake-gui` see it.

What Release and Debug change, as seen in `build-ci-mujoco/CMakeFiles/se3pf.dir/flags.make` and `build-ci-debug/CMakeFiles/se3pf.dir/flags.make`:

| Build type | Flags | Consequences |
| --- | --- | --- |
| Release | `-O3 -DNDEBUG` | optimized; `NDEBUG` turns off `assert` and Eigen's internal checks; `SLOW_IN_DEBUG` tests run by default |
| Debug | `-g` | debug symbols, no optimization; Eigen checks every index and size; Eigen's malloc guard around the control step is active; `[slow]` tests are hidden |

### CMakeLists.txt: Eigen and the warnings target

```bash
# CMakeLists.txt:12-20
# Eigen 3.4: minCoeff<PropagateNaN> (src/panda.cpp) and the 5- and 6-argument vector constructors are 3.4 only.
find_package(Eigen3 3.4 REQUIRED NO_MODULE)

# Warnings for every target of ours: -Wall -Wextra, and with -DSE3PF_WERROR=ON (tools/ci.sh) they are errors, so a
# warning fails the build however often it is repeated (a grep of the build log misses warnings of files that an
# incremental build did not recompile).
option(SE3PF_WERROR "Treat compiler warnings as errors" OFF)
add_library(se3pf_warnings INTERFACE)
target_compile_options(se3pf_warnings INTERFACE -Wall -Wextra $<$<BOOL:${SE3PF_WERROR}>:-Werror>)
```

- `find_package(Eigen3 3.4 REQUIRED NO_MODULE)` looks for Eigen's own `Eigen3Config.cmake` (here in `/usr/share/eigen3/cmake`, Eigen 3.4.0); `NO_MODULE` means "config mode", which provides the imported target `Eigen3::Eigen`. Version 3.4 is required because `minCoeff<PropagateNaN>` (`src/panda.cpp:88`) and the 5- and 6-argument vector constructors exist only from 3.4 on.
- `add_library(se3pf_warnings INTERFACE)` is a library with no sources. It exists only to carry compile options to whatever links it.
- `$<$<BOOL:${SE3PF_WERROR}>:-Werror>` is a generator expression, evaluated when the build files are generated: it becomes `-Werror` if the option is ON and nothing otherwise.
- Why a target instead of `add_compile_options(-Wall -Wextra -Werror)`: that command applies to every target in this directory and below, including Catch2, which `FetchContent` adds as a subdirectory. A warning in third-party code would then break the build. Each of our targets links `se3pf_warnings` explicitly, and `se3pf` links it `PRIVATE`, so the flags never propagate to consumers.
- Why `-Werror` and not only a grep of the build log: an incremental build recompiles only changed files, so a warning in an unchanged file never reappears in the log. With `-Werror` it fails the first build that sees it and cannot be forgotten.

### CMakeLists.txt: the library and the apps

```bash
# CMakeLists.txt:22-45
# The library: one .cpp per non-template header (types.hpp, spline.hpp, redundancy.hpp and controller.hpp are
# header-only).
add_library(se3pf
    src/se3.cpp
    src/metric.cpp
    src/path.cpp
    src/tube.cpp
    src/rigid_body.cpp
    src/panda.cpp
    src/rigid_body_example.cpp
    src/lift.cpp
    src/panda_example.cpp
)
target_include_directories(se3pf PUBLIC include)
target_link_libraries(se3pf PUBLIC Eigen3::Eigen PRIVATE se3pf_warnings)
# Lets a test forbid Eigen's heap allocations (Eigen::internal::set_is_malloc_allowed(false)) around the 1 kHz
# control step. Checked by an assert, so only in Debug builds; no effect unless a test switches it on.
target_compile_definitions(se3pf PUBLIC EIGEN_RUNTIME_NO_MALLOC)

# Apps
add_executable(rigid_body_sim apps/rigid_body_sim.cpp)
target_link_libraries(rigid_body_sim PRIVATE se3pf se3pf_warnings)
add_executable(panda_sim apps/panda_sim.cpp)
target_link_libraries(panda_sim PRIVATE se3pf se3pf_warnings)
```

- `add_library(se3pf ...)` without `SHARED` builds a static library, `libse3pf.a`. Headers that are templates or header-only (`types.hpp`, `spline.hpp`, `redundancy.hpp`, `controller.hpp`) have no `.cpp`.
- `target_include_directories(se3pf PUBLIC include)`: `PUBLIC` means "for me and for everyone who links me". Every target that links `se3pf` can write `#include "se3pf/panda.hpp"`.
- `target_link_libraries(se3pf PUBLIC Eigen3::Eigen PRIVATE se3pf_warnings)`. Eigen is `PUBLIC` because our headers include Eigen, so consumers need its include path; Eigen comes in as `-isystem /usr/include/eigen3`, which also silences warnings inside Eigen. The warnings target is `PRIVATE`: it applies to the library's own `.cpp` files only.
- `EIGEN_RUNTIME_NO_MALLOC` enables `Eigen::internal::set_is_malloc_allowed(false)`. Between `false` and `true`, any heap allocation inside Eigen fails an `assert`, so the check works in Debug only. The tests use it around the 1 kHz controller step (`tests/test_controller.cpp:831-838` and `tests/test_controller.cpp:1142-1149`). The same windows also count calls of a replaced global `operator new`, which works in Release too.
- The definition is `PUBLIC` so that every file that includes Eigen through `se3pf` sees the same macro. Eigen's inline functions must be compiled identically in every file (the one-definition rule); a macro set in some files and not in others would break that.
- The apps link `se3pf` and the warnings target, `PRIVATE` because nothing links an executable.

### CMakeLists.txt: the tests and FetchContent

```bash
# CMakeLists.txt:47-70
# Tests (Catch2 v3, downloaded the first time you configure; -DFETCHCONTENT_SOURCE_DIR_CATCH2=<dir> uses a local copy)
option(SE3PF_BUILD_TESTS "Build the tests" ON)
if(SE3PF_BUILD_TESTS)
    enable_testing()
    include(FetchContent)
    FetchContent_Declare(Catch2 GIT_REPOSITORY https://github.com/catchorg/Catch2.git GIT_TAG v3.5.2 GIT_SHALLOW TRUE)
    FetchContent_MakeAvailable(Catch2)
    add_executable(tests
        tests/rng_listener.cpp
        tests/test_se3.cpp
        tests/test_metric.cpp
        tests/test_path.cpp
        tests/test_spline.cpp
        tests/test_tube.cpp
        tests/test_rigid_body.cpp
        tests/test_panda.cpp
        tests/test_controller.cpp
        tests/test_rigid_body_example.cpp
        tests/test_lift.cpp
        tests/test_panda_example.cpp
    )
    target_link_libraries(tests PRIVATE se3pf Catch2::Catch2WithMain se3pf_warnings)
    add_test(NAME tests COMMAND tests)
endif()
```

- `FetchContent_Declare` describes where Catch2 lives: the Git tag `v3.5.2`, cloned shallow (`GIT_SHALLOW TRUE`, only the last commit). `FetchContent_MakeAvailable(Catch2)` downloads it at configure time into `<build>/_deps/catch2-src` and adds it to the build as a subproject.
- `-DFETCHCONTENT_SOURCE_DIR_CATCH2=<dir>` skips the download and uses a local source tree. The CI runs on this machine used `build/_deps/catch2-src` this way (see `build-ci-mujoco/CMakeCache.txt`).
- `Catch2::Catch2WithMain` is Catch2 with its own `main()`, so the test files contain only test cases. `tests/rng_listener.cpp` is part of both test programs.
- `enable_testing()` and `add_test(NAME tests COMMAND tests)` register the program with CTest. `ctest --test-dir build-ci-mujoco -N` lists two tests, `tests` and `tests_mujoco`; CTest runs each program as one test and reports pass or fail. Run the programs directly to see Catch2's output.
- `option(SE3PF_BUILD_TESTS ... ON)` lets a user skip the tests and the Catch2 download with `-DSE3PF_BUILD_TESTS=OFF`.

### CMakeLists.txt: the MuJoCo block

```bash
# CMakeLists.txt:74-98
option(SE3PF_WITH_MUJOCO "Build the MuJoCo simulation" OFF)
if(SE3PF_WITH_MUJOCO)
    include(cmake/mujoco.cmake)   # mujoco::mujoco and MENAGERIE_PANDA_DIR

    # Raw C API checks, without se3pf
    add_executable(mujoco_smoke apps/mujoco_smoke.cpp)
    target_link_libraries(mujoco_smoke PRIVATE mujoco::mujoco se3pf_warnings)

    # The Panda in MuJoCo (torque motors) and the closed loop of the Panda example on it
    add_library(se3pf_mujoco sim/mujoco_panda.cpp)
    target_include_directories(se3pf_mujoco PUBLIC sim)
    target_link_libraries(se3pf_mujoco PUBLIC se3pf mujoco::mujoco PRIVATE se3pf_warnings)
    target_compile_definitions(se3pf_mujoco PRIVATE SE3PF_MENAGERIE_PANDA_DIR="${MENAGERIE_PANDA_DIR}")

    add_executable(panda_mujoco apps/panda_mujoco.cpp)
    target_link_libraries(panda_mujoco PRIVATE se3pf_mujoco se3pf_warnings)

    # Separate test program: the default tests never need MuJoCo
    if(SE3PF_BUILD_TESTS)
        add_executable(tests_mujoco tests/rng_listener.cpp tests/mujoco/test_mujoco_panda.cpp)
        target_include_directories(tests_mujoco PRIVATE tests)
        target_link_libraries(tests_mujoco PRIVATE se3pf_mujoco Catch2::Catch2WithMain se3pf_warnings)
        add_test(NAME tests_mujoco COMMAND tests_mujoco)
    endif()

```

- Everything inside `if(SE3PF_WITH_MUJOCO)` exists only when you configure with `-DSE3PF_WITH_MUJOCO=ON`. A cached option keeps its value: once ON in a build directory, it stays ON there until you change it.
- `mujoco_smoke` links `mujoco::mujoco` and the warnings, and not `se3pf`.
- `se3pf_mujoco` is a second static library, `libse3pf_mujoco.a`. `target_include_directories(se3pf_mujoco PUBLIC sim)` lets its users write `#include "mujoco_panda.hpp"`. It links `se3pf` and MuJoCo `PUBLIC`, so `panda_mujoco` and `tests_mujoco` need to name only `se3pf_mujoco`.
- `SE3PF_MENAGERIE_PANDA_DIR="${MENAGERIE_PANDA_DIR}"` defines a string-literal macro for this library's own `.cpp`. The generated flag is `-DSE3PF_MENAGERIE_PANDA_DIR=\"/home/.../franka_emika_panda\"`; the escaped quotes make the value a C++ string literal.
- `tests_mujoco` gets the `tests` directory as an include path, for `test_helpers.hpp` and `panda_fixture.hpp`. It is a separate program, so the default `tests` never need MuJoCo.

### cmake/mujoco.cmake: finding MuJoCo

```bash
# cmake/mujoco.cmake:8-27
set(MUJOCO_DIR "" CACHE PATH "MuJoCo release directory (contains include/mujoco/mujoco.h and lib/libmujoco.so)")

if(NOT MUJOCO_DIR)
    file(GLOB _mujoco_candidates LIST_DIRECTORIES true "${PROJECT_SOURCE_DIR}/third_party/mujoco-*")
    if(NOT _mujoco_candidates)
        message(FATAL_ERROR
            "MuJoCo not found in ${PROJECT_SOURCE_DIR}/third_party. Run  bash tools/fetch_mujoco.sh  "
            "or pass -DMUJOCO_DIR=/path/to/mujoco-<version>.")
    endif()
    # Several versions side by side: take the newest (natural order, so 3.15.0 comes after 3.9.0) and say so (set
    # MUJOCO_DIR to choose).
    list(SORT _mujoco_candidates COMPARE NATURAL)
    list(GET _mujoco_candidates -1 _mujoco_dir)
    list(LENGTH _mujoco_candidates _mujoco_count)
    if(_mujoco_count GREATER 1)
        message(STATUS "Several MuJoCo versions in third_party/; using ${_mujoco_dir} (set MUJOCO_DIR to choose)")
    endif()
else()
    set(_mujoco_dir "${MUJOCO_DIR}")
endif()
```

- `set(MUJOCO_DIR "" CACHE PATH ...)` declares a cache variable with an empty default. `-DMUJOCO_DIR=/path/to/mujoco-3.15.0` sets it.
- Without it, `file(GLOB ... "third_party/mujoco-*")` lists the matching directories. `list(SORT ... COMPARE NATURAL)` compares digit runs as numbers, so 3.15.0 sorts after 3.9.0 (a plain string sort would put "3.15" first). `list(GET ... -1)` takes the last, the newest.
- `message(FATAL_ERROR ...)` stops the configure with a message that names the fix: run the fetch script or pass the directory.

```bash
# cmake/mujoco.cmake:29-48
# Check the files directly instead of find_library: a cached search result would survive a change of MUJOCO_DIR.
set(MUJOCO_INCLUDE_DIR "${_mujoco_dir}/include")
set(MUJOCO_LIBRARY "${_mujoco_dir}/lib/libmujoco.so")
if(NOT EXISTS "${MUJOCO_INCLUDE_DIR}/mujoco/mujoco.h" OR NOT EXISTS "${MUJOCO_LIBRARY}")
    message(FATAL_ERROR "${_mujoco_dir} is not a MuJoCo release directory (no include/mujoco/mujoco.h or lib/libmujoco.so)")
endif()
get_filename_component(MUJOCO_LIBRARY_DIR "${MUJOCO_LIBRARY}" DIRECTORY)

if(NOT TARGET mujoco::mujoco)
    add_library(mujoco::mujoco SHARED IMPORTED)
    # SYSTEM include directory: -Wall -Wextra in our targets should not report warnings from MuJoCo's headers.
    set_target_properties(mujoco::mujoco PROPERTIES
        IMPORTED_LOCATION "${MUJOCO_LIBRARY}"
        INTERFACE_INCLUDE_DIRECTORIES "${MUJOCO_INCLUDE_DIR}"
        INTERFACE_SYSTEM_INCLUDE_DIRECTORIES "${MUJOCO_INCLUDE_DIR}")
    # Run without LD_LIBRARY_PATH: every executable that links MuJoCo records its lib/ directory as a runtime
    # search path. (CMake adds it to the build-tree RPATH by itself; the explicit option also covers installed
    # copies and builds with CMAKE_SKIP_BUILD_RPATH.)
    set_property(TARGET mujoco::mujoco PROPERTY INTERFACE_LINK_OPTIONS "LINKER:-rpath,${MUJOCO_LIBRARY_DIR}")
endif()
```

- The files are checked directly instead of with `find_library`. `find_library` stores its result in the cache, and a later change of `MUJOCO_DIR` would not search again.
- `add_library(mujoco::mujoco SHARED IMPORTED)` declares an imported target: a library built elsewhere, described by properties. `IMPORTED_LOCATION` is the `.so` file, and `INTERFACE_INCLUDE_DIRECTORIES` its headers. `INTERFACE_SYSTEM_INCLUDE_DIRECTORIES` turns them into `-isystem`, so warnings inside MuJoCo's headers do not fail our `-Werror` build.
- `if(NOT TARGET mujoco::mujoco)` makes a second `include()` of this file harmless.
- The run path. A program that links a shared library must find it again when it starts. `LINKER:-rpath,<dir>` becomes `-Wl,-rpath,<dir>` on every executable that links `mujoco::mujoco`, directly or through `se3pf_mujoco`. `readelf -d build-ci-mujoco/panda_mujoco` shows `RUNPATH [/home/jaiden/Desktop/SE3_pathFollowing/third_party/mujoco-3.15.0/lib]`.
- The link line of `panda_mujoco` holds `-Wl,-rpath` twice: once from this property and once from CMake's own build-tree path. The explicit one also survives an install and `CMAKE_SKIP_BUILD_RPATH`. Without either, starting the program fails with "error while loading shared libraries: libmujoco.so.3.15.0" (the library's SONAME).

### Test tags: [slow], SLOW_IN_DEBUG and [.timing]

```cpp
// tests/test_helpers.hpp:15-23
// A closed loop of 10 000-20 000 control steps takes a minute in a Debug build (unoptimized Eigen is 30-100 times
// slower) and a fraction of a second in Release. Tests tagged SLOW_IN_DEBUG are hidden in Debug ("[.slow]"; run
// them with ./build-dbg/tests "[slow]") and run by default in Release, so tools/ci.sh still checks every number of
// the design doc's Closed loops table. Each hidden closed loop has a short stand-in that runs in Debug too.
#ifdef NDEBUG
#define SLOW_IN_DEBUG "[slow]"
#else
#define SLOW_IN_DEBUG "[.slow]"
#endif
```

- In Catch2, a tag that starts with a dot hides a test from the default run: `"[.slow]"` hides it and still tags it `slow`, so `./build-dbg/tests "[slow]"` runs it. In Release the macro expands to a plain `"[slow]"`, and the test runs by default.
- `NDEBUG` is defined in Release and not in Debug, which is what the `#ifdef` tests. A 20 s closed loop takes a fraction of a second in Release and about a minute in Debug.
- `[.timing]` is always hidden. Those tests call `SKIP("timing is meaningful in a Release build only")` in Debug and run with `./build-rel/tests "[.timing]"`.

| Program and build | Test cases run by default | Hidden |
| --- | --- | --- |
| `tests`, Release | 132 (6 tagged `[slow]` among them) | 5 `[.timing]` |
| `tests`, Debug | 126 | 6 `[.slow]`, 5 `[.timing]` |
| `tests_mujoco`, Release | 15 (2 tagged `[slow]`) | none |
| `tests_mujoco`, Debug | 13 | 2 `[.slow]` |

The timing tests measured here: `Controller<PandaArm>::step` 12.1 µs per call (the paper reports 27 µs; the bound is 100 µs, the 1 kHz budget 1000 µs), `Controller<RigidBody>::step` 9.3 µs (bound 50 µs), the tube's `outputs()` + `JPsi()` 1.6 µs (bound 20 µs), `PandaArm::output` with J_b 0.25 µs (bound 2 µs), and the `PandaExample` construction 0.025 s (bound 0.5 s).

Random inputs repeat exactly. `tests/rng_listener.cpp` reseeds the tests' shared generator before every run of a test case:

```cpp
// tests/rng_listener.cpp:12-26
namespace {

    class ReseedTestRng : public Catch::EventListenerBase {
        public:
            using Catch::EventListenerBase::EventListenerBase;

            void testCasePartialStarting(Catch::TestCaseInfo const&, std::uint64_t) override
            {
                testing::rng().seed(testing::kRngSeed);
            }
    };

}  // namespace

CATCH_REGISTER_LISTENER(ReseedTestRng)
```

- `class ReseedTestRng : public Catch::EventListenerBase` derives from Catch2's listener base. `using ...::EventListenerBase;` inherits its constructors. `override` asks the compiler to confirm that a virtual function with this exact signature exists in the base; a typo becomes a compile error instead of a function that is never called.
- `testCasePartialStarting` runs before each leaf section of each test case, so a test sees the same random numbers alone, in the full suite, or with `--order rand`. `CATCH_REGISTER_LISTENER` registers the class once per program.
- Catch2's own line "Randomness seeded to: ..." is Catch2's generator, not ours; it changes per run and does not affect our inputs.

### tools/ci.sh, stage by stage

```bash
# tools/ci.sh:12-13, 15-18, 21-39
set -euo pipefail
cd "$(dirname "$0")/.."
# ...
extra=()
if [[ -n "${CATCH2_SRC:-}" ]]; then
    extra+=("-DFETCHCONTENT_SOURCE_DIR_CATCH2=${CATCH2_SRC}")
fi
# ...
stage() {
    local dir="$1" cfg="$2"
    shift 2
    echo "== ${dir}: configure (${cfg})"
    cmake -S . -B "$dir" -DCMAKE_BUILD_TYPE="$cfg" -DSE3PF_WERROR=ON ${extra[@]+"${extra[@]}"} "$@" \
        > "$dir.configure.log" 2>&1 \
        || { cat "$dir.configure.log"; echo "CI FAILED: configure (${dir})"; exit 1; }

    echo "== ${dir}: build"
    if ! cmake --build "$dir" -j > "$dir.build.log" 2>&1; then
        grep -E "error|warning" "$dir.build.log" | head -40 || tail -40 "$dir.build.log"
        echo "CI FAILED: build (${dir})"
        exit 1
    fi
    if grep -E "warning:" "$dir.build.log" | grep -v "/_deps/"; then
        echo "CI FAILED: compiler warnings (${dir}); the definition of done allows none"
        exit 1
    fi
}
```

The shell mechanisms, since they are easy to misread:

- `set -euo pipefail`: stop at the first failing command (`-e`), treat an unset variable as an error (`-u`), and let a pipeline fail if any command in it fails (`pipefail`).
- `cd "$(dirname "$0")/.."` moves to the project root, so the script works from any directory.
- `extra=()` is a bash array. `${extra[@]+"${extra[@]}"}` expands to the array's elements if it has any and to nothing otherwise. Plain `"${extra[@]}"` on an empty array is an "unbound variable" error under `set -u` in bash before 4.4.
- `local dir="$1" cfg="$2"; shift 2` takes the first two arguments; `"$@"` passes the rest on to `cmake`.
- `> "$dir.configure.log" 2>&1` sends standard output and errors to one log file. `|| { ...; exit 1; }` runs the block only if the command failed.
- The warning grep is a second net behind `-Werror`: any `warning:` line outside `/_deps/` (Catch2) fails the stage.

```bash
# tools/ci.sh:50-73
for cfg in Debug Release; do
    dir="build-ci-${cfg,,}"
    stage "$dir" "$cfg"
    echo "== ${dir}: tests"
    "./$dir/tests" || { echo "CI FAILED: tests (${cfg})"; exit 1; }
done

# The apps write their logs into the build directory, so out/ is not touched.
app build-ci-release rigid_body_sim build-ci-release/out
app build-ci-release panda_sim build-ci-release/out

if compgen -G "third_party/mujoco-*" > /dev/null; then
    dir="build-ci-mujoco"
    stage "$dir" Release -DSE3PF_WITH_MUJOCO=ON
    app "$dir" mujoco_smoke third_party/mujoco_menagerie/franka_emika_panda/panda_nohand.xml
    echo "== ${dir}: tests_mujoco"
    "./$dir/tests_mujoco" || { echo "CI FAILED: tests_mujoco"; exit 1; }
    # The full runs (20 s each, about 15 s in all) and every check of their summary
    app "$dir" panda_mujoco "$dir/out"
else
    echo "== MuJoCo: skipped (no third_party/mujoco-*; bash tools/fetch_mujoco.sh adds it)"
fi

echo "CI PASSED"
```

The helper `app` (`tools/ci.sh:42-48`) runs one program with its output in `<dir>.<name>.log` and checks only its exit code.

The stages in order:

1. Debug: configure `build-ci-debug` with `-DSE3PF_WERROR=ON`, build, grep for warnings, run `tests` (126 test cases, `[slow]` hidden). `${cfg,,}` lower-cases `Debug` to `debug` for the directory name.
2. Release: the same in `build-ci-release`, running all 132 test cases including `[slow]`.
3. The apps: `rigid_body_sim` and `panda_sim` from `build-ci-release`, with output in `build-ci-release/out`, so `out/` is never touched. Only the exit code is checked; on failure the script shows the log's `FAIL` or `error` lines, or its last 20 lines.
4. MuJoCo, only if `compgen -G "third_party/mujoco-*"` finds a match (`compgen -G` prints the matches of a glob and fails if there are none). It configures and builds `build-ci-mujoco` in Release with `-DSE3PF_WITH_MUJOCO=ON`, then runs `mujoco_smoke` on `panda_nohand.xml`, `tests_mujoco`, and `panda_mujoco` with output in `build-ci-mujoco/out`. Every check of that summary must pass.
5. "CI PASSED".

Each stage leaves its logs at the project root: `<dir>.configure.log`, `<dir>.build.log` and `<dir>.<app>.log`, where `<dir>` is `build-ci-debug`, `build-ci-release` or `build-ci-mujoco` (for example `build-ci-release.panda_sim.log` and `build-ci-mujoco.panda_mujoco.log`). `.gitignore` excludes them all. The whole script takes about 3 minutes (`README.md`).

### tools/fetch_mujoco.sh

```bash
# tools/fetch_mujoco.sh:9-17
set -euo pipefail

# --- Pins (update together with the Python package in .venv: pip install mujoco==<version>) ---
MUJOCO_VERSION="${MUJOCO_VERSION:-3.15.0}"
# sha256 of mujoco-3.15.0-linux-x86_64.tar.gz, as published with the release; checked in addition to the
# release's own .sha256 file. Only used for the default version.
MUJOCO_SHA256_PINNED="319943b332fd84c968f655f695d8f4b03cc6a68f658bacd0591f0a552744e497"
# google-deepmind/mujoco_menagerie main on 2026-10-07; franka_emika_panda last changed in 71f066a (2026-07-04).
MENAGERIE_COMMIT="${MENAGERIE_COMMIT:-0059d4335f8156206f63a35662313385f7ad6d74}"
```

`"${MUJOCO_VERSION:-3.15.0}"` means "the environment's value if set and not empty, else 3.15.0", so `MUJOCO_VERSION=3.16.0 bash tools/fetch_mujoco.sh` overrides the pin for one run. The Menagerie is pinned to one commit, not a branch, so the model cannot change under you.

What the script does:

1. If `<dest>/mujoco-3.15.0` already holds `lib/libmujoco.so` and `include/mujoco/mujoco.h`, it is kept. Otherwise the tarball is downloaded into a temporary directory from `mktemp -d`; `trap 'rm -rf "$tmp"' EXIT` deletes that directory whenever the script exits, also on an error. `curl -fsSL --retry 3` fails on HTTP errors, prints nothing but errors, follows redirects and retries three times.
2. The SHA-256 of the download is checked twice: against the release's own `.sha256` file (if the release has none, the script warns and relies on the pin) and, for version 3.15.0, against the hash pinned in the script. A tampered or truncated download stops the script.
3. The tarball is unpacked into a staging directory and moved into place only when complete, so an interrupted run never leaves a half-extracted library that CMake would accept.
4. The Menagerie checkout uses `git sparse-checkout` in cone mode for the single directory `franka_emika_panda` (cone mode also checks out the files at the repository root), a fetch of depth 1 at the pinned commit, and `--filter=blob:none`, which downloads file contents only for checked-out paths. `checkout -q FETCH_HEAD` checks out that commit as a detached head.
5. Re-running is safe: a complete library and a checkout at the pinned commit are both kept.

Pins: MuJoCo 3.15.0 with SHA-256 `319943b3...e497`, Menagerie commit `0059d433...6d74`. The Python package must have the same version as the C library, so that a model and its numbers agree between C++ and Python.

### The Python environment

The MuJoCo tools run from a virtual environment in `.venv` (Python 3.13.5 here), created once:

```bash
python3 -m venv .venv
.venv/bin/pip install -r tools/requirements-mujoco.txt
```

`tools/requirements-mujoco.txt` pins `mujoco==3.15.0`, `numpy==2.5.4`, `matplotlib==3.11.2`, `imageio==2.38.1`, `imageio-ffmpeg==0.6.0` and `pillow==12.3.0`. The two plain plot scripts need only numpy and matplotlib. Off-screen rendering works with `MUJOCO_GL=egl` (no window); `MUJOCO_GL=osmesa` does not work on this machine (`third_party/README.md`).

### When something goes wrong

| Symptom | Cause | Fix |
| --- | --- | --- |
| "MuJoCo not found in .../third_party" at configure | `-DSE3PF_WITH_MUJOCO=ON` without a fetched MuJoCo | `bash tools/fetch_mujoco.sh`, or `-DMUJOCO_DIR=...` |
| "No panda_nohand.xml in ..." at configure | the Menagerie checkout is missing | the same script, or `-DMENAGERIE_PANDA_DIR=...` |
| configure hangs or fails at Catch2 | no network for `FetchContent` | `-DFETCHCONTENT_SOURCE_DIR_CATCH2=<local Catch2>` or `CATCH2_SRC=...` for `ci.sh` |
| "Could not find a configuration file for package "Eigen3" that is compatible with requested version "3.4"" | Eigen older than 3.4, or no Eigen CMake config | install Eigen 3.4 |
| a warning stops the build | `-DSE3PF_WERROR=ON` in that build directory | fix the warning; the CI allows none |
| the tests take minutes | a Debug build: unoptimized Eigen | use the Release directory for routine runs |
| "error while loading shared libraries: libmujoco.so.3.15.0" | the MuJoCo directory was moved or deleted after linking (the run path is absolute) | reconfigure and rebuild, so the run path points at the current directory |
| a plot script says "missing columns ...; rerun ..." | the logs come from an older build | rerun the app with the current build |
| `plot_panda.py` says the limits file does not reproduce `joint_margin` | `panda_limits.csv` and the logs come from different builds | rerun `panda_sim` into one directory |
