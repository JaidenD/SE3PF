## Design decisions and C++

Each design choice in this layer guards against a concrete risk: a wrong geodesic, a dangling object, a heap allocation at 1 kHz, or an open spline. This section states each choice, the C++ feature behind it, and what breaks without it.

### C++ mechanisms of this layer

The table lists every C++ feature the layer uses, where it first appears, and what goes wrong without it.

### Why closed forms only

`Metric` implements only W = diag(w_R I, w_p I) because Example 1 gives exact closed forms for it, and both examples use it. A general left-invariant W needs Exp_I and Γ from the geodesic ODEs (eq:Exp-ode, eq:Gamma-ode) integrated by RK4, and Log_I by Newton's method on top (`docs/DESIGN.md:147`).

- Speed: the Panda control step takes about 12 µs in Release (`README.md:71`). The design doc estimates 56 µs for one RK4 Exp plus Γ (`docs/DESIGN.md:149`), and the step needs several per cycle.
- Exactness: the closed-form `Log` inverts `Exp` to rounding (round trip 6.6e-16 in the test). With ODEs, `Log` would invert only the discretized `Exp`.
- Scope: milestone 11 (general W) is deferred (`TICKETS.md:7`). Until then the constructor refuses every other W.

The refusal is essential because nothing downstream would notice a wrong W. For W = diag(1, 1, 2, 1, 1, 1), both paths still have constant speed: ω̃_z is constant on both curves (cos α − 1 and 1), and so is ω̃_x² + ω̃_y². `constantSpeed` would pass, and Exp, Log and Γ would silently compute the geodesics of a different metric (`src/metric.cpp:10-11`, `tests/test_metric.cpp:49`).

### Why Metric is a class with const member functions

W is private and set once, in the constructor, after the product-type check. No code can change it afterwards, so every `Metric` object is a valid product-type metric for its whole life.

Every member function except the constructor and the static `product` is `const`. `Tube::metric()` returns the metric as `const Metric&` (`include/se3pf/tube.hpp:61`), and `Path` constructors take `const Metric& W`; through those references only `const` members can be called.

`W_` itself is not declared `const`. Being private, with no member function that writes it, already makes it read-only. A `const Mat6 W_` would add nothing and would delete `Metric`'s copy assignment, so `a = b;` between two metrics would stop compiling.

`Tube` copies the metric (`Metric metric_;`, `include/se3pf/tube.hpp:94`) but keeps a reference to the path (`include/se3pf/tube.hpp:93`). A `Metric` is a 288-byte value (`sizeof`, measured), so a copy is cheap and cannot dangle. A `Path` is abstract, and storing it by value would require its concrete type. So `Tube` keeps a `const Path&` and deletes the constructor that would bind it to a temporary (`include/se3pf/tube.hpp:56`).

The class is also the seam for a general W. `Exp`, `Log` and `Gamma` could integrate the geodesic ODEs behind the same signatures, and no caller would change.

### operator() versus inner() and flat()

`W(v, w)` and `W(v)` exist so code can mirror the paper's notation W(v, w) = ⟨v, w⟩_W and W♭v. They are one-line forwards to `inner` and `flat`, and the test checks they return identical values (`tests/test_metric.cpp:33-34`).

The library itself uses the named forms (`metric_.inner(e, z)` at `src/tube.cpp:254`, `metric_.flat(e)` at `src/tube.cpp:291`). Overloads with one and two parameters are told apart by the number of arguments, so both can be called `operator()`.

### Why types.hpp aliases

The aliases put every size in one file and make each signature self-describing: `Mat65` says "the normal frame", not just "a matrix". They are fixed-size types, which matters in three ways.

- No heap: the control step must not allocate. `CMakeLists.txt:39` defines `EIGEN_RUNTIME_NO_MALLOC`, so a test can switch Eigen's allocations off around a step; in a Debug build an allocation then fails an assert.
- Compile-time checks: `Vec7 b = a;` with `a` a `Vec6` stops compilation with Eigen's `YOU_MIXED_MATRICES_OF_DIFFERENT_SIZES` (checked with g++).
- Speed: loops over 6 or 7 entries are unrolled; no size is read at run time.

With C++17 and Eigen 3.4, `std::vector<Mat65>` needs no aligned allocator: C++17's aligned `new` handles the alignment that Eigen's vectorized types need.

### Why the spline is header-only

`PeriodicHermite<T>` is a template, and the compiler can only generate `PeriodicHermite<Mat65>` where it sees the full definition. If `eval` were in a `.cpp`, every other file would compile against the declaration and the linker would report "undefined reference" for each `T`.

Explicit instantiation of the three types in a `.cpp` would also work, but would fix the list of `T` forever. Member functions defined inside the class body are implicitly `inline`, so including the header in many `.cpp` files is legal (`CMakeLists.txt:22-23` lists the header-only files).

### Why Path is abstract with a virtual destructor

`Tube` and `Lift` take any `const Path&`, so one `Tube` class serves both curves and any future curve. The curve is chosen at run time; the virtual call costs a few nanoseconds against microseconds of Newton projection.

The alternative, `Tube<PathType>`, would fix the curve at compile time, as `Controller<System>` does for the system. The design doc chose run-time polymorphism for `Path` and `RedundancyOutput` and templates for the controller (`docs/DESIGN.md:499`).

The virtual destructor makes `delete` through a base pointer call the subclass's destructor. `std::unique_ptr<Path> p = std::make_unique<ConingCircle>(...)` is safe only because of it, and that is exactly the case g++ does not warn about.

### Why σ is computed in the constructor, and why it throws

σ is a constant of the curve, and every call of `pose`, `velocity` and `acceleration` divides by it. Computing it once in the constructor saves the work and establishes the class invariant: s = σθ is arc length.

A constructor cannot return an error code, so it throws `std::invalid_argument`. Then an object with a wrong σ never exists, and no member function needs to check validity.

Throwing is allowed here because construction is offline. The online functions `pose`, `velocity` and `acceleration` never throw. One gap remains: σ = 0 (a path that is a single point) is accepted, and every later division by σ gives NaN.

### Why node n repeats node 0

A periodic spline is continuous across the seam s = L ≡ 0 only if interval n − 1 ends at node 0's value and slope. Storing node n as a copy of node 0 makes the last interval end there, so the interpolant is a C¹ periodic function.

`build` overwrites node n instead of checking it. The offline constructions close only up to their accuracy: the Panda frame's node values close to 3.7e-11 (`TICKETS.md:36`; 3.68e-11 measured), the lift's to 1.5e-13 (`build-ci-release.panda_sim.log`). The spline must close exactly anyway, or `eval(L)` and `eval(0)` would disagree.

Because the spline hides the closure gap, the gap is measured before `build`: `diag_.closureGap` at `src/tube.cpp:208` and `src/lift.cpp:169`. The test "closes exactly" checks `eval(L) == y_0` to 0.0, bit for bit.

### Failure reporting: throw offline, return a value online

The layer follows one rule. Offline code (constructors, `build`, `centralDifferences`) throws; online code returns a value that says it failed.

| Function | Failure | Reported as |
| --- | --- | --- |
| `Metric::Metric`, `Metric::product` | W not of product type, w_R or w_p not positive or not finite | `std::invalid_argument` |
| `ConingCircle`, `TumblingCircle` | speed not constant | `std::invalid_argument` |
| `PeriodicHermite::build` | L ≤ 0 or NaN, fewer than 2 values, size mismatch | `std::invalid_argument` |
| `PeriodicHermite::centralDifferences` | fewer than 5 samples | `std::invalid_argument` |
| `Metric::Log` | tr R < −1 + 1e-12, that is π − θ below about 1e-6 | returns `false` |
| `Metric::distance` | `Log` failed | returns NaN |
| `PeriodicHermite::eval` | s not finite | NaN in every entry |
| `PeriodicHermite::eval` | `build` never called | `assert` in Debug; undefined in Release |
| `logSO3`, `expSO3`, `Jr`, `JrInv` | none | always a value |

Exceptions are avoided online because their cost is unpredictable and a robot controller must decide what to do on failure itself. The design doc offered `std::optional<OutputState>` as an alternative (`docs/DESIGN.md:500`); the code uses `bool` plus out-parameters throughout.
