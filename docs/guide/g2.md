## Trace drills

A trace drill runs one test under a debugger, stops on the lines that implement one equation, and compares the live values with the numbers below. Every number in this section was read from a real run: the project's Debug build `build-ci-debug` under gdb in batch mode, or a small program linked against the Release library. Quantities near rounding level can differ in their last digits between builds; Trace 2 shows how much, and why.

### Build for the debugger

A debugger needs symbols (`-g`) and, to show local variables, no optimization. CMake's build types give you three choices.

| Build type | Flags | Speed | What the debugger shows |
| --- | --- | --- | --- |
| `Debug` | `-g`, no `-O`, Eigen's asserts on | a Panda step about 2 ms; the full suite about 45 s | every local, every line in order; use this for traces |
| `RelWithDebInfo` | `-O2 -g -DNDEBUG` | about as fast as Release | many locals print as `<optimized out>`, lines jump around; use it only to break inside a 20 s closed loop |
| `Release` | `-O3 -DNDEBUG` | a Panda step about 12 µs | no symbols; not for debugging |

```bash
cd ~/Desktop/SE3_pathFollowing
cmake -S . -B build-dbg -DCMAKE_BUILD_TYPE=Debug
cmake --build build-dbg -j8
./build-dbg/tests --list-tests "Tube: initial frame*"     # check a name filter before you debug it
```

A Debug build takes about 0.9 GB of disk. If `bash tools/ci.sh` has run, `build-ci-debug` is already one, built from the current sources; replace `build-dbg` by it in every command below.

Three Catch2 rules matter when you pass a test name to the debugger:

- `*` is a wildcard only at the start or the end of a name, so `"Tube: J_Psi*"` selects both J_Ψ tests.
- A comma separates test specs, so a name that contains one needs `\,`: `"simulate (Panda): the paper's run\, first second*"`.
- Tests tagged `[.slow]` (hidden in Debug, `tests/test_helpers.hpp:19-23`) still run when you name them explicitly.

`./build-dbg/tests -b "<name>"` (`--break`) makes Catch2 stop in the debugger at the first failing check. Combined with a mutation drill, that puts you on the failing line with all its values in scope.

Without a debugger, `-s` prints every check with its `CAPTURE`d values, also the passing ones: in a Release build, `./build-rel/tests "Tube: the frame closes*" -s` shows `sci(gap) := "3.678e-11"` for the Panda tube (a Debug build shows `"3.972e-11"`; Trace 2 explains the difference).

Set a breakpoint by clicking left of a line number, then press F5. Eigen has no gdb pretty printer installed on this machine, so a matrix shows as its raw storage. Add a watch expression such as `out.A.m_storage.m_data.array`, or type `-exec print out.xi.m_storage.m_data.array` in the Debug Console.

That array is column-major (Eigen's default): for a `Mat65`, entries 0 to 5 are column 0. A `std::vector` prints through the standard library's printers, so `basis.size()` and `basis[0].m_storage.m_data.array` both work.

### Plain gdb

The same session at the terminal: start gdb with the test name as the program's argument, set breakpoints by `file:line`, run, print.

```bash
cd ~/Desktop/SE3_pathFollowing
gdb --args ./build-dbg/tests "Tube: initial frame*"
# at the (gdb) prompt:
#   break tube.cpp:51
#   run
#   print basis.size()
#   print basis[0].m_storage.m_data.array
#   continue
#   finish
#   quit
```

For a repeatable trace, put the commands in a file and use batch mode. A breakpoint's `commands ... end` block runs every time it is hit, which is how the traces below print loop iterations without stopping.

```bash
cd ~/Desktop/SE3_pathFollowing
cat > /tmp/trace3.gdb <<'EOF'
set pagination off
break tube.cpp:270
commands
silent
printf "k=%d  s=%.12f  phi=% .6e  dphi=% .9f\n", k, s, phi, dphi
continue
end
break tube.cpp:274
commands
silent
printf "converged: k=%d  s=%.15f\n", k, s
print e.m_storage.m_data.array
quit
end
run "Controller<PandaArm>: a beta that depends on eta gets*"
EOF
gdb -batch -x /tmp/trace3.gdb ./build-dbg/tests
```

Two gdb habits save time. In a `commands` block, gdb ignores every command after one that resumes the program (`continue`, `next`, `step`), so put `continue` last; to end the session once you have what you need, put `quit` in the block of the last breakpoint, as the script above does. Break on a line with code, not on a comment: gdb moves the breakpoint to the next code line, where block-scoped variables such as `plus` may already be out of scope.

### Trace 1: the initial frame N₀(0) by Gram–Schmidt (Lemma 1, step 1)

- Run: `./build-dbg/tests "Tube: initial frame*"`. The test builds `rigidTube()` first, then `pandaTube()`, so the breakpoint is hit twice.
- Break: `src/tube.cpp:51`, the first line after the Gram–Schmidt loop and its size check in `initialFrame`; then `finish` to see the returned `Mat65`.
- Watch: `basis.size()`, `z0.m_storage.m_data.array`, `basis[0].m_storage.m_data.array`, and the returned value.

```cpp
// src/tube.cpp:36-49
            std::vector<Vec6> basis;
            auto add = [&](Vec6 x) {
                for (const Vec6& b : basis)
                    x -= W.inner(b, x) * b;
                const double nx = W.norm(x);
                if (nx > 1e-8)
                    basis.push_back(x / nx);
            };
            add(z0);
            for (int i = 0; i < 6; ++i)
                add(Vec6::Unit(i));
            // seven vectors in R^6: exactly one e_i drops out (e_5 on the rigid-body path, e_6 on the Panda path)
            if (basis.size() != 6)
                throw std::runtime_error("Tube: Gram-Schmidt did not give six W-orthonormal vectors");
```

| Hit | `z0` = ζ_γ(0) | `basis.size()` | dropped | the returned N₀(0), column by column |
| --- | --- | --- | --- | --- |
| 1, rigid body (W = I) | (0.57735, −0, 0.57735, 0, 0.57735, 0) = (e₁ + e₃ + e₅)/√3 | 6 | e₅ | (2, 0, −1, 0, −1, 0)/√6, e₂, (0, 0, 1, 0, −1, 0)/√2, e₄, e₆ |

Why the Panda's first column is 10 e₁: ζ_γ(0) has no ω_x, so e₁ is already W-orthogonal to it, and ‖e₁‖_W = √0.01 = 0.1. The `-0` in z0 is a negative zero from `-std::sin(0)` in the tumbling circle's ω̃ = (cos θ, −sin θ, 1); it compares equal to 0.

Question: the lambda `add` captures `basis` and `W` by reference (`[&]`). What would `[=]` (capture by copy) do to `basis.push_back`? (It would not compile: a by-copy capture is `const` inside a non-`mutable` lambda.)

Question: why is `skewError` exactly zero and not 1e-17? (Entry (i, j) of v uᵀ − u vᵀ is v_i u_j − u_i v_j, and entry (j, i) is v_j u_i − u_j v_i: the same two products, since floating-point multiplication commutes exactly, subtracted in the other order. And why do Debug and Release differ in the 11th digit? (Not because optimization changes the mathematics: the PandaExample's tube gives 3.577e-11 in both builds. Its inputs differ from the fixture's in the last bit: W from 0.1 × 0.1 = 0.010000000000000002 instead of 0.01, and R₀ from forward kinematics, 1.1e-16 from the typed one. At the 1e-11 level the digits depend on such last-bit differences and on the order of floating-point operations, which an optimized build changes for some inputs and not for others; building with `-DEIGEN_DONT_VECTORIZE` moves the fixture's gap to 3.52e-11. That is why the test bound, 1e-9, sits far above.)
