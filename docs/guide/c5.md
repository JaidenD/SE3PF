## Design decisions and C++

The controller's C++ follows from three requirements of the 1 kHz loop: every size known at compile time, no heap allocation, and no exceptions. This section explains each decision, the alternative it rules out, and the C++ mechanism behind it.

### A template for the controller, virtual functions for the path and β

The controller is a class template over `System`, while `Path` and `RedundancyOutput` are abstract classes with virtual functions. The difference is not taste; it follows from what varies.

| | `Controller<System>` | `Path`, `RedundancyOutput` |
| --- | --- | --- |
| What varies between implementations | n (6 or 7) and the type of q (`Pose` or `Vec7`) | only the formulas; the types are always `Pose`/`Vec6` of s, or `Vec7` |
| When the choice is made | at compile time (`Controller<RigidBody>`) | at run time (which path, which β) |
| Mechanism | template instantiation; `static` member functions | virtual call through a pointer or reference |
| Cost of a call | direct call, can be inlined | one indirect call (nanoseconds) |
| Where the code lives | header only (`include/se3pf/controller.hpp`) | compiled once (`src/path.cpp`, `src/lift.cpp`) |

Why a template for the controller:

- n sets every matrix size: `Mat<6, n>` for J_b, `MatN` for A, `VecN` for q̇, q̈* and μ. With n a compile-time constant, Eigen allocates these on the stack and can unroll its small loops. With run-time sizes (`Eigen::MatrixXd`) every matrix and many temporaries would live on the heap, so the step would allocate many times per cycle.
- `Config` differs in kind: a 4 × 4 pose for the rigid body, a 7-vector for the Panda. A virtual function cannot return a different type in each derived class, so an abstract `System` base class could not even declare `retract`.
- `System::output` and `System::retract` are `static`: the controller calls them on the type, with no object and no virtual table.

Why virtual functions for the path and β:

- Their interfaces have the same types for every implementation, so one compiled `Tube` (`src/tube.cpp`) serves both example paths, and one `Controller<PandaArm>` serves `LiftRedundancy`, `CouplingRedundancy` and the test's `WavyCouplingOutput`.
- A virtual call costs an indirect jump. A moving Panda step makes three `RedundancyOutput::evaluate` calls (one per projection) and a few `Path` calls per Newton update: nanoseconds against a step of 9 to 12 µs (measured on this machine).
- Making them template parameters too would multiply the instantiations (`Controller<PandaArm, LiftRedundancy>`, ...) and force the tube into a header, to save a few nanoseconds per call.

A template's body must be visible wherever it is instantiated, so `controller.hpp` has no `.cpp` (`CMakeLists.txt:22-23`). Each file that uses `Controller<RigidBody>` compiles its own copy; the linker keeps one.

### The three template pitfalls, with the lines where the code avoids them

All three were reproduced with GCC 11.4 on a copy of the header; the messages are the ones you will see.

1. `typename` before a dependent type. Inside the template, `System::Config` could be a type or a static value until `System` is known; C++ assumes a value. The code writes `using Config = typename System::Config;` (`include/se3pf/controller.hpp:141`), and the tests write `typename Controller<System>::OutputState o;` (`tests/test_controller.cpp:170`). Without it GCC says: `need 'typename' before 'System::Config' because 'System' is a dependent scope`.
1. `.template` before a member template of a dependent object. `out.A.topRows<6>()` would parse as `(out.A.topRows < 6) > ()`, a comparison. The code writes `out.A.template topRows<6>()` (`include/se3pf/controller.hpp:229`), `yDot.template segment<5>(1)` (`include/se3pf/controller.hpp:257`) and `mu.template segment<5>(1)` (`include/se3pf/controller.hpp:294`). Without it GCC says only `expected primary-expression before ')' token`, followed by `invalid operands of types '<unresolved overloaded function type>' and 'int' to binary 'operator<'`. Outside a template no keyword is needed: `g.block<3,3>(0,0)` in `src/rigid_body.cpp:56` is fine because `g` has a concrete type.
1. `if constexpr` for code that compiles for only one n. A plain `if (n == 7)` still compiles its body for `Controller<RigidBody>`. At `include/se3pf/controller.hpp:232` that body makes a `Vec7` from a 6-entry row, passes the 4 × 4 pose as a `Vec7` and assigns a 7-entry row into the 6 × 6 A; Eigen's static checks stop the build at lines 233, 235 and 236 with `static assertion failed: YOU_MIXED_MATRICES_OF_DIFFERENT_SIZES`. A discarded `if constexpr` branch is parsed but never instantiated. The other uses, `include/se3pf/controller.hpp:295`, `include/se3pf/controller.hpp:319` and the tests at `tests/test_controller.cpp:176` and `tests/test_controller.cpp:234`, would compile with a plain `if` too: `mu[6]`, `yDot[6]` and `y[6]` are run-time indexes that the false condition never reaches. There `if constexpr` keeps the n = 6 class free of β code and states the intent.

The constructor's `if (n == 7 && redundancy_ == nullptr)` (`include/se3pf/controller.hpp:176`) is a plain `if` on purpose: its body compiles for both n, so nothing needs to be discarded.

### std::function in the loop

`TangentialReference` stores ν_d or η_d as a `std::function`, and the step calls it once per cycle. That is allowed because calling a `std::function` never allocates; constructing or copying one may.

- Measured with a counting `operator new` (GCC 11.4, libstdc++): `constantVelocity(0.5)` allocates 0 times, because its one-`double` capture fits in the 16-byte buffer inside `std::function`. A lambda capturing three doubles allocates once, and a copy of that reference allocates once more; a move allocates nothing. Two thousand calls allocate nothing.
- The controller never copies the reference in `step`: it calls `reference_.velocity(...)` on its own member. The constructor and `setReference` take the reference by value and `std::move` it into place, which transfers any heap buffer instead of copying it.
- The header states the resulting rule (`include/se3pf/controller.hpp:36-37`): build references before the run, call them freely inside it.
- The cost of the indirection is one indirect call per step, invisible next to the SVD (4 to 5 µs).

### No allocation in step, and the two detectors

Heap allocation in a real-time loop can take unbounded time (a lock inside `malloc`, a page fault) and can fail, so `outputs` and `step` use only fixed-size Eigen types, value structs on the stack (`OutputState`, `Status`) and no strings, vectors or output. Even the logging is outside: `Status` carries the numbers, and `simulate` reserves its log before the loop (`src/rigid_body_example.cpp:89`).

The tests enforce this with two different detectors, because neither sees everything:

| Detector | Sees | Misses | Where |
| --- | --- | --- | --- |
| Counting global `operator new` | `new`: `std::vector` growth, `std::function` buffers, `std::string` | Eigen's own heap use, which calls `malloc` directly | `tests/test_controller.cpp:52-72`, window at lines 829-843 |
| `EIGEN_RUNTIME_NO_MALLOC` with `set_is_malloc_allowed(false)` | every Eigen heap allocation (dynamic-size matrices, heap temporaries) | anything that is not Eigen | `CMakeLists.txt:39`, window at `tests/test_controller.cpp:830-839` |

A scratch demonstration: a test `System` whose `output` builds an `Eigen::MatrixXd` passes the counting `operator new` (0 calls, in Release and in Debug), but in a Debug build with `EIGEN_RUNTIME_NO_MALLOC` the step aborts with Eigen's assertion `heap allocation is forbidden (EIGEN_RUNTIME_NO_MALLOC is defined and g_is_malloc_allowed is false)`. A `std::vector::push_back` inside the step would be the opposite case.

Eigen's check is an `eigen_assert`, which `NDEBUG` removes, so it only works in Debug builds. The `#ifdef EIGEN_RUNTIME_NO_MALLOC` guards in the test keep it compiling in any build; `CMakeLists.txt:39` defines the macro `PUBLIC` on the library, so the tests (and every app) see it.

### Failure is a bool online, an exception offline

The code has two kinds of functions, and they fail differently.

- Offline (constructors, `setReference`, `setRampTime`, `stepCount`, `simulate`'s argument checks, `RigidBody`'s constructor): they throw `std::invalid_argument`. A failure there is a bug or bad input, found before anything moves, and an exception carries a message to the person who made it.
- Online (`Controller::outputs`, `Controller::step`, and below them `Tube::outputs`, `Tube::projectionCondition`): they return `bool`. A pose that leaves the tube is an expected event in a control loop, not a bug, and the caller must act on it (stop the simulation, damp the robot to rest).

Why not exceptions online:

- Throwing allocates the exception object (libstdc++ obtains it from `malloc`), which breaks the no-allocation rule at the worst moment.
- Unwinding the stack takes an unpredictable time.
- A `bool` return makes the failure path visible at every call site (`if (!controller.step(...))`), and the outputs are written only on success: `qdd` is assigned at `include/se3pf/controller.hpp:310`, after every check, and η̂ at `include/se3pf/controller.hpp:313`.

The online code reports invalid numbers as values rather than trapping them. NaN and inf propagate through Eigen arithmetic, and explicit checks turn them into `false`: `allFinite()` at lines 227 and 308 of `include/se3pf/controller.hpp`, `std::isfinite` at line 237, `!(sigmaMin >= 1e-9)` at line 305. The idiom `!(x > 0.0)` or `!(x >= c)` appears wherever NaN must count as failure, because every comparison with NaN is false.

### Lifetimes: who owns what

The controller owns only small things (gains, the reference, η̂); it borrows the tube and the redundancy output.

- `const Tube& tube_` is a reference: the tube holds the frame spline (2001 nodes of 6 × 5 values and derivatives) and must not be copied per controller. The tube's own `const Path& path_` is a reference too (`include/se3pf/tube.hpp:93`).
- `const RedundancyOutput* redundancy_` is a pointer, not a reference, because it is optional: `nullptr` for n = 6. A reference cannot be null.
- Borrowing means the borrowed object must outlive the borrower. The code makes the common mistakes fail to compile: deleted `&&` constructors (`Controller(const Tube&&, ...)` at `include/se3pf/controller.hpp:182-183`, `Tube(const Path&&, ...)` at `include/se3pf/tube.hpp:56`, the `LiftRedundancy` overloads at `include/se3pf/lift.hpp:130-132`), and ref-qualified accessors and deleted copies in `RigidBodyExample` (`include/se3pf/rigid_body_example.hpp:32-42`).
- The test fixtures build each path and tube as function-local `static` objects (`tests/tube_fixture.hpp:31-37`). They are built on first use, in the right order, and live until the program ends.

### Eigen habits in these files

| Habit | Example | Why |
| --- | --- | --- |
| Write the type, never `auto`, for an Eigen result | `const VecN yDot = out.A * dq;` (`include/se3pf/controller.hpp:256`) | `auto` would store an unevaluated expression that re-reads its operands later |
| Start every conditionally filled matrix at zero | `VecN Adq = VecN::Zero();` (`include/se3pf/controller.hpp:262`), `Vec7 dbeta = Vec7::Zero();` (`include/se3pf/controller.hpp:234`) | Eigen does not initialize; the rest case never writes `Adq` |
| Solve, do not invert | `JPsi.partialPivLu().solve(Jb)` (`include/se3pf/controller.hpp:226`), `out.A.partialPivLu().solve(mu - Adq)` (`include/se3pf/controller.hpp:307`) | one factorization, fewer operations, less rounding |
| Check finiteness explicitly | `top.allFinite()` (`include/se3pf/controller.hpp:227`), `result.allFinite()` (`include/se3pf/controller.hpp:308`) | LU does not report a singular matrix; NaN does not throw |
| Coefficient-wise tests through `.array()` | `(dq.array() == 0.0).all()` (`include/se3pf/controller.hpp:263`) | `dq == 0.0` does not compile for a matrix (no `operator==` with a scalar); `.array()` switches to per-entry operations, here a boolean per entry |
| Fixed-size blocks with template sizes | `zeta.head<3>()`, `g.block<3,3>(0,0)` (`src/rigid_body.cpp:56-59`) | block sizes fixed at compile time; only the offsets are run-time values |
