## Design decisions and C++

Each choice in this layer trades a little code for a guarantee: the same lift as the reference, a check that cannot pass on corrupted data, or a lifetime error caught by the compiler. This section collects the choices and the C++ that enforces them.

### Projected Newton or the square system

Two solvers reach the paper's lift. The code uses the projected step; the earlier implementation (and the oracle) uses the square system with h(q) = x(q)ᵀ(q − q_r):

```latex
\begin{bmatrix} J_b(q) \\ \nabla h(q)^\top \end{bmatrix}\Delta q = \begin{bmatrix} e \\ -h(q) \end{bmatrix},\qquad \nabla h = Dx(q)^\top (q - q_\mathrm r) + x(q)
```

A scratch implementation of the square system (Dx by central differences with step 1e-6, step cap 0.2 rad), run on the same grid, gave:

| | Projected step (`projectedNewton`) | Square system |
| --- | --- | --- |
| Needs | J_b only | x(q) and Dx(q): 14 extra kernel vectors (98 determinants of 6 × 6) per update |
| Convergence | linear, factor 0.025 to 0.18 per update along the path | quadratic |
| Updates per node | 9 typical, 13 at most | 2 typical, 3 at most |
| First node, from q_r | 11, no step cap needed (first step 0.97 rad) | 8, with the 0.2 rad cap |
| Result | q* | the same q* to 1.1e-12 (max over all nodes) |
| Closure gap | 1.5e-13 | 5.9e-13 (reference) |

Both stop on the same tolerances and solve the same Lagrange condition, so they give the same lift; only the path to it differs. The projected step was chosen because it has fewer ways to be wrong: no Dx, no finite-difference step, no cap. Its extra updates cost nothing that matters, since the whole lift takes about 0.02 s.

The pitfall it avoids: dropping the Dxᵀ(q − q_r) term from ∇h. Since |q* − q_r| is 0.37 to 1.0 rad on this lift, that term is not small. With xᵀ alone as the last row, the solution of [J_b; xᵀ]Δq = (e, −xᵀ(q − q_r)) is J⁺e + x xᵀ(q_r − q), and x xᵀ = I − J⁺J for r = 1: the "square system" quietly becomes the projected step again, with linear convergence.

### Why minimumCheck is a separate function

A constructor should do what the object needs to be valid, and the controller needs q* to be a critical point that is smooth, closed and inside the joint range. Whether it is a minimum rather than a maximum matters for the paper's claim, not for the controller. The check costs 4000 constrained solves (about 13 ms in Release here, about 2 s in Debug), so it is a free function that the tests call, with the lift passed by `const&`.

It returns a number instead of a `bool`, so a test can compare it with the reference (4.1028e-3) and print it on failure. It returns NaN if it cannot decide, so `d2 > 0` and `d2 >= 4.1e-3` both fail.

### Fail closed: every failure path at a glance

A safety-relevant check must fail when its input is garbage. Every comparison with NaN is false, so `if (x < 0.0) reject;` lets a NaN through, while `if (!(x >= 0.0)) reject;` rejects it. The code writes its checks as `!(good condition)` for that reason.

| Function | On failure | Why this form |
| --- | --- | --- |
| `PandaArm::jointMargin` | NaN (with the NaN joint) or −inf | `margin >= 0.10` fails for both |
| `kernelVector` | NaN entries (rank < 6) | `allFinite()` checks catch it |
| `projectedNewton` (private) | −1 | the constructor throws on −1 |
| `constrainedIK` | `false`, `q` unchanged | the caller's guess survives |
| `Lift::Lift` | throws `std::invalid_argument` or `std::runtime_error` | no half-built lift exists |
| `Lift::eval`, `KernelFrame::eval` | NaN for a non-finite s | the controller's `allFinite` checks fail the step |
| `minimumCheck` | NaN at the first failing node | `d2 > 0` fails |
| `KernelFrame::KernelFrame` | throws `std::runtime_error` | unreachable safeguard |
| `startConfiguration` | `false`, `q` unchanged | as `constrainedIK` |
| `PandaExample::PandaExample` | throws (bad ℓ, lift, start) | built once, before any motion |
| `simulate` | throws on bad T or dt, or if the self-motion start's q̇₀ cannot be computed; `ok = false` on a failed step | argument errors are bugs; a failed step is a result |

The split between exceptions and return values follows the time of the call. Offline code (constructors, `simulate`'s argument checks) throws, because a failure there is a setup error and nobody can continue. Online code (`output`, `eval`, `evaluate`, the controller's `step`) never throws and never allocates; it returns `false` or NaN, and the caller decides: a simulation stops, and the planned robot driver will damp the arm to rest.

### Static limit functions

The PandaArm section explains the hazard: a namespace-scope `static const Vec7` is built by code that runs before `main`, in an order unspecified across `.cpp` files, so another file's static could read it as zeros. Two other designs would also be safe. A `constexpr std::array<double, 7>` is constant-initialized, but it is not an Eigen vector, so every use would need an `Eigen::Map` to do arithmetic. A function returning a reference to a function-local `static const Vec7` is built once on first call, but pays a thread-safe guard check on every call. Returning a fresh `Vec7` by value is the simplest: seven stores, no guard, and `simulate` hoists the two it needs out of its loop. The scalars `tauRateMax`, `flangeSpeedMax` and all of `HardwareBounds` are `double`, a literal type, so they are `static constexpr` and have no such problem.

### References, lifetimes and deleted constructors

The objects of this layer form a graph of references. Who copies and who refers:

| Object | Holds | Built from a temporary? |
| --- | --- | --- |
| `Tube` | `const Path&` | no: `Tube(const Path&&, ...) = delete` |
| `Lift` | copies L, q_r, the nodes and the spline | yes |
| `KernelFrame` | copies its spline | yes |
| `LiftRedundancy` | `const Lift&`, `const KernelFrame&` | no: three deleted `&&` overloads |
| `Controller<PandaArm>` | `const Tube&`, `const RedundancyOutput*` | no for the tube: deleted `&&` overload |
| `PandaExample` | owns all of the above | not copyable, not movable |

A reference member is a promise that the referred object outlives the holder, and the compiler cannot check it. A dangling reference compiles, runs, and reads freed memory, which may still hold the old numbers for a while. The deleted rvalue overloads turn the most common mistake, passing a temporary, into a compile error: for a temporary argument, overload resolution prefers the `&&` overload, and selecting a deleted function is ill-formed.

### Why PandaExample is non-copyable

Copying an object with reference members copies the references, not the objects they refer to. A copy of `PandaExample` would hold its own `path_`, but its `tube_` would still refer to the original's `path_`, and its `beta_` to the original's lift and kernel frame. So the copy constructor and copy assignment are `= delete`, which also suppresses the implicit move constructor. `Tube`'s and `LiftRedundancy`'s reference members already make the implicit copy assignment ill-formed, but the implicit copy constructor would have compiled.

The consequences for use: build the example once, as a named `const` object (`const PandaExample example;` in `panda_sim`), and pass it by `const PandaExample&` (as `simulate` does). The test fixture builds one function-local static shared by all tests.

### Ref-qualified accessors

The parts of `PandaExample` that a controller or a redundancy output keeps references to (`metric`, `path`, `tube`, `lift`, `kernelFrame`, `redundancy`, `coupling`) are returned by `const&`-qualified accessors, with the `const&&` versions deleted. `example.tube()` on a named example compiles; `PandaExample().tube()` does not, because the temporary would die at the end of the statement while the caller kept its tube. The test `HasTube<PandaExample>` checks this at compile time with SFINAE (section on the tests).
